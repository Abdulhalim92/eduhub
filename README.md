# Линия

Multi-Tenant SaaS для учебных центров Таджикистана: панель владельца платформы (SuperAdmin), кабинет центра, учебный модуль, каналы родителя и ученика. Язык интерфейса — русский, валюта — сомони.

В репозитории три слоя, и важно не путать их статус:

| Слой | Где | Статус |
|:--|:--|:--|
| Требования | `docs/spec/src/` | Источник правды, версия 2.5 |
| ТЗ на бэкенд (Go) | `docs/tz/` | Черновик 1, план разработки в `95-dev-plan.md` |
| Кликабельный прототип | `index.html`, `eduhub.html`, `src/` | Работает, бэкенда нет: данные в памяти страницы (mock-слой `api`) |

Каталога `backend/` пока нет. Он появится с первым кодом по ТЗ.

## Быстрый старт

Сборки нет. Tailwind и шрифты идут с CDN, поэтому нужен интернет; страницы открываются двойным кликом (`file://`).

| Файл | Что это |
|:--|:--|
| `index.html` | Панель платформы: центры, модерация каталога, тарифы, биллинг, магазин методик, SMS, рассылки, журнал аудита |
| `eduhub.html` | Кабинет центра: дашборд, группы, ученики, расписание, баланс и счета, баллы, сотрудники, курсы |
| `login.html` | Вход |

Проверка:

```sh
sh tests/run.sh                      # три набора в Chrome headless; итог: PASS: n FAIL: n EXC: n
python3 tools/build-spec.py --check  # проверка ID, ссылок и полей спецификации
```

Текущий результат: `PASS: 610 FAIL: 0 EXC: 0`; спецификация проходит проверку (96 требований, 40 правил BR, 35 вопросов Q).

## Команды

| Задача | Команда |
|:--|:--|
| Тесты прототипа | `sh tests/run.sh` (нужен Chrome; путь задаёт переменная `CHROME`). Вывод `NO OUTPUT` значит, что набор не завершился, а не что тесты прошли |
| Сбросить кеш браузера после правок в `src/` | `sh tools/bump-version.sh` (ставит `?v=` в `index.html`, `eduhub.html`, `login.html`) |
| Проверить спецификацию | `python3 tools/build-spec.py --check` |
| Собрать спецификацию в `.docx` | `python3 tools/build-spec.py` (нужны pandoc: `pip install pypandoc_binary`, и python-docx) |
| Скриншот экрана | `chrome --headless=new --window-size=1440,900 --virtual-time-budget=8000 --screenshot=out.png "file://$PWD/index.html#/<экран>"` |
| Проверки бэкенда (из `backend/`, когда появится) | `go build ./...`, `go vet ./...`, `go test ./... -race -count=1`, `golangci-lint run`, `govulncheck ./...` |
| Графы знаний | `graphify update .` (AST, без LLM); `code-review-graph build` |

## Документация

**Спецификация** (`docs/spec/src/`) — источник правды. Требования имеют идентификаторы (`PLT-…` платформа, `CTR-…` центр, `LRN-…` обучение, `SYS-…` система, `NFR-…`, `INT-…`), бизнес-правила — `BR-NNN`, открытые вопросы — `Q-NNN`.

| Раздел | Содержание |
|:--|:--|
| `00-introduction.md`, `01-roles.md` | Введение, роли и матрица полномочий |
| `10-platform/`, `20-center/`, `30-learning/`, `40-system/` | Требования по областям |
| `50-scenarios.md`, `60-client-platforms.md`, `70-nfr.md`, `75-integrations.md` | Сценарии, клиентские платформы, нефункциональные требования, интеграции |
| `80-business-rules.md`, `85-states.md` | Правила BR и статусы |
| `90-open-questions.md` | Допущения и открытые вопросы владельцу |
| `95-changelog.md` | Что менялось между версиями |

**ТЗ на бэкенд** (`docs/tz/`, индекс `README.md`) описывает, как реализовать требования: архитектура (модульный монолит, Clean Architecture), модель данных и изоляция по `tenant_id` с RLS, права, деньги, API, аудит и интеграции, тесты и приёмка. `85-traceability.md` связывает каждое требование с модулем бэкенда и этапом, `95-dev-plan.md` задаёт план по этапам. При расхождении правится спецификация, а не ТЗ.

**Оформление экранов** — `docs/design/ui-principles.md`. **Контракт методов данных** — шапка `src/js/core/api.js` (прототип) и `docs/tz/50-api.md` (бэкенд).

## Правила проекта

- Согласованное решение владельца вносится сначала в спецификацию (требование, `BR-`, строка в `95-changelog.md`, закрытый `Q-` убирается из `90-open-questions.md`), затем в ТЗ и трассировку, затем собирается `.docx`.
- Правило, влияющее на деньги, тариф или права, живёт только в `api` (прототип) или в сервисе (бэкенд); экран читает флаг из DTO и не пересчитывает правило сам.
- В файлах репозитория фиксируется итог решения, а не история обсуждения.
- Деньги: атомарность, идемпотентность мутаций, журнал аудита, сторно вместо удаления проводок.

## Работа с Claude Code

Инструкции — `CLAUDE.md`, подробные правила — `.claude/rules/`.

| Правило | О чём |
|:--|:--|
| `no-code-without-permission.md` | Код не пишется и не меняется без явного «делай». Вопрос, анализ и ревью — не разрешение: сначала план правок и согласование. Разрешение действует на одну задачу |
| `workflow.md` | Анализ → план → одобрение → реализация → проверка; чек-листы по типу задачи; критерии готовности (без свежего вывода проверки «готово» не говорится) |
| `debugging.md` | Нет фикса без первопричины; сначала падающая проверка в `tests/`; три неудачные попытки — перепланировать |
| `architecture.md`, `go.md`, `db.md`, `migrations.md`, `security.md`, `money.md` | Правила Go-бэкенда: слои, код, PostgreSQL и миграции, безопасность, деньги |

Для бэкенда цепочка такая: `go-planner` (план) → согласование → `go-coder` → `go-reviewer` → `go-tester`. Приёмка работы субагента — навык `subagent-review`: сначала соответствие требованиям, потом качество кода. Миграции — навык `db-migration`, каркас модуля — `service-scaffold`.

Что проверять после правок:

| Что менялось | Проверка |
|:--|:--|
| `src/` (js, css) | `sh tools/bump-version.sh`, затем `sh tests/run.sh`; для вёрстки ещё скриншот |
| `docs/spec/src/` | `python3 tools/build-spec.py` (`--check` без сборки) |
| Решение владельца | Спецификация + `95-changelog.md`, ТЗ и `85-traceability.md`, затем сборка |
| `backend/` | команды Go из раздела «Команды» |

## Что в прототипе сознательно не сделано

Массовые чекбоксы в реестре центров, «Добавить точку» в модерации, загрузка реальных файлов, содержимое уроков (только список материалов), покупка курса центром без участия платформы. Биллинг, онлайн-оплата, SMS и геокодер имитируются. Лицензии обложек (CC BY-SA) нужно проверить перед публичным релизом.
