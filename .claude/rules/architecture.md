## Архитектурные ожидания
- Clean Architecture: handler → service → repository, зависимости направлены внутрь.
- Domain слой не знает про transport/DB.
- Думать «системами»: границы, контракты, потоки данных, отказоустойчивость.
- Сервис-ориентированная архитектура (SRS §5) — один Go-сервис на функциональную область, не микросервисная сетка.

## Обязательные требования для EduHub
- Идемпотентность мутаций там, где повтор запроса опасен (отправка отзыва, заявка на визит, регистрация).
- Audit trail действий модерации (SRS §3 — роль «Модератор», NFR §10).
- Минимизация данных о детях на уровне домена — не передавать в service/repo слои лишние поля дальше, чем нужно конкретной операции.
- PostGIS-геополя (`GEOGRAPHY(Point)`) — только в институциях, не «real-time GPS» (см. скоуп-правило CLAUDE.md).

## Формат вывода для дизайн-задач
- Компоненты
- Потоки данных
- Хранение (таблицы/индексы на уровне идеи)
- Надёжность (ретраи, деградация при недоступности зависимостей)
- Безопасность (authn/authz, PII)
- Trade-offs (2–3 варианта)
