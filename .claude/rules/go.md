## Стиль кода
- Следовать идиоматичному Go (Effective Go, Go Code Review Comments)
- Ясность важнее хитроумных решений
- Явное лучше неявного
- Маленькие функции, одна ответственность
- Имена пакетов: короткие, строчные, без подчёркиваний

## Обработка ошибок
- Всегда возвращать ошибки, не panic (кроме действительно неисправимых ситуаций)
- Оборачивать контекстом: `fmt.Errorf("операция: %w", err)`
- Проверять каждую ошибку; не игнорировать через `_`
- Использовать `errors.Is()` и `errors.As()` для сравнения
- Кастомные типы ошибок для доменных сбоев

## Context
- `context.Context` первым параметром во всех I/O и внешних вызовах
- Никогда не хранить context в структурах
- Использовать `context.WithTimeout` для внешних вызовов (NFR: API p95 ≤ 300мс)
- Уважать отмену context в циклах

## Паттерны конкурентности
- Для параллельных I/O использовать `errgroup.WithContext`, не «голые» goroutine
- Каналы для коммуникации, mutex/atomic для разделяемого состояния
- Избегать утечек goroutine, всегда обеспечивать cleanup
- Прогонять тесты с флагом `-race`

## Логирование
- Использовать `slog` (структурные логи), не `fmt.Println`/`log.Println`
- Не логировать PII (контакты детей/родителей, точные адреса без необходимости)
- Включать `request_id` во все ключевые логи

## Указатели / nil-safety
- Любой `*T` считать optional, не разыменовывать без `nil`-проверки
- Optional поля контракта выражать через `*T` (или `sql.Null*` на границе БД), не через `0`/`""`/`false`
- Не логировать и не отправлять в метрики значения `*ptr` без проверки `ptr != nil`
- Для `map`/`slice` соблюдать JSON-контракт (`omitempty`, `[]` vs `null`)

## Размещение валидации
- Transport (HTTP DTO / middleware): синтаксис (required/format/enum), нормализация входа
- Usecase/service: инварианты операции, orchestration, guard checks
- Domain/entity: чистые инварианты модели без зависимостей от transport/DB
- Repo/adapters: без бизнес-валидации; только техническая корректность и `nil`-handling

## TDD (Test-Driven Development)
- **Мандат**: NO PRODUCTION CODE WITHOUT FAILING TEST FIRST
- **RED**: написать минимальный failing test → убедиться что падает **по правильной причине** (обязательный шаг, нельзя пропускать)
- **GREEN**: минимальный код чтобы тест прошёл
- **REFACTOR**: чистка при зелёных тестах
- Написал код до теста → удали код, начни заново — тест написанный после всегда проходит и ничего не доказывает
- Антипаттерны: тестировать моки вместо реального кода; добавлять test-only методы в production; неполные моки скрывающие поведение; интеграционные тесты как afterthought

## Публичные API
- Не менять публичные API без явного запроса
- Обратная совместимость по умолчанию
- Deprecate перед удалением
