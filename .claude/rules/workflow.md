## Порядок

1. **Анализ:** что есть в коде и в `docs/spec/src/`, где менять, какие риски (бизнес-правила `BR-NNN`, тесты, соседние экраны).
2. **План:** пошаговый, с критерием приёмки у каждого шага; для нетривиальных задач (3+ шага, несколько модулей, развилки) — в Plan Mode.
3. **Согласование:** для нетривиальных задач реализация не начинается до явного одобрения плана. «Простые» задачи скрывают самые опасные непроверенные допущения.
4. **Реализация:** строго текущий шаг, без рефакторинга «по пути». Заметил соседнюю проблему — сообщить, не чинить.
5. **Проверка:** `sh tests/run.sh`; после правок js/css — `sh tools/bump-version.sh`; после правок спецификации — `python3 tools/build-spec.py`.

Если по ходу выяснился неверный план, скрытая зависимость или новый риск — остановиться и перепланировать, а не «дотягивать».

## Критерии готовности

- Нельзя считать задачу выполненной без подтверждения, что изменённое поведение работает.
- **Verification gate:** никаких «должно работать», «наверное», «готово» без свежего вывода команды. Определить команду → выполнить сейчас → прочитать полный вывод → сообщить результат. Прошлые запуски не считаются.
- Если проверка не выполнялась (например, экран не открывался в браузере) — сказать об этом прямо. `tests/run.sh` проверяет DOM и `api`, но не вёрстку: для визуальных правок нужен скриншот (команда в `CLAUDE.md`).
- Итог `tests/run.sh` — строка `PASS: n FAIL: n EXC: n`; код возврата 1 при любом `FAIL`/`EXC`. Если вывод `NO OUTPUT`, набор не завершился (путь к Chrome или `BUDGET`) — это не «тесты прошли».
- Решение проходит «staff-level» самопроверку: корректность, ясность, нет лишнего. Простую задачу не усложнять; обходной путь заменять решением корня проблемы.

## Чек-листы по типу задачи

- **Новый экран платформы:** файл в `src/js/views/<platform|shared>/` → `<script>` в `index.html` до `main.js` → пункт в `SUPER_NAV` (`nav.js`) → `<option>` в `#screenJumper` → требование в спецификации (поле «Экран») → блок в `tests/suite.js` → `bump-version.sh`.
- **Новый экран кабинета центра:** файл в `src/js/views/cabinet/` → `<script>` в `eduhub.html` до `center-main.js` (порядок тегов = порядок меню) → поле `nav` в `registerView` → требование в спецификации → блок в `tests/suite-center.js` → `bump-version.sh`.
- **Новое или изменённое правило / метод `api`:** правило только в `api` и флагом в DTO; денежное, тарифное или правовое действие пишет `log(...)`; ошибка — `ApiError(code, message, fields)`; обновить таблицу «метод → REST» в шапке `api.js`; `BR-NNN` в `80-business-rules.md`, если правило общее.
- **Согласованное с владельцем решение:** сначала Markdown в `docs/spec/src/` (требование, `BR-`, статусы), строка в `95-changelog.md`, закрытый `Q-NNN` убрать из `90-open-questions.md`, затем `python3 tools/build-spec.py`. Допущение, принятое в прототипе без решения владельца, — новый `Q-NNN`.
- **Экран со списком:** фильтры, «Сбросить фильтры», пагинация 10, пустое и ошибочное состояния, шестерёнка вместо ряда кнопок (см. `docs/design/ui-principles.md`).
- **Только документация:** `python3 tools/build-spec.py --check`; тесты прототипа не нужны, если не менялись `src/`.

## Go-бэкенд (`backend/`)

- Go-код живёт в `backend/` со своим `go.mod`; прототип в корне не меняем ради бэкенда.
- Проверка перед «готово» (из `backend/`): `go build ./...`, `go vet ./...`, `go test ./... -race -count=1`, `golangci-lint run`, `govulncheck ./...`. Свежий вывод — как и для `tests/run.sh`.
- Цепочка для нетривиальной фичи: `go-planner` (план) → согласование → `go-coder` → `go-reviewer` → `go-tester`; приёмка работы субагента — навык `subagent-review`. Правило «код без явного „делай“» действует и на `go-coder`.
- Контракт бэкенда — требования `docs/spec/src/` и `docs/tz/50-api.md`, не прототип; расхождение решается правкой спецификации (`Q-NNN`), а не молча в коде.
- Деньги, тариф, баланс — `.claude/rules/money.md`; миграции — навык `db-migration`; новый модуль — навык `service-scaffold`.

## Баг-репорты

Симптом → причина → исправление, коротко и по фактам; не перекладывать рутину диагностики на пользователя. Метод — `debugging.md`.

## Субагенты

- Исследования, параллельные проверки и независимые области — субагентам; в основном контексте остаются интеграция и решения.
- Один субагент — одна задача с чётким ожидаемым результатом.
- Параллельно запускать только при доказанной независимости; перед интеграцией проверить, что агенты не правили одни и те же файлы.
- Реализацию, переданную субагенту, принимать по навыку `subagent-review`: сначала соответствие требованиям, потом качество.

## Приём ревью

- Без поддакивания («отличное замечание!»): переформулировать техническое требование и исправить.
- Возражать по существу, если замечание ломает поведение, противоречит `BR-NNN` или архитектуре, — с ссылкой на код.
- Неясное замечание — сначала уточнить, потом делать.
