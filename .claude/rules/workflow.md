## Рабочий процесс
Всегда придерживаться порядка:
1) Анализ: что есть в коде/доках, где менять, риски.
2) План: пошагово, атомарные шаги с критериями приёмки.
3) Реализация: строго текущий шаг, без «рефакторинга по пути».
4) Ревью: качество, доступность (a11y), консистентность UI.
5) Тесты: покрыть happy path + edge cases.

## Оркестрация задач (по умолчанию)
- Для нетривиальных задач (3+ шага, архитектурные развилки, изменения в нескольких модулях) сначала включать Plan Mode.
- **Design Approval gate**: для нетривиальных задач — никакой реализации до явного одобрения дизайна. "Простые" задачи скрывают самые опасные непроверенные предположения.
- Если в ходе реализации выявлен неверный план, скрытые зависимости или новый риск — остановиться и перепланировать, а не «дотягивать» текущий план.
- Проверка входит в рабочий план как отдельный этап, а не как «опциональный хвост» после реализации.

## Формат плана
- Задачи: 2–5 минут каждая. Внутренний TDD-цикл: write test → verify fail → implement → verify pass → commit.
- Запрещены placeholder'ы: "обработай граничные случаи", "добавь валидацию" — только конкретный код и команды с ожидаемым выводом.
- Self-review перед передачей: покрытие всех требований + scan на размытые формулировки + консистентность сигнатур/пропсов компонентов.

## Стратегия субагентов
- Для исследований, параллельных проверок и анализа независимых областей использовать subagents.
- Один subagent = одна задача с чётким ожидаемым результатом.
- Основной контекст должен оставаться чистым: в main-thread — только интеграция результатов и решения.
- **Двухэтапный review при делегировании реализации**: сначала spec compliance (бинарно ✅/❌ — требования выполнены?) → только после прохождения: code quality review. Нельзя начинать quality review до ✅ spec compliance.
- **Статусы implementer**: `DONE` / `DONE_WITH_CONCERNS` / `NEEDS_CONTEXT` / `BLOCKED` — ответить на вопросы подагента до начала его работы.
- **Параллельные агенты**: dispatch только при доказанной независимости задач. Перед интеграцией — overlap check: убедиться что агенты не изменили одни файлы.

## Критерии готовности (Definition of Done)
- Нельзя отмечать задачу завершённой без подтверждения работоспособности изменённого поведения (запуск в браузере для UI).
- Для значимых изменений сравнивать поведение «до/после», чтобы исключить регрессии и побочные эффекты.
- Перед финализацией провести инженерную self-check: решение должно проходить staff-level review по корректности, ясности и надёжности.
- **Verification gate**: запрещён язык без доказательств — "should work", "наверное", "кажется", "Готово!" без вывода команды. Паттерн: определить команду → выполнить свежо → прочитать полный вывод → подтвердить → сообщить с доказательством. Предыдущие запуски не считаются.

## Качество решения (elegance, без over-engineering)
- Для нетривиальных изменений проверять, можно ли решить задачу проще и чище.
- Если решение выглядит как workaround, предпочесть аккуратное root-cause решение.
- Для простых задач не усложнять реализацию искусственно.

## Автономное исправление дефектов
- Получен баг-репорт, ошибка в консоли, падение CI или failing tests: перейти к диагностике и исправлению без перекладывания рутины на пользователя.
- Пользователю сообщать кратко и по фактам: симптом → причина → исправление.
- Не ограничиваться симптоматическим фиксом, если есть подтверждённая первопричина.

## Task management (если используется в проекте)
- Если в репозитории приняты `tasks/todo.md` и `tasks/lessons.md`, вести их как рабочие артефакты:
  1) план с checkable пунктами;
  2) отметки прогресса по ходу;
  3) итоговый review-блок;
  4) фиксация lessons после пользовательских коррекций.

## Что должно быть явно отражено в планах/ревью
- Где находится состояние (context/hooks/props) и почему именно там
- Как обрабатываются optional/undefined значения и пустые состояния (loading/empty/error)
- Консистентность типов между компонентами (props, context value shapes)

## Приём code review
- Запрещено: "Отличное замечание!", "Абсолютно верно!" — вместо этого переформулировать техническое требование и сразу исправить.
- Technical pushback приветствуется: если фидбек нарушает функциональность, противоречит YAGNI или архитектурному решению — возражать с обоснованием и ссылкой на код.
- Неясный фидбек: стоп, уточнить всё перед реализацией — частичное понимание ведёт к неверной реализации.

## Чекпоинты
- Если работа прервалась — обнови `CLAUDE.local.md` (что сделано / что осталось / следующий шаг).
- Не хранить секреты/API-ключи в заметках.
- Перед удалением ветки или worktree — требовать typed confirmation: пользователь вводит слово `discard`.
