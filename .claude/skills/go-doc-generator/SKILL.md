# Назначение

Навык генерирует техническую документацию для Go-проектов и сохраняет её в `./docs/`.

Навык НЕ должен самостоятельно придумывать структуру документации.

Основной источник структуры и формата — шаблоны из директории `references/`.

Документация должна:
- быть полностью на русском языке;
- основываться только на реальном коде и конфигурации;
- строго соответствовать шаблонам;
- не выходить за рамки обнаруженного функционала;
- не содержать предположений и архитектурных фантазий.

---

# Главный принцип

## references/ — источник истины

Если для документа существует шаблон в `references/`, необходимо:

1. Загрузить соответствующий `.md` файл.
2. Следовать его структуре.
3. Следовать его секциям.
4. Следовать его стилю.
5. Следовать его уровню детализации.

Запрещено:
- самостоятельно расширять структуру документа;
- добавлять новые крупные разделы;
- придумывать архитектурные паттерны;
- описывать то, чего нет в коде;
- превращать документацию в "архитектурное исследование".

Навык должен работать как генератор документации по шаблонам, а не как архитектурный консультант.

---

# Что анализировать

Перед генерацией документации определить структуру проекта.

## Если проект использует стандартную структуру

Анализировать:

- `internal/domain/`
- `internal/handler/`
- `internal/service/`
- `internal/repository/`
- `internal/adapter/`
- `internal/config/`
- `internal/db/`
- `cmd/`
- `pkg/`
- `utils/`

## Если структура нестандартная

Если типичные директории отсутствуют:

1. Выполнить анализ всего репозитория.
2. Определить:
   - точки входа;
   - HTTP handlers;
   - бизнес-логику;
   - data layer;
   - интеграции;
   - конфигурации;
   - migrations;
   - workers/background jobs.
3. Сопоставить найденные компоненты с их фактической ролью.
4. Документировать только реально найденные компоненты.

---

# Всегда анализировать

Независимо от структуры:

- `README.md`
- `config.*`
- `.env*`
- `Dockerfile*`
- `Makefile`
- `.gitlab-ci.yml`
- `.github/workflows/`
- директории migrations

---

# Ограничения генерации

## Запрещено

Не генерировать:
- предположения;
- "best practices" секции;
- ADR без явного наличия;
- рекомендации по рефакторингу;
- гипотетические flows;
- описания будущего поведения;
- выводы о масштабируемости;
- "возможные улучшения";
- описание неиспользуемого кода;
- TODO/FIXME;
- абстрактные объяснения Go или архитектуры.

## Запрещено расширять scope

Если в шаблоне:
- нет раздела observability → не добавлять его;
- нет sequence diagram → не генерировать её;
- нет раздела retry → не описывать retry;

Генерировать только то, что:
1. есть в шаблоне;
2. подтверждается кодом.

---

# Достоверность данных

Документация должна содержать только явно подтверждённые данные из:
- исходного кода;
- конфигураций;
- migrations;
- README;
- templates из `references/`.

Запрещено придумывать:
- команды;
- owners;
- usernames;
- Slack channels;
- email addresses;
- URLs;
- domains;
- ingress names;
- Kubernetes namespaces;
- API gateways;
- environment names;
- deployment topology;
- metric names;
- Kafka/RabbitMQ topics;
- CI/CD stages;
- internal service names;
- configuration values.

---

## Environments и URLs

Не экстраполировать инфраструктуру по типовым enterprise-patterns.

Не выводить URL или окружения по naming conventions.

Если environment или URL не указаны явно:
- не генерировать их;
- не строить их из имени сервиса;
- не предполагать наличие:
  - `dev`
  - `stage`
  - `staging`
  - `preprod`
  - `prod`
  - `production`

Разрешено документировать только реально обнаруженные:
- domains;
- hosts;
- ports;
- endpoints;
- environments.

---

## Неизвестные значения

Если информация отсутствует:
- не подставлять примеры;
- не генерировать правдоподобные фиктивные данные;
- не использовать placeholders как реальные значения.

Предпочтительно:
- пропустить поле полностью;
- либо указать:
  - `unknown`
  - `not specified`

---

## Примеры запрещённого

Плохо:

```md
Owner: Platform team
Contact: #team-platform
Production URL: https://service.company.test
Staging URL: https://service-stage.company.test
```

если эти данные отсутствуют в проекте.

---

## Примеры корректного поведения

Хорошо:

```md
Owner: not specified
```
или полностью пропустить секцию.

---

# Использование code snippets

## Основное правило

Не вставлять фрагменты кода автоматически.

Документация должна преимущественно:
- объяснять поведение системы;
- описывать архитектуру;
- документировать API и flows;
- описывать ответственность компонентов.

А не дублировать исходный код.

---

## Когда snippets разрешены

Вставлять code snippets только если без них невозможно понятно объяснить:

- нестандартный protocol flow;
- сложную SQL-конструкцию;
- важный interface contract;
- структуру DTO;
- critical middleware behavior;
- сложную конфигурацию;
- формат XML/JSON сообщений;
- sequence retry logic;
- integration-specific behavior.

---

## Когда snippets запрещены

Не вставлять snippets:

- в каждый файл автоматически;
- ради "иллюстрации";
- для очевидного CRUD-кода;
- для стандартных handlers;
- для обычных struct definitions;
- для boilerplate;
- для GORM моделей без необходимости;
- для простых маршрутов;
- для обычных config structs.

---

## Ограничения snippets

Если snippet действительно необходим:

- использовать только короткие фрагменты;
- минимально необходимый объём;
- не копировать большие блоки;
- избегать длинных функций;
- избегать полного файла;
- не вставлять несколько похожих примеров.

Максимум:
- 10–20 строк на snippet;
- 1–2 snippets на документ.

---

## Приоритет объяснения над кодом

Предпочитать:
- текстовое описание;
- таблицы;
- sequence diagrams;
- схемы flow;
- краткое описание ответственности.

А не копирование Go-кода.

---

## Формат snippets

Каждый snippet должен:
- сопровождаться пояснением;
- иметь указание файла;
- объяснять зачем он приведён.

Пример:

```go
// internal/adapter/cft/client.go

func (c *Client) BlockAccount(...)
````

Использовать snippets как исключение, а не как основной способ документирования.

# Использование references/

## Правила

При генерации каждого документа:

1. Найти соответствующий шаблон в `references/`.
2. Использовать его как обязательную структуру.
3. Заполнять шаблон только подтверждёнными данными из проекта.

---

# Приоритет источников

При конфликте источников использовать приоритет:

1. `references/*.md`
2. исходный код
3. конфигурации
4. README
5. inferred behavior

Inference использовать только если поведение очевидно из кода.

---

# Что генерировать

Создать:

```text
docs/
├── README.md
├── Architecture.md
├── API.md
├── Database.md
├── Stack.md
├── Glossary.md
├── Integrations.md
├── Deployment.md
└── Workflows/
```

Генерировать только документы:

* для которых есть шаблон;
* либо которые явно запрошены.

---

# Правила документирования

## Описывать

* реальные endpoints;
* реальные DTO;
* реальные таблицы;
* реальные integrations;
* реальные workers;
* реальные env vars;
* реальные HTTP flows.

## Не описывать

* внутренние размышления;
* "вероятно используется";
* "скорее всего";
* "предположительно";
* непроверенные зависимости.

---

# Mermaid

Если используется Mermaid:

- генерировать диаграммы, совместимые с GitLab Mermaid `10.7.0`;
- использовать только стандартный Mermaid syntax;
- использовать только:
  - `flowchart TD`
  - `sequenceDiagram`
  - `erDiagram`

## Правила

Использовать:
- короткие и простые labels;
- ASCII labels по возможности;
- кавычки вокруг labels со спецсимволами;
- только стандартные стрелки:
  - `-->`
  - `->>`
  - `-->>`

Для sequenceDiagram:
- использовать только:
  - `Note over`
  - `Note left of`
  - `Note right of`

Избегать:
- HTML;
- markdown внутри labels;
- multiline labels;
- nested brackets;
- unicode symbols;
- нестандартных стрелок;
- `:::`;
- emoji;
- сложных inline expressions;
- `click`;
- `style`;
- `classDef`;
- `%%{init: }%%`;
- nested subgraph.

При сомнении использовать максимально простой синтаксис.

# Формат документации

## Язык

Вся документация:

* на русском языке;
* без перевода технических терминов.

## Стиль

Документация должна быть:

* короткой;
* структурированной;
* технической;
* конкретной.

Не превращать документы в длинные архитектурные статьи.

---

# Формат файлов

Каждый файл:

```md
# Название

> Назначение: ...
> Обновлено: YYYY-MM-DD

---

## Раздел
```

# Workflows

## Обязательная генерация workflow-документов

Workflow-файлы необходимо создавать для всех endpoint-ов и процессов, которые:

* содержат orchestration logic;
* вызывают service layer;
* взаимодействуют с repository/adapters;
* изменяют состояние системы;
* инициируют async processing;
* запускают payment/business flow;
* содержат retry/post-processing behavior;
* взаимодействуют с внешними системами.

---

## Workflow-файлы должны генерироваться автоматически

Если endpoint:

* не является healthcheck;
* не является trivial CRUD without orchestration;
* содержит бизнес-логику;
* инициирует flow выполнения;

то для него ОБЯЗАТЕЛЬНО должен быть создан отдельный workflow-файл.

---

## Проверка полноты workflows

Перед завершением генерации документации необходимо:

1. Собрать список всех обнаруженных business endpoints.
2. Собрать список созданных workflow-файлов.
3. Проверить соответствие:

   * один business flow → один workflow document.
4. Если workflow отсутствует — создать его.

---

## Workflow coverage

Документация workflows должна покрывать:

* payment flow;
* precheck flow;
* async processing;
* retry processing;
* cancellation/reverse flow;
* integration calls;
* background jobs;
* queue/goroutine orchestration;
* postcheck/status polling;
* любые другие подтверждённые business flows.

---

## Исключения

Не создавать workflow только для:

* `/health`
* `/metrics`
* readiness/liveness probes
* trivial CRUD endpoints без orchestration
* purely technical endpoints

---

## Workflow index

Файл:

```text
docs/Workflows/_index.md
```

обязан содержать:

* список всех workflow-документов;
* краткое описание каждого flow;
* относительные ссылки на workflow-файлы.

После генерации workflows необходимо проверить, что:

* все workflow-файлы присутствуют в `_index.md`;
* ссылки корректны;
* отсутствуют пропущенные flows.

---

# Ожидаемое поведение

После анализа проекта:

1. Прочитать templates из `references/`.
2. Проанализировать проект.
3. Сгенерировать документацию строго по шаблонам.
4. Не выходить за scope шаблонов.
5. Проверить полноту workflow coverage.
6. Сохранить файлы в `./docs/`.
7. Сообщить список созданных файлов.

# Использование references/

## Источник шаблонов

Все шаблоны находятся внутри директории навыка.

Использовать следующие файлы как source templates:

```text
references/README.md
references/Architecture.md
references/API.md
references/Database.md
references/Deployment.md
references/Glossary.md
references/Integrations.md
references/Stack.md
references/Workflows/_index.md
references/Workflows/order-creation.md
```

## Важно

Эти пути относятся к директории самого навыка, а НЕ к анализируемому репозиторию.

Никогда:

* не искать `./references` внутри проекта пользователя;
* не создавать новую директорию `references`;
* не ожидать наличия templates в working directory проекта.

Всегда загружать templates по указанным путям внутри skill.

---

# Приоритет шаблонов

Шаблоны из `references/` являются основным источником структуры документации.

При генерации документации необходимо:

1. Сначала загрузить соответствующий template из `references/`.
2. Следовать структуре template максимально близко.
3. Заполнять только разделы, подтверждённые кодом проекта.
4. Не добавлять новые крупные разделы без необходимости.
5. Не расширять документацию за пределы template.

---

# Режим работы

Перед началом генерации документации:

1. Выполнить анализ проекта.
2. Определить:

   * структуру сервиса;
   * найденные компоненты;
   * integrations;
   * endpoints;
   * workflows;
   * список файлов документации, которые будут созданы.
3. Сформировать краткий план генерации документации.
4. Отдельно показать:

   * список business endpoints;
   * список workflow-файлов, которые будут созданы;
   * соответствие endpoint → workflow file.
5. Показать план пользователю.
6. Не начинать генерацию файлов до подтверждения пользователя.

Только после подтверждения пользователя:

* приступать к генерации документации;
* создавать файлы в `./docs/`.

---

# Финальная проверка

Перед завершением работы обязательно проверить:

* все business endpoints покрыты workflow-файлами;
* `_index.md` содержит ссылки на все workflows;
* нет missing workflow documents;
* нет orphan workflow files;
* все Mermaid diagrams совместимы с GitLab Mermaid 10.7.0;
* документация соответствует templates из `references/`.
