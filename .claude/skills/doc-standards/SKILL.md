# Стандарты документации

## При вызове

1. Уточни задачу — написать новую документацию или проверить/обновить существующую?
2. Уточни тип: README / godoc / архитектура / API / runbook / другое.
3. Для README — использовать `templates/README.md.tmpl`.
4. Применяй языковую политику и правила ниже.
5. Проверь по критериям качества перед выводом.

## Языковая политика

| Контекст | Язык |
|----------|------|
| Код (godoc, комментарии) | Русский |
| Внутренние руководства, ADR | Русский |
| API-описания (proto, OpenAPI) | Русский |
| Коммиты | English |

## Godoc
- Документировать все экспортируемые типы, функции, методы
- Формат: что делает + граничные случаи + пример
- Не документировать очевидное из сигнатуры
- Package-level комментарий в `doc.go`

## Правила Markdown
- Один `#` на файл (заголовок)
- Не перескакивать уровни заголовков (h1 → h3)
- Всегда указывать язык в блоках кода
- Примеры должны быть рабочими (копипаст → работает)
- Таблицы для структурированных данных (не bullet-списки)
- Ссылки: относительные внутри репо, абсолютные для внешних

## Структура проектной документации
```
docs/
├── README.md           # Обзор проекта, quickstart
├── architecture.md     # Архитектура системы
├── adr/                # Architectural Decision Records
│   └── NNNN-title.md
├── api/                # Спецификации API
├── guides/             # How-to руководства
└── runbook/            # Операционные runbooks
```

## Что НЕ документировать
- Очевидное поведение из сигнатур кода
- Временные хаки без TODO/FIXME
- Внутренние детали реализации, которые часто меняются
- То, что лучше выражается тестом

## Проверка качества
- Может ли новый разработчик onboard-иться только по этим документам?
- Каждый внешний API-эндпоинт задокументирован с примером запроса/ответа?
- Runbooks проверены (кто-то реально прошёл по шагам)?
