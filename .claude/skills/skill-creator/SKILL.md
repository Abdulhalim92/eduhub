# Создатель скиллов

## Iron Law
**НЕТ СКИЛЛУ БЕЗ FAILING TEST ПЕРВЫМ.** Без теста невозможно знать что скилл учит правильному поведению.

RED: запустить сценарии без скилла, зафиксировать поведение агента дословно.
GREEN: написать минимальный скилл закрывающий зафиксированные нарушения.
REFACTOR: найти новые рационализации, добавить явные счётчики, повторять до исчезновения новых.

## Persuasion principles (Meincke et al. 2025, 33%→72% compliance)
Использовать в скиллах дисциплинирующего характера:
- **Authority**: "YOU MUST", "No exceptions", "обязательный шаг"
- **Commitment**: явные announcements + tracking ("Объявляю: использую скилл X")
- Избегать: Reciprocity и Liking — конфликт с честным техническим фидбеком

## Правила структуры
- Description: начинать с "Используй когда..." + конкретные trigger-условия
- Часто загружаемые скиллы: под 200 слов в SKILL.md
- Отдельные файлы только для 100+ строк справочного контента
- References: один уровень вложенности от SKILL.md

---

Скилл для создания новых скиллов и их итеративного улучшения.

На высоком уровне процесс создания скилла выглядит так:

- Определить что скилл должен делать и как примерно работать
- Написать черновик скилла
- Создать несколько тестовых промптов и запустить claude-с-доступом-к-скиллу на них
- Помочь пользователю оценить результаты качественно и количественно
  - Пока запуски идут в фоне, набросать количественные оценки (assertions). Объяснить их пользователю.
  - Использовать скрипт `eval-viewer/generate_review.py` для показа результатов и метрик
- Переписать скилл на основе обратной связи
- Повторять до удовлетворения
- Расширить тестовый набор и попробовать в большем масштабе

Задача — понять где пользователь находится в этом процессе и помочь двигаться дальше. Например, пользователь говорит «хочу скилл для X» — помочь уточнить суть, написать черновик, написать тест-кейсы, определить метод оценки, запустить всё и повторять.

Если пользователь уже имеет черновик — сразу переходить к eval/итерации.

Быть гибким: если пользователь говорит «не нужны оценки, просто помоги» — делать именно это.

После готовности скилла можно запустить оптимизатор описания — отдельный скрипт для улучшения точности триггеринга.

## Общение с пользователем

Создатель скиллов используется людьми с разным уровнем технической грамотности. Обращать внимание на контекстные подсказки.

В общем случае:
- «оценка» и «бенчмарк» — допустимые термины
- «JSON» и «assertion» — объяснять если нет явных сигналов что пользователь знает эти термины

Кратко пояснять термины при сомнении.

## Создание скилла

### Фиксация намерения

Начать с понимания намерения пользователя. Текущий разговор может уже содержать workflow который нужно захватить («сделай это скиллом»). Если так — извлечь ответы из истории: использованные инструменты, последовательность шагов, исправления, форматы ввода/вывода.

1. Что этот скилл должен позволить Claude делать?
2. Когда скилл должен срабатывать? (какие фразы/контексты пользователя)
3. Какой ожидаемый формат вывода?
4. Нужно ли создавать тест-кейсы? Скиллы с объективно верифицируемыми выводами (преобразование файлов, извлечение данных, генерация кода, фиксированные workflow) выигрывают от тест-кейсов. Субъективные скиллы (стиль письма, искусство) часто не нуждаются в них.

### Интервью и исследование

Проактивно задавать вопросы о граничных случаях, форматах ввода/вывода, примерах файлов, критериях успеха и зависимостях. Не писать тест-промпты до прояснения этих вопросов.

Проверить доступные MCP — если полезны для исследования, использовать в параллельных субагентах.

### Написание SKILL.md

На основе интервью заполнить компоненты:

- **name**: Идентификатор скилла
- **description**: Когда срабатывать, что делает. Это основной механизм триггеринга — включать и что делает скилл, И конкретные контексты использования. Описание должно быть немного «настойчивым». Вместо «Как построить быстрый дашборд для отображения данных» — «Как построить быстрый дашборд. Использовать этот скилл всегда когда пользователь упоминает дашборды, визуализацию данных, внутренние метрики, даже если явно не просит «дашборд».»
- **Остальное содержимое скилла :)**

### Гайд по написанию скиллов

#### Структура скилла

```
skill-name/
├── SKILL.md (обязательно)
│   ├── YAML frontmatter (name, description обязательны)
│   └── Markdown-инструкции
└── Bundled Resources (опционально)
    ├── scripts/    - Исполняемый код для детерминированных задач
    ├── references/ - Документация загружаемая в контекст по мере необходимости
    └── assets/     - Файлы используемые в выводе (шаблоны, иконки, шрифты)
```

#### Прогрессивное раскрытие (Progressive Disclosure)

Скиллы используют трёхуровневую систему загрузки:
1. **Метаданные** (name + description) — всегда в контексте (~100 слов)
2. **Тело SKILL.md** — в контексте при срабатывании (<500 строк идеально)
3. **Bundled resources** — по мере необходимости (без ограничений, скрипты могут выполняться без загрузки)

**Ключевые паттерны:**
- Держать SKILL.md до 500 строк; при приближении к лимиту добавить иерархию с чёткими указателями
- Явно ссылаться на файлы из SKILL.md с указанием когда их читать
- Для больших файлов (>300 строк) — включить оглавление

**Организация по доменам**: Когда скилл поддерживает несколько фреймворков — организовать по вариантам:
```
cloud-deploy/
├── SKILL.md (workflow + выбор)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

#### Принцип отсутствия сюрпризов

Скиллы не должны содержать вредоносный код, эксплойты или контент компрометирующий безопасность. Содержимое скилла не должно удивлять пользователя при описании.

#### Паттерны написания

Предпочитать повелительную форму в инструкциях.

**Определение форматов вывода:**
```markdown
## Структура отчёта
ВСЕГДА использовать этот точный шаблон:
# [Заголовок]
## Краткое резюме
## Ключевые выводы
## Рекомендации
```

**Паттерн примеров:**
```markdown
## Формат коммита
**Пример 1:**
Ввод: Добавлена аутентификация пользователей с JWT
Вывод: feat(auth): implement JWT-based authentication
```

### Стиль написания

Объяснять модели ПОЧЕМУ что-то важно вместо жёстких MUST. Использовать теорию разума, стремиться к обобщению а не к узкой заточке под примеры. Писать черновик, затем смотреть свежим взглядом и улучшать.

### Тест-кейсы

После написания черновика создать 2–3 реалистичных тестовых промпта. Поделиться с пользователем: «Вот несколько тест-кейсов. Они подходят, или хотите добавить?» Затем запустить.

Сохранить в `evals/evals.json`. Пока не писать assertions — только промпты.

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "Задача пользователя",
      "expected_output": "Описание ожидаемого результата",
      "files": []
    }
  ]
}
```

## Запуск и оценка тест-кейсов

Это непрерывная последовательность — не останавливаться на полпути.

Результаты размещать в `<skill-name>-workspace/` рядом с директорией скилла. Организовать по итерациям (`iteration-1/`, `iteration-2/`) и тест-кейсам (`eval-0/`, `eval-1/`).

### Шаг 1: Запустить все прогоны (со скиллом и базовые) в одном проходе

Для каждого тест-кейса запустить два субагента в одном ходу — один со скиллом, один без.

**Прогон со скиллом:**
```
Выполни задачу:
- Путь к скиллу: <путь>
- Задача: <eval промпт>
- Входные файлы: <файлы или "нет">
- Сохранить вывод в: <workspace>/iteration-N/eval-ID/with_skill/outputs/
```

**Базовый прогон** (тот же промпт):
- **Новый скилл**: без скилла вообще, сохранить в `without_skill/outputs/`
- **Улучшение**: старая версия как снимок, сохранить в `old_skill/outputs/`

Записать `eval_metadata.json` для каждого тест-кейса:
```json
{
  "eval_id": 0,
  "eval_name": "описательное-имя",
  "prompt": "Промпт задачи",
  "assertions": []
}
```

### Шаг 2: Пока прогоны идут — набросать assertions

Не ждать окончания прогонов. Набросать количественные assertions для каждого тест-кейса и объяснить их пользователю.

Хорошие assertions объективно верифицируемы и имеют описательные имена. Субъективные скиллы (стиль письма, дизайн) лучше оценивать качественно.

### Шаг 3: При завершении прогонов — сохранить данные о времени

При завершении каждого субагента получается уведомление с `total_tokens` и `duration_ms`. Сохранить немедленно в `timing.json`:

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

### Шаг 4: Оценить, агрегировать, запустить просмотрщик

1. **Оценить каждый прогон** — субагент-грейдер читает `agents/grader.md` и оценивает assertions. Сохранить в `grading.json`. Поля: `text`, `passed`, `evidence`.

2. **Агрегировать в бенчмарк:**
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```

3. **Аналитический проход** — прочитать `agents/analyzer.md` для поиска паттернов.

4. **Запустить просмотрщик:**
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   
   Для Cowork/headless: использовать `--static <output_path>`.

5. **Сообщить пользователю**: «Открыл результаты в браузере. Две вкладки — “Выводы” для просмотра тест-кейсов и обратной связи, “Бенчмарк” для количественного сравнения.»

### Шаг 5: Прочитать обратную связь

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "не хватает подписей на осях", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "идеально, отлично", "timestamp": "..."}
  ],
  "status": "complete"
}
```

Пустая обратная связь = пользователь доволен. Сфокусироваться на тест-кейсах с конкретными замечаниями.

Завершить сервер просмотрщика: `kill $VIEWER_PID 2>/dev/null`

## Улучшение скилла

Прогоны выполнены, пользователь просмотрел результаты — теперь нужно сделать скилл лучше.

### Как подходить к улучшениям

1. **Обобщать из обратной связи.** Цель — создать скилл работающий миллионы раз на разных промптах. Здесь мы итерируем на нескольких примерах только для скорости. Скилл заточенный только под эти примеры — бесполезен. Вместо точечных изменений — попробовать разные метафоры, рекомендовать другие паттерны работы.

2. **Держать промпт лаконичным.** Удалять то, что не работает. Читать транскрипты, а не только финальные выводы — если скилл заставляет модель тратить время на непродуктивные действия, убрать вызывающие это части.

3. **Объяснять «почему».** Объяснять причину каждой инструкции. Современные LLM умны — при хорошем контексте они идут дальше буквального выполнения инструкций. Если находишься в режиме ВСЕГДА/НИКОГДА капслоком — жёлтый флаг. Объяснить логику вместо жёстких правил.

4. **Искать повторяющуюся работу.** Если все 3 тест-кейса независимо написали похожий скрипт — скилл должен включать этот скрипт в `scripts/`. Написать один раз, сохранить, указать скиллу использовать.

### Итерационный цикл

После улучшения скилла:

1. Применить улучшения
2. Перезапустить все тест-кейсы в новую директорию `iteration-N+1/`, включая базовые прогоны
3. Запустить просмотрщик с `--previous-workspace`
4. Ждать пока пользователь просмотрит и сообщит
5. Читать новую обратную связь, улучшать снова, повторять

Продолжать пока:
- Пользователь говорит что доволен
- Вся обратная связь пустая
- Нет значимого прогресса

## Расширенный режим: слепое сравнение

Для более строгого сравнения версий — читать `agents/comparator.md` и `agents/analyzer.md`. Основная идея: дать два вывода независимому агенту не говоря какой какой, и позволить ему судить о качестве.

Опционально, требует субагентов. Цикл человеческого ревью обычно достаточен.

## Оптимизация описания

Поле `description` в frontmatter SKILL.md — основной механизм запуска скилла. После создания или улучшения — предложить оптимизацию описания.

### Шаг 1: Сгенерировать trigger eval-запросы

Создать 20 eval-запросов — mix из должен-сработать и не-должен-сработать. Сохранить как JSON:

```json
[
  {"query": "промпт пользователя", "should_trigger": true},
  {"query": "другой промпт", "should_trigger": false}
]
```

Запросы должны быть реалистичными. Для **should-trigger** (8–10): разные формулировки одного намерения, часть — неявные. Для **should-not-trigger** (8–10): похожие ключевые слова, но другой контекст — это самые ценные тест-кейсы.

### Шаг 2: Согласовать с пользователем

1. Прочитать шаблон из `assets/eval_review.html`
2. Заменить плейсхолдеры (данные, имя скилла, описание)
3. Записать во временный файл и открыть: `open /tmp/eval_review_<skill-name>.html`
4. Пользователь редактирует запросы и нажимает «Export Eval Set»
5. Файл скачивается как `eval_set.json` в `~/Downloads/`

### Шаг 3: Запустить цикл оптимизации

```bash
python -m scripts.run_loop \
  --eval-set <путь-к-trigger-eval.json> \
  --skill-path <путь-к-скиллу> \
  --model <model-id> \
  --max-iterations 5 \
  --verbose
```

Использовать model ID из системного промпта текущей сессии.

Скрипт автоматически: разделяет eval-набор на 60% train / 40% test, оценивает текущее описание (каждый запрос 3 раза), затем вызывает Claude для предложения улучшений. Возвращает `best_description` выбранный по test-score.

### Шаг 4: Применить результат

Взять `best_description` из JSON-вывода и обновить frontmatter SKILL.md. Показать до/после и отчёт по баллам.

## Инструкции для работы без CLI

Основной workflow тот же (черновик → тест → ревью → улучшение → повторение), но без субагентов:

- **Запуск тест-кейсов**: Последовательно, читая SKILL.md самостоятельно. Пропустить базовые прогоны.
- **Ревью результатов**: Показать результаты прямо в разговоре. Спросить обратную связь inline.
- **Бенчмаркинг**: Пропустить — требует сравнения с базовой линией.
- **Оптимизация описания**: Требует `claude` CLI — пропустить без него.
- **Слепое сравнение**: Требует субагентов — пропустить.

**Обновление существующего скилла**: Сохранить оригинальное имя директории и поле `name`. Скопировать в `/tmp/skill-name/` перед редактированием если путь может быть read-only.

## Инструкции для Cowork

- Субагенты доступны, основной workflow работает
- Нет браузера: использовать `--static <output_path>` для просмотрщика
- Обратная связь: кнопка «Submit All Reviews» скачивает `feedback.json`
- Оптимизация описания работает через `claude -p` в subprocess
- **СОЗДАВАТЬ ПРОСМОТРЩИК ОЦЕНОК ДО САМОСТОЯТЕЛЬНОЙ ОЦЕНКИ**: после прогонов всегда запускать `generate_review.py` для человеческого ревью

## Справочные файлы

- `agents/grader.md` — оценка assertions по выводам
- `agents/comparator.md` — слепое A/B сравнение двух выводов
- `agents/analyzer.md` — анализ почему одна версия победила другую
- `references/schemas.md` — JSON-структуры для evals.json, grading.json и др.
