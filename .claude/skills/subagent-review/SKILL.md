# Двухэтапная приёмка работы субагента

## Принцип

Соответствие требованиям и качество кода — разные проверки. Качество не проверять, пока нет ✅ по требованиям.

## Статусы исполнителя

| Статус | Действие |
|---|---|
| `DONE` | Перейти к проверке соответствия требованиям |
| `DONE_WITH_CONCERNS` | Сначала разобрать замечания исполнителя, затем проверка требований |
| `NEEDS_CONTEXT` | Дать недостающую информацию, перезапустить |
| `BLOCKED` | Диагностировать: контекст / модель / декомпозиция / эскалация пользователю |

## Этап 1. Соответствие требованиям

Вопрос: **каждое требование выполнено?** Источник требований — задача, план и `docs/spec/src/` (`ID`, `BR-NNN`).

Результат бинарный:
- ✅ всё выполнено — к этапу 2;
- ❌ перечислить невыполненное → исполнитель исправляет → повторная проверка.

Отчёту исполнителя не доверять: проверять по коду и свежему запуску `sh tests/run.sh`.

## Этап 2. Качество кода

Только после ✅. Вопрос: **сделано ли хорошо?** Проверять:
- границы слоёв: UI зовёт только `api.*`, правила живут в `api`, а не в экране;
- `esc()` на всём вводе в `innerHTML`; новые hex не добавляются, цвета берутся из `tailwind-config.js` (старые литералы вроде `accent-[#3C5C73]` не трогать без отдельной задачи);
- паттерн экрана (`begin` → `stale` → `errorRow`), мутации через `mutate`, оверлеи в `#modalRoot`/`#menuRoot`;
- денежные и правовые действия: основание, запись `log(...)`, ошибки `ApiError.fields`;
- нет лишнего: неработающие действия не показаны, нет рефакторинга вне задачи;
- тесты добавлены в `tests/suite.js`, `bump-version.sh` выполнен.

Серьёзность: Critical — сразу; Important — до завершения задачи; Minor — отметить.

## Non-negotiable

- Не пропускать приёмку.
- Не начинать этап 2 до ✅ этапа 1.
- Не принимать «почти выполнено».
