# Введение

## Концепция продукта

«Линия» — B2B2C-платформа формата Multi-Tenant SaaS: единое облачное ядро для управления сетью независимых учебных центров с изоляцией их коммерческих данных, локальным учётом начислений, платежей, расходов и зарплат, системой мотивации учеников (баллы, которыми ученик оплачивает часть месяца), B2B-магазином методических материалов и единым каталогом центров на карте города для родителей.

Система разделена на два логических контура: изолированный контур каждого учебного центра (идентификатор `tenant_id`) и глобальный пользовательский контур (Global ID для учеников и родителей, единый каталог центров).

## Как устроен документ

Документ сгруппирован по **областям** (кому принадлежит процесс) и **модулям** (предметные области внутри). Процесс описывается один раз — в области того, кто им владеет. Остальные роли получают короткий подраздел «Сторона центра» или ссылку на номер требования.

| Часть | Область | Основные роли |
|:--|:--|:--|
| A | Управление платформой | SuperAdmin |
| B | Центр: расписание, ученики, финансы, зарплаты | Владелец, Admin центра, Кассир |
| C | Обучение: журнал, кабинеты, каталог на карте | Преподаватель, Ученик, Родитель |
| D | Сквозные службы: аудит, мультиязычность, документы | все роли |

Далее идут сценарии, клиентские платформы, нефункциональные требования, интеграции, каталог бизнес-правил, статусы и переходы, открытые вопросы, история изменений и приложение с трассировкой.

## Идентификаторы требований

Каждое требование имеет устойчивый идентификатор **`ОБЛАСТЬ-МОДУЛЬ-НОМЕР`**, например [`PLT-BAL-030`](#PLT-BAL-030). Номера не переиспользуются и не меняются при переносе раздела: на них ссылаются код, тесты и задачи. Нумерация идёт с шагом 10, чтобы можно было вставить новое требование между существующими.

| Область | Код | Модуль |
|:--|:--|:--|
| Платформа | `PLT-DSH` | Дашборд и рабочие очереди |
| | `PLT-CTR` | Реестр центров и подключение |
| | `PLT-TRF` | Тарифы и лимиты |
| | `PLT-BAL` | Баланс на платформе и овердрафт |
| | `PLT-BIL` | Счета и оплата |
| | `PLT-SMS` | Биллинг SMS-пакетов |
| | `PLT-MKT` | Магазин методик |
| | `PLT-MOD` | Модерация каталога |
| | `PLT-COM` | Рассылки и справочники |
| | `PLT-AUD` | Журнал аудита платформы |
| Центр | `CTR-ORG` `CTR-SCH` `CTR-STU` `CTR-AST` `CTR-CRM` `CTR-ANL` `CTR-FIN` `CTR-PAY` | Структура, расписание, ученики, инвентарь, CRM, аналитика, финансы (начисления, платежи, расходы), зарплаты |

Новая область или модуль добавляется как новый файл исходников без перенумерации остального.

## Шаблон требования

Заголовок: идентификатор и название. Под ним строка полей и текст:

- **Роль** — кто выполняет или кому принадлежит функция.
- **Согласование** — «согласовано» или «допущение» (принято в прототипе, ждёт решения владельца, см. раздел «Открытые вопросы»).
- **Реализация** — «прототип» (работает в кликабельном прототипе), «частично» или «план».
- **Экран** — где функция видна пользователю. Из полей «Роль», «Реализация» и «Экран» строится приложение «Трассировка».
- **Описание** — что и зачем.
- **Правила** — ссылки на бизнес-правила `BR-…`; сами правила записаны один раз в каталоге.
- **Критерии приёмки** — проверяемые формулировки «Дано / Когда / Тогда». Для планируемых функций критерии добавляются при проработке модуля.

Оформление экранов (цвета, таблицы, пагинация, фильтры) описано не здесь, а в отдельном дизайн-гайде проекта.

## Глоссарий

| Термин | Значение |
|:--|:--|
| Центр (tenant) | Независимая организация-клиент платформы со своими данными, штатом и кассой |
| Global ID | Единый аккаунт родителя или ученика по номеру телефона, объединяющий все центры |
| Shadow ID | Теневой профиль ребёнка без телефона; позже привязывается к номеру ребёнка с сохранением истории |
| Баланс на платформе | Предоплаченные средства центра для оплаты счетов платформы; не касса и не выручка центра |
| Овердрафт центра | Лимит, на который баланс на платформе может уйти в минус; использованная часть — долг перед платформой |
| Долг ученика | Непогашенный остаток начисления за месяц по связке «ученик + группа»; не связан с овердрафтом центра ([`BR-019`](#BR-019)) |
| Feature Flags | Включение и выключение модулей и лимитов для конкретного центра |
| Режим поддержки (Impersonation) | Вход сотрудника платформы в кабинет центра только для чтения, без финансов, с причиной и таймером; фиксируется в журналах платформы и центра |
| Счёт | Документ платформы центру: продление, смена тарифа, курс, SMS-пакет |
| Заявка на публикацию | Карточка филиала, отправленная центром на модерацию каталога |
| Заявка на курс | Запрос центра на получение курса из магазина методик |
| Передача курса | Создание доступа центра к курсу после оплаты, бонусом или списанием с баланса |
| Собственный курс центра | Курс, который центр создал сам; виден только этому центру |
| Центр у лимита | Центр, у которого использование сотрудников, хранилища или филиалов достигло порога ([`BR-021`](#BR-021)) |
| Churn Risk (отток) | Риск ухода центра; признак — отсутствие входов более 10 дней |
| NPS | Оценка качества уроков родителем или учеником (1–5 звёзд) |
| Z-отчёт | Итоговый отчёт кассира при закрытии кассовой смены: наличные, эквайринг, p2p |
| Сторно | Отмена финансовой записи отдельной операцией с причиной (физическое удаление запрещено) |
| Лот баллов | Порция баллов ученика с датой выдачи, сроком действия и остатком ([`BR-030`](#BR-030)) |
| Связка «ученик + группа» | Единица начисления: на неё создаётся счёт за месяц ([`BR-028`](#BR-028)) |
| Сверка | Подтверждение администратором, что принятый кассиром платёж действительно поступил ([`CTR-FIN-070`](#CTR-FIN-070)) |
| p2p-платёж | Перевод родителя на кошелёк или карту сотрудника центра, который фиксируется в платформе ([`CTR-FIN-060`](#CTR-FIN-060)) |

# Роли и права (RBAC)

## Роли центра и участников

| Роль | Уровень доступа | Зона ответственности и полномочия |
|:--|:--|:--|
| Owner (владелец центра) | Весь центр, все филиалы | Один на центр ([`BR-039`](#BR-039)). Подписка, тариф и оплата счетов платформы, настройки центра ([`CTR-SET-010`](#CTR-SET-010)), назначение администраторов и кассиров, отчёты и журнал аудита по всему центру, аналитика, расходы, зарплаты, ключи эквайринга. Может выполнять всё, что доступно администратору |
| Admin (администратор филиала) | Один филиал | Привязан строго к одному филиалу ([`BR-038`](#BR-038)). Ученики, родители, группы, расписание, замены, начисления и скидки, сверка платежей, расходы филиала, заявки и пробные уроки, цены групп и бюджеты баллов своего филиала, курсы и материалы. Не меняет тариф, подписку и общие настройки центра, не удаляет владельца |
| Cashier (кассир) | Один филиал | Привязан строго к одному филиалу ([`BR-038`](#BR-038)). Внесение платежей (касса, эквайринг, p2p), квитанции, открытие и закрытие смены (Z-отчёт). Не меняет начисления и скидки, не видит журнал аудита |
| Teacher (преподаватель) | Назначенные группы | Гео-чек-ин, электронный журнал, баллы за успехи, создание курсов, материалов и тестов центра, групповые и индивидуальные занятия. Не видит телефоны родителей и долги учеников, свою зарплатную ведомость видит. Группы коллег — только при замене на дату занятия |
| Student (ученик) | Глобальный профиль (Global ID) | Расписание по всем центрам, материалы, ДЗ и тесты, баланс баллов и оплата ими, долги, платежи и квитанции (своё, только для ученика 14+ со своим входом, [`BR-036`](#BR-036)), оценка уроков. Не вносит платежи |
| Parent (родитель) | Глобальный профиль и привязанные дети | Всё по своему ребёнку: расписание, посещаемость, оценки, долги, баллы и их траты, квитанции; поиск в каталоге на карте, оценка качества. Родители одного ребёнка равноправны и не видят данные друг друга. Права родителя отзывает администратор по заявлению |

Один человек может иметь несколько ролей в одном центре, права складываются ([`BR-040`](#BR-040)). Роль менеджера центра не используется: заявки и пробные уроки ведёт администратор.

## Роли команды платформы

Команда платформы разделена по зонам ответственности. Никто из команды не видит финансы центров ([`BR-022`](#BR-022)); телефоны владельцев центров видят владелец платформы, менеджер и финансы, остальным они показываются в маске.

| Роль | Зона |
|:--|:--|
| Владелец платформы (SuperAdmin) | Всё в пределах платформы, включая управление командой и передачу владения центром ([`BR-039`](#BR-039)) |
| Менеджер по клиентам | Подключение и сопровождение центров, закрепление менеджера, контакты, предложение смены тарифа и выставление счёта на неё, магазин методик, выдача и сброс доступа владельцу центра |
| Финансы | Счета, баланс на платформе, овердрафт, SMS-пакеты, ручное подтверждение оплат; остальное только чтение |
| Модератор | Модерация каталога и заявок на публикацию филиалов |
| Поддержка | Режим поддержки только для чтения ([`PLT-CTR-050`](#PLT-CTR-050)) |

# Часть A. Управление платформой (SuperAdmin)

Область объединяет всё, чем управляет владелец платформы: центры, тарифы, взаиморасчёты, SMS, магазин методик, модерацию каталога и контроль. Процессы, в которых участвует центр (заявки на курсы, заявки на публикацию филиалов, оплата счетов), описаны здесь один раз; в подразделах «Сторона центра» показано, что видит и делает центр.

Правила, общие для нескольких модулей, вынесены в каталог бизнес-правил (`BR-…`); статусы и переходы — в раздел «Статусы и переходы».

## PLT-DSH. Дашборд и рабочие очереди {#PLT-DSH}

Первый экран SuperAdmin и очереди, которые требуют внимания: отток, истекающие подписки, заявки.

### PLT-DSH-010 Дашборд платформы {#PLT-DSH-010}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Главная

Сводные показатели: число центров, активные подписки, выручка платформы, отправлено SMS и остаток в пакетах; график динамики подключений и выручки; виджет «Требует внимания» (ожидающие модерации филиалы, истекающие подписки, риск оттока, центры у лимита — [`PLT-TRF-040`](#PLT-TRF-040)); таблица «Активность центров» (тариф, последний вход, уроков за 7 дней, статус). Таблица служит для просмотра: клик по строке открывает реестр [`PLT-CTR-010`](#PLT-CTR-010), меню даёт переходы в кабинет и к балансу.

В прототипе значения KPI и график демонстрационные; счётчики виджета «Требует внимания» считаются по данным.

**Критерии приёмки**

1. Дано: на платформе есть центры в очередях. Когда SuperAdmin открывает главную. Тогда виджет «Требует внимания» показывает число по каждой очереди и общую сумму.
2. Когда SuperAdmin нажимает на строку в «Активности центров». Тогда открывается реестр центров, отфильтрованный по этому центру.

### PLT-DSH-020 Контроль оттока (Churn Risk) {#PLT-DSH-020}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Риск оттока

Список активных центров, не заходивших в систему более 10 дней, для проактивной работы менеджеров. Для каждого центра: причины риска (дни без входа, мало уроков, истекающая подписка), последний вход, уроков за 7 дней, уровень риска (низкий, средний, высокий; рассчитывается сервером), ответственный менеджер, отметка «Контакт сегодня». Плитки: центров в зоне риска, высокий риск, выручка под угрозой, без менеджера. Фильтры: все, без менеджера, связались; уровень риска.

**Критерии приёмки**

1. Дано: центр заходил 11 и более дней назад. Тогда он попадает в список; центры с недавним входом и заблокированные в список не попадают.
2. Когда SuperAdmin назначает менеджера. Тогда выбор сохраняется, фильтр «Без менеджера» перестаёт показывать этот центр.
3. Когда SuperAdmin отмечает контакт. Тогда центр получает метку «Контакт сегодня», повторная отметка недоступна.

### PLT-DSH-030 Истекающие подписки {#PLT-DSH-030}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Истекающие подписки

Центры платных тарифов, у которых подписка истекает в выбранном окне (7, 14 или 30 дней; по умолчанию 14). Бесплатный тариф не истекает. Действия: выставить счёт на продление (затем подтвердить оплату — [`PLT-BIL-040`](#PLT-BIL-040)), отправить напоминание владельцу, открыть баланс и овердрафт, сменить тариф. Фильтры: окно, тариф, наличие счёта. Плитки: истекают в ближайшие 7 дней, всего в окне, сумма к получению, выставленные счета.

**Правила:** [`BR-009`](#BR-009), [`BR-012`](#BR-012), [`BR-034`](#BR-034).

**Критерии приёмки**

1. Дано: у центра нет открытого счёта на продление. Когда SuperAdmin выставляет счёт. Тогда в строке появляется номер счёта и кнопка «Подтвердить оплату».
2. Когда счёт уже выставлен. Тогда повторно выставить его нельзя, система показывает номер действующего счёта.
3. Когда оплата подтверждена. Тогда подписка продлена на 30 дней и центр исчезает из списка.

## PLT-CTR. Реестр центров и подключение {#PLT-CTR}

### PLT-CTR-010 Реестр центров {#PLT-CTR-010}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Все центры

Реестр всех учебных центров. Плитки: всего центров, активные подписки, новые за месяц, центры в овердрафте. Колонки: название (город, владелец, последний вход), тариф и филиалы, сотрудники и лимит, SMS-баланс, баланс на платформе (и доступно к расходу), овердрафт (лимит и использование), статус. Фильтры: поиск по названию, городу и владельцу; тариф; город; чипы «В овердрафте», «Истекают», «Риск оттока», «Заблокированы». В строке главное действие «Войти» (режим поддержки, [`PLT-CTR-050`](#PLT-CTR-050)) и меню «Действия»: баланс и овердрафт, пополнить баланс, начислить пакет SMS, сменить тариф, настройка модулей. Ожидающий оплаты счёт на смену тарифа и срок отсрочки видны в строке.

**Правила:** [`BR-005`](#BR-005), [`BR-012`](#BR-012), [`BR-019`](#BR-019).

**Критерии приёмки**

1. Когда открыт реестр. Тогда показано 10 центров на странице, внизу «Показано 1–10 из N» и всего на платформе.
2. Когда выбран фильтр или поиск. Тогда выдача возвращается на первую страницу, рядом появляется «Сбросить фильтры».
3. Дано: у центра отрицательный баланс. Тогда он помечен «В овердрафте» и входит в одноимённый фильтр.

### PLT-CTR-020 Подключение центра {#PLT-CTR-020}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Подключить центр

Пошаговая регистрация нового центра: данные организации; владелец и Global ID (поиск по номеру телефона); стартовый бесплатный тариф «Старт» (до 5 сотрудников, 2 ГБ, 2 филиала). Название центра уникально; ошибки сервера показываются под полями соответствующего шага.

При подключении платформа выдаёт администратору центра данные для входа: логин (номер телефона владельца; если номер уже занят другим центром, логин формируется по номеру центра) и случайный пароль из 10 символов без похожих знаков. Пароль показывается SuperAdmin один раз на последнем экране мастера с кнопкой копирования и нигде не хранится в открытом виде; он временный, при первом входе его нужно сменить. Выдача данных записывается в журнал аудита без пароля ([`PLT-AUD-010`](#PLT-AUD-010), [`BR-025`](#BR-025)). Основной вход владельца — по номеру телефона и SMS-коду ([`SYS-ACC-030`](#SYS-ACC-030)); логин и пароль остаются запасным вариантом.

**Критерии приёмки**

1. Дано: название уже занято. Когда SuperAdmin вводит его. Тогда мастер сообщает о занятости до создания.
2. Когда мастер завершён. Тогда центр появляется в реестре на тарифе «Старт» со статусом «Активен».
3. Когда мастер завершён. Тогда показаны логин и пароль администратора, у каждого есть кнопка «Копировать», пароль после закрытия экрана повторно увидеть нельзя.
4. Когда у двух центров один и тот же владелец. Тогда у второго центра другой логин и другой пароль.
5. Когда данные для входа выданы. Тогда в журнале аудита есть запись без пароля.

### PLT-CTR-060 Состав центра {#PLT-CTR-060}

**Роль:** SuperAdmin · **Согласование:** допущение ([`Q-022`](#Q-022)) · **Реализация:** прототип · **Экран:** Все центры → панель центра → Состав центра

Из панели центра в реестре SuperAdmin открывает состав центра только для просмотра: три раздела — группы (название, курс, филиал, преподаватель, дни и время занятий, заполненность, статус), ученики (имя, группа, филиал, статус) и сотрудники (имя, роль, дата приёма). В каждом разделе поиск по названию или имени и постраничный вывод; в заголовках разделов показано число записей. Телефоны, касса, платежи и зарплаты не показываются ([`BR-022`](#BR-022)); менять состав из кабинета платформы нельзя — для этого есть режим поддержки ([`PLT-CTR-050`](#PLT-CTR-050)).

**Критерии приёмки**

1. Дано: у центра 48 учеников, 4 группы. Когда SuperAdmin открывает состав центра. Тогда в разделах показаны «Группы · 4» и «Ученики · 48».
2. Когда открыт раздел «Ученики». Тогда в списке нет телефонов.
3. Когда SuperAdmin ищет по части имени. Тогда в списке только подходящие записи.

### PLT-CTR-030 Статусы центра {#PLT-CTR-030}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** частично · **Экран:** Все центры

Статусы центра: «Активен» и «Заблокирован». Для заблокированного центра недоступны вход в режим поддержки, смена тарифа, покупки, заявки и начисления ([`BR-012`](#BR-012)). В прототипе статус отображается и учитывается в правилах; действие «Заблокировать / разблокировать» не реализовано.

### PLT-CTR-040 Управление модулями и лимитами (Feature Flags) {#PLT-CTR-040}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** частично · **Экран:** Все центры → Настройка модулей

Выдвижная панель быстрой настройки центра: включение и выключение модулей (зарплаты, инвентарь, CRM-воронка, гео-чек-ин), лимиты (сотрудники, хранилище, филиалы). В панели показан текущий тариф и кнопка «Сменить тариф» ([`PLT-TRF-020`](#PLT-TRF-020)). В прототипе переключатели и ползунки демонстрационные: значения в данных не сохраняются.

### PLT-CTR-050 Режим поддержки (Impersonation) {#PLT-CTR-050}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Все центры → Войти

Безопасный вход SuperAdmin и сотрудника поддержки в кабинет центра для диагностики без запроса пароля. Режим только для чтения: изменять данные и видеть финансы центра (платежи, кассу, расходы, зарплаты) нельзя ([`BR-022`](#BR-022)). Вход требует причины, сессия ограничена по времени (по умолчанию 30 минут) и отмечена заметным баннером «Режим поддержки». Вход записывается в журнал аудита платформы ([`PLT-AUD-010`](#PLT-AUD-010)), а центр видит запись о входе в своём журнале. Кабинет центра открывается на профиле именно того центра, из строки которого нажато «Войти»; внутри кабинета доступны все его разделы, баннер сохраняется при переходах между ними. Выход из режима — кнопкой «Выйти в кабинет платформы» в баннере: SuperAdmin возвращается в реестр центров.

**Критерии приёмки**

1. Когда SuperAdmin нажимает «Войти» у центра «Sitora Kids». Тогда открывается профиль центра «Sitora Kids» с баннером «Режим поддержки», в журнале появляется запись «Вход в режим поддержки».
2. Когда SuperAdmin переходит между разделами кабинета центра. Тогда баннер сохраняется, а раздел относится к тому же центру.
3. Когда SuperAdmin нажимает «Выйти в кабинет платформы». Тогда открывается реестр центров платформы, баннера нет.
4. Когда причина входа не указана. Тогда вход отклонён.
5. Когда истёк таймер сессии. Тогда режим поддержки завершён.
6. Когда в режиме поддержки открыт раздел с финансами или нажато действие, меняющее данные. Тогда раздел и действие недоступны (целевое поведение; в прототипе не реализовано).

## PLT-TRF. Тарифы и лимиты {#PLT-TRF}

### PLT-TRF-010 Каталог тарифов {#PLT-TRF-010}

**Роль:** SuperAdmin · **Согласование:** согласовано (цены — допущение, [`Q-001`](#Q-001)) · **Реализация:** прототип · **Экран:** Тарифы и лимиты

Карточки тарифов с ценой и лимитами (сотрудники, хранилище, филиалы), метки «Популярный» и «Premium», матрица доступных функций (Feature Flags) по тарифам. Создание, редактирование и перенос в архив.

Правила редактирования:

- название уникально; цена — целое число сомони; бесплатный тариф остаётся бесплатным, платный стоит не менее 1;
- лимиты — целые числа от 1 и не ниже текущего использования любого активного центра на этом тарифе (система называет центр, который мешает);
- в архив нельзя перенести бесплатный тариф (он назначается новым центрам) и тариф, на котором есть центры.

**Критерии приёмки**

1. Дано: у центра на тарифе 7 сотрудников. Когда SuperAdmin ставит лимит 5. Тогда система отказывает и называет центр и текущее использование.
2. Когда SuperAdmin переносит в архив тариф с центрами. Тогда система отказывает, тариф остаётся активным.
3. Когда создан тариф. Тогда он появляется в карточках и в матрице функций.

### PLT-TRF-020 Смена тарифа центра {#PLT-TRF-020}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Все центры → Сменить тариф; Центры у лимита; Настройка модулей

Диалог показывает все тарифы, кроме текущего, с ценой, разницей, нагрузкой центра после перехода и признаком «хватает баланса». Тариф, в который центр не вмещается по лимитам, недоступен, с перечнем превышений. Обязательна причина. Способы оплаты:

1. выставить счёт (оплатит владелец онлайн либо SuperAdmin подтвердит оплату по документу);
2. списать с баланса на платформе, если хватает «баланса и овердрафта» (тариф меняется сразу);
3. отсрочка оплаты по решению SuperAdmin ([`PLT-TRF-030`](#PLT-TRF-030)).

Переход на бесплатный тариф выполняется сразу. Платный тариф действует 30 дней с момента оплаты; при понижении новый период оплачивается по цене нового тарифа. Предложение центру при смене снимается.

**Правила:** [`BR-001`](#BR-001), [`BR-007`](#BR-007), [`BR-008`](#BR-008), [`BR-009`](#BR-009), [`BR-011`](#BR-011), [`BR-012`](#BR-012).

**Критерии приёмки**

1. Дано: центр не вмещается в тариф «Старт». Тогда тариф помечен «Не вмещает» и выбрать его нельзя.
2. Когда выбран способ «Выставить счёт». Тогда создан счёт со статусом «Ожидает оплаты», тариф центра не изменился.
3. Когда счёт оплачен любым способом. Тогда тариф изменён, счёт «Оплачен», в журнале видны выставление, оплата и смена «Было → Стало».
4. Дано: у центра уже есть открытый счёт на смену тарифа. Тогда новый выставить нельзя, показан номер действующего.
5. Когда выбрано списание с баланса и средств не хватает. Тогда вариант недоступен, указано, сколько не хватает.

### PLT-TRF-030 Отсрочка оплаты при смене тарифа {#PLT-TRF-030}

**Роль:** SuperAdmin · **Согласование:** допущение ([`Q-004`](#Q-004)) · **Реализация:** прототип · **Экран:** Сменить тариф → «Сменить сейчас, оплата позже»

Исключение для случая, когда центру нужен тариф сразу, а оплата ещё не поступила или не хватает баланса. Нужны причина и явное подтверждение, что решение принимается до поступления денег. Тариф меняется немедленно, счёт остаётся открытым в течение 7 дней; в реестрах центров и счетов виден признак «тариф уже изменён / оплата ожидается до …». Оплата отсроченного счёта любым способом закрывает его, тариф сохраняется. Отмена неоплаченного отсроченного счёта возвращает прежний тариф и срок подписки, если центр вмещается в прежний тариф; иначе откат запрещён с указанием превышения. Все шаги пишутся в журнал аудита.

**Правила:** [`BR-001`](#BR-001), [`BR-010`](#BR-010), [`BR-011`](#BR-011).

**Критерии приёмки**

1. Когда выбрана отсрочка без подтверждения. Тогда система отказывает.
2. Когда отсрочка оформлена. Тогда тариф изменён, счёт «Ожидает оплаты» с пометкой «тариф уже изменён».
3. Когда отсроченный счёт отменён и центр вмещается в прежний тариф. Тогда прежний тариф и срок подписки восстановлены.

### PLT-TRF-040 Центры у лимита {#PLT-TRF-040}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Центры у лимита

Рабочий список центров, у которых использование любого лимита (сотрудники, хранилище, филиалы) достигло порога (по умолчанию 80%; переключатель 70, 80, 90, 100%). Для каждого: нагрузка по трём лимитам, рекомендуемый тариф (самый дешёвый из более дорогих, где нагрузка ниже порога), цена и разница, статусы «Предложено» и «Ожидает оплаты». Поиск; фильтры по метрике, тарифу и статусу; сортировка по загрузке, потенциалу допродаж и названию. Предложение отправляется одному или нескольким центрам; перевод центра выполняется через [`PLT-TRF-020`](#PLT-TRF-020).

**Правила:** [`BR-021`](#BR-021).

**Критерии приёмки**

1. Когда выбран порог 90%. Тогда в списке только центры с нагрузкой не ниже 90% по выбранной метрике.
2. Когда выбраны несколько центров и отправлено предложение. Тогда центры с подходящим тарифом получают статус «Предложено», а заблокированные, без более дорогого тарифа и с открытым счётом на смену тарифа пропускаются; система сообщает, сколько отправлено и сколько пропущено.
3. Когда центр переведён на тариф выше. Тогда он исчезает из списка, если нагрузка стала ниже порога.

## PLT-BAL. Баланс на платформе и овердрафт {#PLT-BAL}

Взаиморасчёты центра с платформой. Это не касса и не выручка центра ([`BR-022`](#BR-022)).

### PLT-BAL-010 Баланс на платформе {#PLT-BAL-010}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Все центры (колонка «Баланс на платформе»), панель «Финансы центра»

У каждого центра есть баланс на платформе — предоплаченные средства, с которых оплачиваются счета платформы (подписка, смена тарифа, методики, SMS-пакеты). Показывается баланс и «доступно к расходу» (баланс плюс лимит овердрафта). Панель «Финансы центра» показывает журнал операций и открытые счета центра.

**Правила:** [`BR-005`](#BR-005), [`BR-019`](#BR-019), [`BR-022`](#BR-022).

**Критерии приёмки**

1. Дано: баланс 2 400 сомони и лимит овердрафта 2 000. Тогда в реестре показан баланс 2 400 и «доступно 4 400».
2. Когда открыта панель «Финансы центра». Тогда видны журнал операций и открытые счета центра.


### PLT-BAL-020 Овердрафт центра {#PLT-BAL-020}

**Роль:** SuperAdmin · **Согласование:** допущение ([`Q-002`](#Q-002)) · **Реализация:** прототип · **Экран:** Все центры

Лимит, на который баланс может уйти в минус. Счёт оплачивается в пределах «баланс + лимит овердрафта»; использованная часть — долг центра перед платформой, который гасится пополнением. Для нового центра берётся значение по умолчанию для тарифа; для тарифа «Старт» овердрафт может быть не предусмотрен. Центр с отрицательным балансом помечен «В овердрафте»; при использовании 80% лимита и более — «Овердрафт почти исчерпан».

**Правила:** [`BR-005`](#BR-005), [`BR-006`](#BR-006).

**Критерии приёмки**

1. Дано: баланс -150 при лимите 300. Тогда центр помечен «В овердрафте», доступно к расходу 150.
2. Когда использовано 80% и более. Тогда показана метка «Овердрафт почти исчерпан».

### PLT-BAL-030 Пополнение баланса вручную {#PLT-BAL-030}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Все центры → Пополнить баланс

Деньги уже поступили вне системы (расчётный счёт, касса, перевод на карту). SuperAdmin указывает способ, номер документа (банковская выписка, приходный кассовый ордер, чек перевода), дату и сумму поступления и явно подтверждает получение. Предпросмотр показывает баланс до и после. Операция необратима, записывается в журнал баланса и журнал аудита.

**Правила:** [`BR-002`](#BR-002), [`BR-010`](#BR-010).

**Критерии приёмки**

1. Когда дата в будущем, нет документа, сумма не положительная или нет подтверждения. Тогда пополнение отклонено, ошибки показаны под полями.
2. Когда пополнение выполнено. Тогда баланс вырос на сумму, в журнале баланса и аудита появились записи.

### PLT-BAL-040 Оплата счёта с баланса {#PLT-BAL-040}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Реестр счетов, карточка счёта

Счёт можно оплатить списанием с баланса, если хватает «баланса и овердрафта» и центр не заблокирован. Уход баланса в минус фиксируется как использование овердрафта. Операция попадает в журнал баланса.

**Правила:** [`BR-005`](#BR-005), [`BR-012`](#BR-012).

**Критерии приёмки**

1. Дано: доступно меньше суммы счёта. Когда SuperAdmin пытается списать. Тогда система отказывает с указанием нехватки, счёт остаётся открытым.
2. Когда списание выполнено. Тогда счёт «Оплачен» (канал «с баланса»), создана запись списания.

### PLT-BAL-050 Изменение лимита овердрафта {#PLT-BAL-050}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Панель «Финансы центра» → Изменить лимит

Выполняется с обязательной причиной. Лимит нельзя установить ниже уже использованной суммы. Изменение пишется в журнал аудита («Было → Стало»).

**Правила:** [`BR-006`](#BR-006), [`BR-010`](#BR-010), [`BR-011`](#BR-011).

**Критерии приёмки**

1. Когда лимит ниже использованной суммы овердрафта. Тогда изменение отклонено с пояснением.
2. Когда причина короче 5 символов или лимит не изменился. Тогда изменение отклонено.
3. Когда изменение выполнено. Тогда в журнале аудита запись «Было → Стало» с причиной.

### PLT-BAL-060 Журнал операций по балансу {#PLT-BAL-060}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Панель «Финансы центра»

Для каждого центра: дата, операция (пополнение или списание), сумма, баланс после операции, основание (способ и документ либо назначение счёта). Записи неизменяемы ([`BR-010`](#BR-010)).

**Критерии приёмки**

1. Когда выполнено пополнение или списание. Тогда в журнале появилась запись с суммой, балансом после операции и основанием.
2. Записи показываются от новых к старым и не редактируются.

## PLT-BIL. Счета и оплата (B2B-биллинг) {#PLT-BIL}

### PLT-BIL-010 Счета {#PLT-BIL-010}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** B2B-биллинг и счета

Виды счетов: продление подписки, смена тарифа, методика (курс), SMS-пакет. Счёт содержит номер, центр, назначение, сумму, дату выставления, срок оплаты (по умолчанию 7 дней) и историю событий: выставлен → напоминание → оплата → применено.

**Критерии приёмки**

1. Когда выставлен счёт. Тогда срок оплаты равен 7 дням от даты выставления, в истории есть событие «Счёт выставлен».
2. Когда счёт оплачен. Тогда в истории добавлены события оплаты и применения.


### PLT-BIL-020 Статусы счёта {#PLT-BIL-020}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип

Статусы: «Ожидает оплаты», «Оплачен», «Отменён». «Просрочен» — не статус, а признак открытого счёта с истёкшим сроком оплаты ([`BR-003`](#BR-003)). Отменить можно только неоплаченный счёт с причиной ([`BR-004`](#BR-004)). Допустимые переходы — в разделе «Статусы и переходы».

**Критерии приёмки**

1. Дано: срок оплаты истёк. Тогда счёт остаётся «Ожидает оплаты» с признаком «Просрочен».
2. Когда отмена без причины или счёт уже оплачен. Тогда отмена отклонена.

### PLT-BIL-030 Способы оплаты {#PLT-BIL-030}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип

Результат оплаты всегда один: тариф меняется, подписка продлевается, курс передаётся. Способы:

1. **онлайн** — владелец центра платит по ссылке, платёжный шлюз сообщает платформе, счёт закрывается автоматически без участия SuperAdmin ([`INT-PAY-010`](#INT-PAY-010));
2. **с баланса на платформе** — [`PLT-BAL-040`](#PLT-BAL-040);
3. **вручную** — SuperAdmin подтверждает оплату по документу ([`PLT-BIL-040`](#PLT-BIL-040)).

**Критерии приёмки**

1. Когда счёт оплачен онлайн. Тогда канал «онлайн», оплату подтвердила система.
2. Когда счёт оплачен с баланса. Тогда канал «с баланса на платформе».
3. Когда оплата подтверждена вручную. Тогда в счёте указан сотрудник, подтвердивший оплату.

### PLT-BIL-040 Ручное подтверждение оплаты {#PLT-BIL-040}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Реестр счетов → Подтвердить оплату

Только когда деньги уже поступили. Основание: способ (безнал — банковская выписка и номер платёжного поручения; наличные — кассовый документ и номер ордера; перевод на карту — чек и ID перевода или последние 4 цифры карты), дата поступления (не в будущем и не раньше даты выставления счёта), сумма (равна сумме счёта; частичные оплаты не поддерживаются), явное подтверждение. Действие необратимо и пишется в журнал аудита.

**Правила:** [`BR-002`](#BR-002), [`BR-010`](#BR-010).

**Критерии приёмки**

1. Когда сумма не совпадает со счётом. Тогда подтверждение отклонено с пояснением.
2. Когда основание полное. Тогда счёт «Оплачен» (канал по способу), указано, кто подтвердил, и применено действие счёта (тариф, продление или передача курса).
3. Когда счёт уже оплачен. Тогда подтвердить повторно нельзя.

### PLT-BIL-050 Реестр счетов {#PLT-BIL-050}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** B2B-биллинг и счета

Вкладки по статусам со счётчиками (считаются внутри выбранного типа и поиска), фильтр по типу, поиск по счёту, центру, назначению и документу, чипы применённых фильтров и «Сбросить все фильтры», пагинация, массовая отправка напоминаний (выбираются только счета, ожидающие оплаты), карточка счёта по клику на строку (плательщик, срок, баланс на платформе и хватает ли его, способ оплаты, документ и основание, кто подтвердил, история событий).

В строке главное действие «Подтвердить оплату» (для открытых счетов) и меню «Действия»: подробности счёта; списание с баланса (если хватает); напоминание; копирование ссылки на оплату; отмена счёта.

**Критерии приёмки**

1. Когда выбрана вкладка «Просрочены». Тогда показаны открытые счета с истёкшим сроком, счётчик вкладки равен числу строк.
2. Когда отмечена галочка у строки. Тогда выбирается только эта строка; галочка в шапке выбирает все ожидающие оплаты счета страницы.
3. Когда счёт отменён с причиной. Тогда он получает статус «Отменён», кнопки оплаты исчезают.

### PLT-BIL-060 Напоминания об оплате {#PLT-BIL-060}

**Роль:** SuperAdmin · **Согласование:** допущение ([`Q-012`](#Q-012)) · **Реализация:** частично

Напоминание владельцу центра по одному или нескольким счетам фиксируется в истории счёта. Реальная отправка уведомлений в прототипе не выполняется.

### PLT-BIL-070 Продление подписки {#PLT-BIL-070}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Истекающие подписки

Подписка продлевается на 30 дней только после оплаты счёта на продление ([`BR-009`](#BR-009)). «Продлить без оплаты» не существует. После окончания периода действуют льготный срок, режим «только чтение» и блокировка по [`BR-034`](#BR-034).

**Критерии приёмки**

1. Когда счёт на продление оплачен. Тогда подписка продлена на 30 дней.
2. Когда счёт не оплачен. Тогда срок подписки не меняется: продления без оплаты нет.

## PLT-SMS. Биллинг SMS-пакетов {#PLT-SMS}

### PLT-SMS-010 Каталог пакетов {#PLT-SMS-010}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Биллинг SMS

Три пакета (500, 1 000 и 5 000 SMS) с ценой и описанием, число продаж и центров. SuperAdmin меняет цену и описание с обязательной причиной; новая цена действует на новые продажи ([`BR-020`](#BR-020)). Изменение пишется в журнал аудита.

**Критерии приёмки**

1. Когда цена меняется. Тогда прежние продажи сохраняют старую цену.
2. Когда цена не изменилась или нет причины. Тогда сохранение отклонено.

### PLT-SMS-020 Начисление пакета центру {#PLT-SMS-020}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Биллинг SMS → Начислить пакет SMS

SuperAdmin выбирает центр, пакет и способ: 1) списание с баланса на платформе (в пределах «баланс + овердрафт», запись в журнал баланса); 2) деньги получены вне системы (способ, документ, дата, сумма равна цене пакета, подтверждение); 3) бесплатно (бонус или компенсация) с обязательной причиной. Начисление пишется в журнал аудита. Заблокированному центру начислить нельзя.

**Правила:** [`BR-002`](#BR-002), [`BR-005`](#BR-005), [`BR-011`](#BR-011), [`BR-012`](#BR-012).

**Критерии приёмки**

1. Дано: не хватает баланса. Тогда способ «с баланса» отклонён.
2. Когда выбран бонус без причины. Тогда начисление отклонено.
3. Когда начисление выполнено. Тогда SMS-баланс центра вырос на размер пакета.

### PLT-SMS-030 История продаж и балансы центров {#PLT-SMS-030}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Биллинг SMS

Таблица продаж: центр, пакет, дата, остаток SMS с индикатором, сумма, статус («Оплачено» или «Бонус»). Остаток ниже 10% пакета помечен «Заканчиваются». Фильтры: поиск по центру или номеру, пакет, статус, заканчиваются; пагинация. Суммарный SMS-баланс центра показан в реестре центров.

**Критерии приёмки**

1. Дано: остаток не больше 10% пакета. Тогда в строке метка «Заканчиваются», продажа входит в фильтр «Заканчиваются».
2. Когда введено название центра в поиск. Тогда остаются продажи этого центра.


### PLT-SMS-040 Автопереход на Push и Telegram {#PLT-SMS-040}

**Роль:** система · **Согласование:** согласовано · **Реализация:** план

При нулевом остатке SMS уведомления центра автоматически отправляются бесплатными каналами Push и Telegram ([`INT-NTF-010`](#INT-NTF-010)).

## PLT-MKT. Магазин методик (B2B) {#PLT-MKT}

Платформа продаёт учебным центрам готовые программы обучения. Модуль описывает обе стороны: управление курсами (SuperAdmin) и получение курсов (центр).

### PLT-MKT-010 Каталог курсов {#PLT-MKT-010}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Магазин методик

Карточка курса: обложка, направление, название, число уроков и тестов, статус («Опубликован» или «Черновик»), цена, число купивших центров. Фильтры по направлению и статусу, поиск по названию, пагинация (9 карточек). Клик по карточке открывает страницу курса. Вкладка «Заявки центров» показывает входящие заявки ([`PLT-MKT-070`](#PLT-MKT-070)). Собственные курсы центров в каталог не попадают ([`BR-016`](#BR-016)).

**Критерии приёмки**

1. Когда выбрано направление или статус. Тогда показаны только соответствующие курсы, выдача возвращается на первую страницу.
2. Дано: у центра есть собственный курс. Тогда в каталоге платформы его нет.

### PLT-MKT-020 Страница курса {#PLT-MKT-020}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Магазин методик → курс

Единое место управления курсом. Вкладки: «Обзор» (описание, состав, выручка, готовность к публикации), «Программа и материалы» ([`PLT-MKT-030`](#PLT-MKT-030)), «Покупатели» ([`PLT-MKT-110`](#PLT-MKT-110)), «Заявки» (заявки центров на этот курс). В шапке: опубликовать или снять с публикации, цена, передача центру, изменение данных курса (название уникально, направление, описание до 600 символов).

**Критерии приёмки**

1. Когда SuperAdmin нажимает карточку курса. Тогда открывается страница курса с вкладками «Обзор», «Программа и материалы», «Покупатели», «Заявки».
2. Когда описание длиннее 600 символов или название пустое. Тогда сохранение отклонено, ошибка под полем.


### PLT-MKT-030 Программа и материалы курса {#PLT-MKT-030}

**Роль:** SuperAdmin; Admin центра (для собственного курса) · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Страница курса → Программа и материалы

Программа строится как «модуль → урок → материал». Материалы пяти типов: методический план, видео, документ PDF, презентация, тест с автопроверкой (указывается число вопросов). Добавление, переименование и удаление модулей, уроков и материалов; удаление требует подтверждения (удаление модуля удаляет его уроки и материалы). Число уроков и тестов в карточке считается по программе автоматически. Изменения программы платформенного курса пишутся в журнал аудита. Загрузка файлов в прототипе имитируется: хранятся тип, название и размер.

**Критерии приёмки**

1. Когда добавлен урок с тестом. Тогда счётчики уроков и тестов курса выросли на единицу.
2. Когда удалён модуль. Тогда его уроки и материалы исчезли, счётчики уменьшились.
3. Когда название материала пустое. Тогда сервер возвращает ошибку, диалог остаётся открытым, ошибка показана под полем.

### PLT-MKT-040 Создание и публикация курса {#PLT-MKT-040}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Магазин методик → Создать курс

Курс создаётся черновиком (название уникально, направление, цена) и наполняется на странице курса. Публикация возможна только при заданной цене и хотя бы одном уроке ([`BR-013`](#BR-013)); решение пишется в журнал аудита.

**Критерии приёмки**

1. Когда в курсе нет уроков или цена не задана. Тогда публикация отклонена с перечнем недостающего.
2. Когда условия выполнены. Тогда курс опубликован и виден центрам в каталоге.

### PLT-MKT-050 Цена и снятие с публикации {#PLT-MKT-050}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип

Изменение цены и снятие курса с публикации выполняются с обязательной причиной ([`BR-011`](#BR-011)). Центры, уже получившие курс, сохраняют доступ; цена прошлых покупок не меняется.

**Критерии приёмки**

1. Когда цена совпадает с текущей или не указана причина. Тогда изменение отклонено.
2. Когда курс снят с публикации. Тогда он исчез из каталога центров, но остался доступен купившим.

### PLT-MKT-060 Заявка центра на курс (сторона центра) {#PLT-MKT-060}

**Роль:** Admin центра · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Кабинет → Материалы и тесты → Каталог, Заявки

Центр видит опубликованные курсы платформы с ценой и описанием и подаёт заявку с необязательным комментарием. Статусы заявки: «Новая» (ждёт счёта), «Счёт выставлен» (ожидает оплаты), «Выполнена» (курс получен), «Отклонена» (с причиной). Нельзя подать заявку на курс, которым центр уже владеет, и дублировать открытую заявку; заблокированный центр заявки подавать не может. Центр может отменить заявку, пока по ней нет счёта.

**Правила:** [`BR-012`](#BR-012), [`BR-014`](#BR-014).

**Критерии приёмки**

1. Когда центр подаёт заявку. Тогда она получает статус «Новая» и видна платформе и центру.
2. Когда по заявке выставлен счёт. Тогда отменить её нельзя, в кабинете появляется оплата онлайн.
3. Когда заявка отклонена. Тогда центр видит причину отказа.

### PLT-MKT-070 Обработка заявки {#PLT-MKT-070}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Магазин методик → Заявки центров

Заявки отображаются с фильтрами по статусу и пагинацией. SuperAdmin выбирает: выставить счёт на курс; списать стоимость с баланса на платформе (в пределах «баланс + овердрафт», доступ сразу); передать бесплатно по обязательной причине; отклонить с причиной, которую увидит центр. Если выставленный счёт отменён, заявка возвращается в статус «Новая».

**Критерии приёмки**

1. Когда выставлен счёт. Тогда статус заявки «Счёт выставлен», обработать её повторно нельзя.
2. Когда счёт отменён. Тогда заявка снова «Новая», доступа у центра нет.
3. Когда заявка отклоняется без причины. Тогда действие отклонено.

### PLT-MKT-080 Передача курса центру {#PLT-MKT-080}

**Роль:** SuperAdmin, система · **Согласование:** согласовано · **Реализация:** прототип

Курс передаётся только после оплаты. Онлайн-оплата (владелец центра платит по ссылке, шлюз сообщает платформе) передаёт курс автоматически без участия SuperAdmin. Если деньги поступили вне системы, SuperAdmin подтверждает оплату по документу ([`PLT-BIL-040`](#PLT-BIL-040)), и тем же действием курс передаётся центру. SuperAdmin также может передать курс без заявки: счётом, списанием с баланса или бесплатно по причине. Повторно передать курс нельзя, второй открытый счёт на тот же курс не выставляется. Покупка даёт текущую версию курса: число уроков и тестов фиксируется в момент передачи ([`BR-015`](#BR-015)).

**Правила:** [`BR-012`](#BR-012), [`BR-014`](#BR-014), [`BR-015`](#BR-015).

**Критерии приёмки**

1. Когда счёт на курс оплачен онлайн. Тогда у центра появляется курс, счёт «Оплачен», заявка «Выполнена».
2. Когда SuperAdmin подтверждает оплату по документу. Тогда курс передаётся тем же действием.
3. Когда курс опубликован и позже в нём добавлены уроки. Тогда у центра остаётся версия на дату получения.

### PLT-MKT-090 Кабинет центра: Материалы и тесты {#PLT-MKT-090}

**Роль:** Admin центра · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Кабинет → Материалы и тесты

Четыре вкладки: «Мои методики» (переданные курсы; клик открывает страницу курса только для просмотра программы и материалов), «Каталог», «Заявки» (статусы; оплата выставленного счёта онлайн) и «Мои курсы». Если в курсе стало больше уроков, центр видит пометку, что у него версия на дату получения. Отозванные курсы не показываются.

**Критерии приёмки**

1. Дано: у центра нет курсов. Тогда в «Моих методиках» показано «Методик пока нет».
2. Когда по заявке выставлен счёт. Тогда во вкладке «Заявки» доступна оплата онлайн, после оплаты курс появляется в «Моих методиках».

### PLT-MKT-100 Собственные курсы центра {#PLT-MKT-100}

**Роль:** Admin центра, Преподаватель · **Согласование:** допущение ([`Q-008`](#Q-008); видимость материалов — решение: преподаватели привязанных групп и их ученики) · **Реализация:** прототип · **Экран:** Кабинет → Материалы и тесты → Мои курсы

Центр сам создаёт и ведёт курсы: название, направление, описание, модули, уроки и материалы (те же типы, что у курсов платформы). Курс виден только этому центру: платформа его не продаёт, он не попадает в магазин, заявки и аудит платформы; другие центры и SuperAdmin им не управляют.

**Правила:** [`BR-016`](#BR-016).

**Критерии приёмки**

1. Когда другой центр или SuperAdmin пытается изменить такой курс. Тогда доступ запрещён.
2. Когда центр открывает купленный курс. Тогда он может только просматривать: правки запрещены.

### PLT-MKT-110 Покупатели и отзыв доступа {#PLT-MKT-110}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Страница курса → Покупатели

Список центров с доступом: дата, основание (счёт или бонус), версия. Отзыв доступа с обязательной причиной, например при возврате денег ([`Q-011`](#Q-011)). Снятие курса с публикации доступ у получивших центров не отбирает. Передача, заявки, отклонения и отзыв пишутся в журнал аудита.

**Критерии приёмки**

1. Когда доступ отозван. Тогда курс исчезает из «Моих методик» центра, в истории покупателей остаётся запись об отзыве, центр может получить курс снова.

## PLT-MOD. Модерация каталога {#PLT-MOD}

Модерация защищает родителей от неверных адресов, фиктивных центров и пустых описаний перед публикацией филиала в едином каталоге на карте ([`LRN-CAT-010`](#LRN-CAT-010)).

### PLT-MOD-010 Очередь модерации {#PLT-MOD-010}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Модерация каталога

Список заявок на публикацию: центр и филиал, адрес и город, направления, статус («На проверке», «Опубликован», «Возвращён», «Отклонён»), время подачи, метки «GPS расходится» и «Нет TJ». Вкладки «Ожидают» и «Обработаны». Заявка показывает, кто и когда её отправил.

**Критерии приёмки**

1. Когда открыта очередь. Тогда видны заявки «На проверке», остальные — во вкладке «Обработаны».
2. Дано: расхождение точки с адресом больше 150 м. Тогда на заявке метка «GPS расходится».


### PLT-MOD-020 Проверка заявки {#PLT-MOD-020}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Модерация каталога → предпросмотр

Предпросмотр карточки: карта с точкой, указанной центром, и точкой по геокодеру (расхождение более 150 м помечается), координаты (копируются, редактируются), проверки: адрес, описания RU (обязательно) и TJ (обязательно), EN (желательно), телефон. Модератор подтверждает, что пин стоит на нужном здании.

**Правила:** [`BR-017`](#BR-017).

**Критерии приёмки**

1. Когда координаты изменены вручную. Тогда подтверждение сбрасывается, его нужно поставить заново.
2. Когда расхождение больше 150 м. Тогда в проверке адреса показана величина расхождения.

### PLT-MOD-030 Решения модерации {#PLT-MOD-030}

**Роль:** SuperAdmin · **Согласование:** согласовано · **Реализация:** прототип

Решения: «Одобрить и опубликовать» (доступно, когда подтверждены координаты и заполнены описания RU и TJ), «Вернуть на доработку» и «Отклонить» (для двух последних нужна причина). Обработанную заявку можно вернуть в очередь. Все решения пишутся в журнал аудита.

**Критерии приёмки**

1. Дано: нет описания TJ или не подтверждены координаты. Тогда кнопка публикации недоступна, причина показана.
2. Когда выбрано «Вернуть» или «Отклонить» без причины. Тогда действие отклонено.
3. Когда заявка опубликована. Тогда счётчик очереди уменьшился.

### PLT-MOD-040 Заявка на публикацию филиала (сторона центра) {#PLT-MOD-040}

**Роль:** Admin центра · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Кабинет → Филиалы и каталог

Администратор центра заполняет карточку филиала: название, город, район, адрес, телефон, точка на карте (кнопка «Определить по адресу» вызывает геокодер, [`INT-GEO-010`](#INT-GEO-010)), описания RU (обязательно), TJ и EN — и отправляет на публикацию. Число заявок ограничено лимитом филиалов тарифа ([`BR-018`](#BR-018)). Пока заявка на модерации, изменить её нельзя.

**Критерии приёмки**

1. Когда достигнут лимит филиалов тарифа. Тогда новая заявка отклонена с пояснением.
2. Когда заявка отправлена. Тогда она появляется в очереди модерации ([`PLT-MOD-010`](#PLT-MOD-010)).

### PLT-MOD-050 Обратная связь центру {#PLT-MOD-050}

**Роль:** Admin центра · **Согласование:** согласовано · **Реализация:** прототип · **Экран:** Кабинет → Филиалы и каталог

Центр видит статус заявки: «На модерации», «Опубликован на карте», «Возвращён на доработку» (с комментарием модератора; можно исправить и отправить повторно) или «Отклонён».

**Критерии приёмки**

1. Когда заявка возвращена. Тогда центр видит комментарий модератора и может отправить исправленную заявку.
2. Когда заявка опубликована. Тогда центр видит статус «Опубликован на карте».

### PLT-AUD-020 Поиск и фильтры журнала {#PLT-AUD-020}

**Критерии приёмки**

# Часть B. Центр: расписание, ученики, финансы, зарплаты

Область описывает работу владельца, администратора и кассира центра внутри изолированного контура центра. Данные кассы, прайс-листов и зарплат хранятся только в контуре центра; SuperAdmin видит лишь технические метрики (число активных учеников, статус подписки) — [`BR-022`](#BR-022).

Финансовый модуль (`CTR-FIN`, `CTR-PAY`) переработан в версии 2.4; остальные модули перенесены из спецификации v1.2. Критерии приёмки добавляются при проработке каждого модуля; до этого требования имеют статус реализации «план». Исключения: раздел «Материалы и тесты» кабинета центра и подача заявок на публикацию филиалов уже описаны в части A ([`PLT-MKT-060`](#PLT-MKT-060)…[`PLT-MKT-100`](#PLT-MKT-100), [`PLT-MOD-040`](#PLT-MOD-040)).

## CTR-DSH. Дашборд центра {#CTR-DSH}

### CTR-DSH-010 Дашборд центра {#CTR-DSH-010}

**Роль:** Admin центра · **Согласование:** допущение ([`Q-019`](#Q-019)) · **Реализация:** прототип · **Экран:** Кабинет центра → Дашборд

Сводка по центру на одном экране: всего учеников (и сколько из них заблокировано), число преподавателей, активные группы (из всех), филиалы (из них действующие). Ниже — посещаемость по дням недели, три ближайших занятия (время, группа, преподаватель и метка «через 30 мин», «сегодня, 18:00», «завтра, 10:00» или день недели), три группы с самой низкой заполненностью со ссылкой на страницу группы и список филиалов со статусом (активен, на модерации, возвращён, отклонён).

Группа считается малозаполненной, когда занято меньше половины мест (определяет платформа). Посещаемость по дням недели в прототипе демонстрационная; оплаты учеников на дашборд не выносятся ([`BR-022`](#BR-022)).

**Критерии приёмки**

1. Дано: центр с 428 учениками и 19 заблокированными. Когда открыт дашборд. Тогда показано «428» и «заблокировано: 19».
2. Дано: в группе занято меньше половины мест. Тогда она есть в блоке «Группы с низкой заполненностью».
3. Когда у центра есть активные группы с расписанием. Тогда показаны три ближайших занятия по порядку времени.
4. Когда у центра нет филиалов. Тогда показано пояснение со ссылкой на раздел филиалов.

## CTR-SET. Настройки центра {#CTR-SET}

### CTR-SET-010 Настройки центра {#CTR-SET-010}

**Роль:** Owner, Admin центра · **Согласование:** допущение ([`Q-029`](#Q-029), [`Q-030`](#Q-030)) · **Реализация:** план

Настройки делятся на общие для центра и на уровне филиала.

| Настройка | Кто меняет |
|:--|:--|
| Курс обмена баллов, срок жизни баллов | Владелец |
| Шкала оценок (5- или 100-балльная) | Владелец |
| Включённые способы приёма оплаты, ключи эквайринга | Владелец |
| Категории расходов, порог «крупного» сторно, срок подсветки несверенных платежей | Владелец |
| Правила скидок (виды, размеры, сроки) | Владелец |
| Автоправила баллов | Владелец |
| Цены групп, бюджет баллов групп, расписание филиала | Администратор своего филиала |

Каждое изменение записывается в журнал центра («было → стало», актор, время) и видно владельцу ([`BR-038`](#BR-038)). Ключи эквайринга хранятся зашифрованными и не показываются повторно ([`NFR-SEC-040`](#NFR-SEC-040)). Заблокированный центр не может менять настройки ([`BR-012`](#BR-012)).

**Критерии приёмки**

1. Когда администратор филиала пытается изменить курс обмена баллов. Тогда действие отклонено.
2. Когда владелец меняет срок жизни баллов. Тогда новое значение действует для новых лотов, прежние лоты сохраняют свой срок, в журнале есть запись «было → стало».
3. Когда администратор меняет цену группы своего филиала. Тогда изменение применяется к начислениям следующих месяцев, начисления закрытых месяцев не пересчитываются.
4. Когда администратор меняет цену группы другого филиала. Тогда группа не найдена.

## CTR-PRF. Профиль центра {#CTR-PRF}

Витрина центра для его администратора: кто центр, сколько у него учеников и сотрудников, на каком он тарифе и что с балансом на платформе. Профиль открывается в кабинете центра — отдельном рабочем месте, где собраны все разделы центра; кабинет платформы остаётся рабочим местом SuperAdmin.

### CTR-PRF-010 Профиль центра {#CTR-PRF-010}

**Роль:** Admin центра · **Согласование:** допущение ([`Q-016`](#Q-016)) · **Реализация:** прототип · **Экран:** Кабинет центра → Профиль центра

Профиль есть у каждого подключённого центра. Экран показывает:

- **Карточка:** логотип, баннер, название, направление, город, год основания, владелец, телефон, описание, статус центра («Активен», «Риск оттока», «Заблокирован»). У только что подключённого центра направление не указано, учеников нет, логотип стандартный.
- **Показатели:** число учеников; сотрудники и лимит сотрудников по тарифу; филиалы и лимит; остаток SMS.
- **Тариф и лимиты:** название и цена тарифа, срок подписки, использование трёх лимитов (сотрудники, хранилище, филиалы); метка «У лимита» определяется платформой по порогу [`BR-021`](#BR-021). Состав сотрудников по ролям.
- **Баланс на платформе:** баланс, лимит овердрафта, «доступно к расходу», статус («В порядке», «В овердрафте», «Овердрафт почти исчерпан») и последние операции ([`BR-005`](#BR-005), [`BR-019`](#BR-019)).
- **Курсы:** купленные методики и собственные курсы центра с обложками ([`BR-014`](#BR-014), [`BR-016`](#BR-016)).

В кабинете можно переключиться на другой центр: профиль, показатели и разделы относятся к выбранному центру. Центр видит только свои данные и только взаиморасчёты с платформой; касса, платежи учеников и зарплаты в профиль не попадают ([`BR-022`](#BR-022)). Профиль только отображает состояние: деньги и тариф меняет платформа.

**Правила:** [`BR-005`](#BR-005), [`BR-012`](#BR-012), [`BR-018`](#BR-018), [`BR-019`](#BR-019), [`BR-021`](#BR-021), [`BR-022`](#BR-022).

**Критерии приёмки**

1. Дано: центр «Sitora Kids» (тариф «Про», 9 филиалов из 10). Когда открыт профиль. Тогда у лимита филиалов показана метка «У лимита».
2. Дано: центр «Умед Плюс» с балансом −150 при лимите овердрафта 300. Тогда статус баланса «В овердрафте», доступно к расходу 150 сомони.
3. Дано: центр заблокирован. Тогда в карточке статус «Заблокирован» и сообщение о блокировке, метки «Активен» нет.
4. Дано: SuperAdmin пополнил баланс центра. Когда профиль открыт заново. Тогда баланс и последние операции содержат пополнение.
5. Когда выбран другой центр. Тогда профиль и все разделы кабинета относятся к выбранному центру.
6. Когда подключён новый центр. Тогда его профиль открывается, направление не указано, учеников и сотрудников нет.

## CTR-STF. Сотрудники центра {#CTR-STF}

### CTR-STF-010 Сотрудники центра {#CTR-STF-010}

**Роль:** Admin центра · **Согласование:** согласовано (решение по [`Q-017`](#Q-017), роли — [`BR-035`](#BR-035)) · **Реализация:** прототип · **Экран:** Кабинет центра → Сотрудники

Список активных сотрудников центра: ФИО, роль (владелец, администратор, кассир, преподаватель), филиал администратора и кассира, телефон, дата приёма. Фильтр по роли, поиск по имени и телефону, постраничный вывод. Над списком показано использование лимита сотрудников по тарифу («14 из 100»), метки «У лимита» и «Лимит исчерпан».

Администратор добавляет сотрудника (ФИО, роль, телефон) и придумывает ему логин для входа; пароль создаётся автоматически и показывается один раз с кнопкой копирования ([`BR-025`](#BR-025)). Уволить сотрудника можно только с обязательной причиной: доступ закрывается, логин освобождается. Число активных сотрудников не может превышать лимит тарифа ([`BR-023`](#BR-023)): при исчерпанном лимите кнопка добавления заменяется пояснением, как освободить место или сменить тариф. Добавление и увольнение записываются в журнал аудита платформы ([`PLT-AUD-010`](#PLT-AUD-010)). Состав сотрудников по ролям в профиле центра ([`CTR-PRF-010`](#CTR-PRF-010)) считается по этому списку.

Администратор и кассир привязываются строго к одному филиалу при добавлении ([`BR-038`](#BR-038)). Владелец у центра один ([`BR-039`](#BR-039)). Человек может совмещать роли ([`BR-040`](#BR-040)).

**Правила:** [`BR-011`](#BR-011), [`BR-012`](#BR-012), [`BR-023`](#BR-023), [`BR-025`](#BR-025), [`BR-035`](#BR-035), [`BR-038`](#BR-038), [`BR-039`](#BR-039), [`BR-040`](#BR-040).

**Критерии приёмки**

1. Дано: центр на тарифе «Старт» с 4 сотрудниками из 5. Когда добавлен ещё один. Тогда использовано 5 из 5, метка «Лимит исчерпан», добавить следующего нельзя.
2. Когда администратор пытается добавить сотрудника сверх лимита. Тогда добавление отклонено с пояснением про лимит тарифа.
3. Когда сотрудник уволен с причиной. Тогда место освобождается, сотрудник исчезает из списка и из показателей профиля, в журнале аудита есть запись.
4. Когда причина увольнения не указана или короче 5 символов. Тогда увольнение отклонено, сообщение показано под полем.
5. Дано: телефон уже есть у активного сотрудника этого центра. Когда добавляется сотрудник с тем же телефоном. Тогда добавление отклонено.
6. Дано: центр заблокирован. Тогда добавлять сотрудников нельзя ([`BR-012`](#BR-012)).
7. Когда сотрудник добавлен. Тогда показаны его логин и пароль, пароль после закрытия окна повторно увидеть нельзя и его нет в журнале аудита.
8. Когда выбранный логин уже занят или не соответствует формату. Тогда добавление отклонено, сообщение показано под полем логина.
9. Когда сотрудник уволен. Тогда его логин можно использовать повторно.

## CTR-STL. Взаиморасчёты с платформой {#CTR-STL}

### CTR-STL-010 Баланс и счета центра {#CTR-STL-010}

**Роль:** Admin центра · **Согласование:** допущение ([`Q-018`](#Q-018)) · **Реализация:** прототип · **Экран:** Кабинет центра → Баланс и счета

Раздел показывает то, что центр должен и имеет на платформе: баланс на платформе, доступно к расходу, лимит овердрафта и его использование, остаток SMS, открытые счета и журнал последних операций по балансу. Счета выставляет платформа (продление подписки, смена тарифа, методики); центр оплачивает открытый счёт онлайн картой.

Перед оплатой показываются сумма и последствие: смена тарифа или продление подписки произойдут сразу после оплаты, купленный курс будет передан центру. Центр оплачивает только свои счета. Пополнить баланс может только платформа после получения денег вне системы ([`PLT-BAL-030`](#PLT-BAL-030)): центр видит пополнение в журнале. Касса, платежи учеников и зарплаты в разделе не показываются ([`BR-022`](#BR-022)).

**Правила:** [`BR-001`](#BR-001), [`BR-005`](#BR-005), [`BR-014`](#BR-014), [`BR-019`](#BR-019), [`BR-022`](#BR-022).

**Критерии приёмки**

1. Дано: у центра выставлен счёт на продление подписки. Когда открыт раздел. Тогда счёт виден в открытых счетах с суммой, сроком оплаты и кнопкой «Оплатить онлайн».
2. Когда центр открывает оплату. Тогда до подтверждения показаны сумма и последствие оплаты.
3. Когда оплата подтверждена. Тогда счёт оплачен, последствие применено (подписка продлена, тариф сменён или курс передан), в разделе «Открытых счетов нет», платформа видит счёт оплаченным.
4. Дано: счёт принадлежит другому центру. Тогда оплатить его из этого кабинета нельзя.
5. Дано: счёт уже оплачен. Когда повторная оплата. Тогда она отклонена.
6. Дано: баланс −150 при овердрафте 300. Тогда показаны статус «В овердрафте» и доступно к расходу 150 сомони.

## CTR-USR. Пользователи центра {#CTR-USR}

### CTR-USR-010 Пользователи центра {#CTR-USR-010}

**Роль:** Admin центра · **Согласование:** согласовано (решение по [`Q-020`](#Q-020)) · **Реализация:** прототип · **Экран:** Кабинет центра → Пользователи

Единый список всех людей центра: ФИО, телефон, роль (ученик, преподаватель, администратор, кассир), филиал, статус («Активен» или «Заблокирован»). Фильтры по роли и филиалу, поиск по имени и телефону, постраничный вывод. Филиал ученика определяется его группой.

Администратор добавляет ученика (ФИО, телефон, логин для входа, при желании группа); пароль создаётся автоматически и показывается один раз ([`BR-025`](#BR-025)). и блокирует его или возвращает доступ, указав причину; действие записывается в журнал аудита платформы. Сотрудников добавляют и увольняют в разделе «Сотрудники» ([`CTR-STF-010`](#CTR-STF-010)), потому что их число ограничено тарифом ([`BR-023`](#BR-023)). У заблокированного центра добавление и блокировка недоступны ([`BR-012`](#BR-012)).

**Правила:** [`BR-012`](#BR-012), [`BR-023`](#BR-023), [`BR-025`](#BR-025).

**Критерии приёмки**

1. Дано: в центре 48 учеников и 4 сотрудника. Тогда в списке 52 пользователя, фильтр «Студент» показывает 48.
2. Когда добавлен ученик с телефоном, который уже есть у другого ученика центра. Тогда добавление отклонено.
3. Когда ученик заблокирован с причиной. Тогда его статус «Заблокирован», в журнале аудита есть запись, коины ему начислить нельзя.
4. Когда причина блокировки короче 5 символов. Тогда блокировка отклонена, сообщение показано под полем.
5. Когда добавлен ученик. Тогда число учеников в профиле и на дашборде увеличилось.
6. Когда ученик добавлен. Тогда показаны его логин и пароль; логин, занятый на платформе другим человеком, принять нельзя.

## CTR-GRP. Группы {#CTR-GRP}

### CTR-GRP-010 Группы центра {#CTR-GRP-010}

**Роль:** Admin центра · **Согласование:** согласовано (решение по [`Q-020`](#Q-020): ученик в нескольких группах) · **Реализация:** частично · **Экран:** Кабинет центра → Группы, страница группы

Список групп: название, курс, филиал, преподаватель, занято мест из доступных, статус («Активна», «В архиве»). Фильтры по курсу, филиалу, преподавателю и статусу, постраничный вывод. Группа с заполненностью меньше половины отмечена «Мало».

Страница группы показывает курс, филиал, преподавателя, период, систему оценивания (дни и время занятий, длительность, баллы за домашнее задание и за посещение в день, день и баллы за экзамен) и состав: ФИО, телефон, дата вступления, статус. Администратор создаёт и правит группу, добавляет учеников и убирает их из группы. Решение владельца: ученик может состоять в любом числе групп, по каждой ведётся отдельный счёт ([`BR-028`](#BR-028), [`CTR-FIN-050`](#CTR-FIN-050)); в прототипе реализовано ограничение «не более одной группы»: добавление в новую переводит ученика из прежней, и это поведение подлежит замене. Нельзя добавить сверх числа мест, заблокированного ученика или в архивную группу; уменьшить число мест ниже текущего состава тоже нельзя. Преподавателем может быть только действующий преподаватель этого же центра. Убранный из группы ученик остаётся в центре без группы.

**Правила:** [`BR-012`](#BR-012), [`BR-024`](#BR-024), [`BR-028`](#BR-028).

**Критерии приёмки**

1. Дано: группа на 2 места с двумя учениками. Когда добавляется третий. Тогда добавление отклонено с пояснением, что мест нет.
2. Когда группа создаётся с датой окончания раньше начала или с преподавателем другого центра. Тогда создание отклонено, ошибки показаны под полями.
3. Когда ученик убран из группы. Тогда место освобождается, ученик остаётся в списке пользователей.
4. Дано: группа в архиве. Тогда менять её состав нельзя.
5. Когда открыта группа другого центра. Тогда она не найдена.
6. Когда у группы время занятия пересекается с другой группой того же преподавателя. Тогда сохранение отклонено ([`BR-024`](#BR-024)).

## CTR-ORG. Структура центра {#CTR-ORG}

### CTR-ORG-010 Филиалы и аудитории {#CTR-ORG-010}

**Роль:** Admin центра · **Согласование:** согласовано · **Реализация:** частично · **Экран:** Филиалы и каталог

Создание филиалов с привязкой точных GPS-координат (для карты города и контроля геозоны сотрудников) и справочник кабинетов с указанием вместимости. Каждый новый филиал отправляется на публикацию в каталог через модерацию платформы ([`PLT-MOD-040`](#PLT-MOD-040)) и не виден родителям до публикации; число филиалов ограничено тарифом центра ([`BR-018`](#BR-018)). В прототипе реализована подача заявок на публикацию; справочник кабинетов не реализован.

## CTR-SCH. Расписание и замены {#CTR-SCH}

### CTR-SCH-010 Конструктор расписания {#CTR-SCH-010}

**Роль:** Admin центра · **Согласование:** согласовано (решение по [`Q-021`](#Q-021)) · **Реализация:** частично · **Экран:** Кабинет центра → Расписание, карточка группы

Формирование сетки групповых занятий и индивидуальных уроков (один на один с преподавателем) с автоматической проверкой конфликтов по занятости аудиторий и учителей. Цены привязываются к конкретной группе филиала.

В прототипе реализована недельная сетка групповых занятий: у группы задаются дни недели, время начала и длительность (от 30 до 240 минут, занятие заканчивается до полуночи). Расписание показывает занятия всех активных групп по дням недели, отсортированные по времени; фильтры по филиалу и преподавателю; сегодняшний день выделен; занятие ведёт на страницу группы. Группа в архиве в расписание не попадает. Проверка конфликтов работает по преподавателю ([`BR-024`](#BR-024)); индивидуальные уроки, аудитории, цены и перенос занятий в прототипе не реализованы. Решение владельца: они входят в первую версию; каникулы и праздники центр задаёт списком дат, пропущенный урок отрабатывается вручную (в другой группе или в другое время) без возврата денег.

**Правила:** [`BR-024`](#BR-024).

**Критерии приёмки**

1. Дано: у преподавателя занятие в понедельник с 10:00 до 11:30. Когда администратор сохраняет другую его группу на понедельник с 11:00. Тогда сохранение отклонено, под полем времени названа группа, с которой пересечение.
2. Когда группа переведена в архив. Тогда её занятий в расписании нет.
3. Когда в расписании выбран филиал. Тогда показаны только занятия групп этого филиала.
4. Когда время указано не в формате ЧЧ:ММ или длительность меньше 30 минут. Тогда сохранение группы отклонено, ошибки показаны под полями.

### CTR-SCH-020 Оперативная замена преподавателей {#CTR-SCH-020}

**Роль:** Admin центра · **Согласование:** согласовано · **Реализация:** план

При болезни или отсутствии учителя администратор в один клик подбирает свободного преподавателя того же профиля. Урок переносится в график заменяющего, ученикам уходит уведомление (`SYS-I18-020`), ставка за урок перенаправляется заменяющему ([`CTR-PAY-020`](#CTR-PAY-020)).

## CTR-CIN. Автоправила баллов {#CTR-CIN}

### CTR-CIN-010 Автоправила начисления баллов {#CTR-CIN-010}

Фильтр по области, постраничный вывод. Администратор добавляет правило (порог от 1 до 100 процентов, награда от 1 до 10 000 баллов), меняет его, включает и выключает. Источник баллов — только автоправила и начисление преподавателем за успехи ([`LRN-TCH-040`](#LRN-TCH-040)); купить баллы или начислить их администратором вручную нельзя ([`BR-030`](#BR-030)). **Критерии приёмки**

1. Дано: у центра два правила, из них одно выключено. Тогда в списке видны условия «Средний % ≥ 90» и статусы.
2. Когда порог больше 100. Тогда сохранение отклонено, сообщение под полем.
3. Когда правило выключено. Тогда его статус «Выключено», остальные поля не меняются.

## CTR-COI. Аналитика баллов {#CTR-COI}

### CTR-COI-010 Аналитика баллов учеников {#CTR-COI-010}

**Роль:** Admin центра · **Согласование:** допущение ([`Q-019`](#Q-019)) · **Реализация:** частично · **Экран:** Кабинет центра → Аналитика

Рейтинг учеников по баллам: место, ученик, группа, филиал, баланс баллов, статус. Итоги: число учеников, всего выдано баллов, среднее на ученика, потрачено на оплату, сгорело. Фильтры по группе и диапазону баллов, поиск по имени, постраничный вывод. Администратор филиала видит данные своего филиала, владелец — всех ([`BR-038`](#BR-038)).

Баллы начисляют только преподаватели за успехи ([`LRN-TCH-040`](#LRN-TCH-040)) и автоправила ([`CTR-CIN-010`](#CTR-CIN-010)); начисление администратором вручную не предусмотрено ([`BR-030`](#BR-030)). У заблокированного центра раздел доступен для просмотра ([`BR-012`](#BR-012)).

**Критерии приёмки**

1. Дано: у центра ученики с разным числом баллов. Тогда рейтинг отсортирован по убыванию баллов.
2. Когда задан диапазон «от 50 до 50». Тогда показаны только ученики с таким остатком.
3. Когда администратор филиала открывает раздел. Тогда видны только ученики его филиала.

## CTR-FIN. Финансы центра: начисления, приём оплат, расходы {#CTR-FIN}

Платформа не принимает деньги учеников и не хранит их: деньги получает центр (наличные в кассу, эквайринг центра, перевод на кошелёк сотрудника), а платформа только фиксирует факт оплаты и ведёт учёт долгов ([`BR-026`](#BR-026)). Все суммы хранятся в дирамах (1 сомони = 100 дирам), валюта одна — сомони ([`BR-027`](#BR-027)).

### CTR-FIN-010 Локальная конфиденциальность данных {#CTR-FIN-010}

**Роль:** система · **Согласование:** согласовано · **Реализация:** план

Прайс-листы, суммы оплат, кассовые остатки, расходы и ведомости зарплат хранятся в изолированном контуре центра. SuperAdmin видит только технические метрики. См. [`BR-022`](#BR-022).

### CTR-FIN-020 Приём оплат и квитанции {#CTR-FIN-020}

**Роль:** Кассир, Admin центра · **Согласование:** допущение ([`Q-028`](#Q-028)) · **Реализация:** план

Платёж вносит кассир: выбирает ученика и его группу (оплата привязана к связке «ученик + группа», [`BR-028`](#BR-028)), месяц, который покрывает платёж, сумму и способ приёма ([`CTR-FIN-060`](#CTR-FIN-060)). Платёж получает статус «Принят». После сверки статус становится «Сверен» ([`CTR-FIN-070`](#CTR-FIN-070)). Для каждого платежа формируется квитанция в виде PDF с номером, уникальным внутри центра; на ней указано «не фискальный документ» ([`SYS-DOC-010`](#SYS-DOC-010), [`Q-026`](#Q-026)).

Платёж можно вносить частично и сверх начисления: остаток и переплата фиксируются ([`BR-029`](#BR-029)). Изменить или удалить проведённый платёж нельзя; ошибку исправляет сторно с причиной ([`BR-010`](#BR-010), [`BR-031`](#BR-031)).

**Правила:** [`BR-010`](#BR-010), [`BR-011`](#BR-011), [`BR-026`](#BR-026), [`BR-028`](#BR-028), [`BR-029`](#BR-029), [`BR-031`](#BR-031).

**Критерии приёмки**

1. Дано: начисление за март 300 сомони. Когда кассир вносит 100. Тогда платёж «Принят», долг за март 200, просрочки до 1 апреля нет.
2. Когда внесено 350. Тогда март закрыт, 50 сомони записаны как лишний остаток ученика и сами ни на какой месяц не распределяются.
3. Когда кассир пытается изменить проведённый платёж. Тогда действие отклонено, доступно только сторно с причиной.
4. Когда платёж внесён. Тогда сформирована квитанция с номером центра и пометкой «не фискальный документ».
5. Когда один и тот же запрос на платёж повторён с тем же ключом идемпотентности. Тогда второй платёж не создаётся.

### CTR-FIN-030 Баллы как платёжный баланс ученика {#CTR-FIN-030}

**Роль:** Admin центра, Родитель, Ученик · **Согласование:** допущение ([`Q-029`](#Q-029)) · **Реализация:** план

Баллы — отдельный платёжный баланс ученика, не деньги. Источники: баллы за успехи ([`LRN-TCH-040`](#LRN-TCH-040)) и автоправила ([`CTR-CIN-010`](#CTR-CIN-010)); купить баллы нельзя. Каждое начисление — отдельный лот: дата выдачи, срок действия, остаток. Срок жизни лота задаёт центр в настройках. Просроченный остаток сгорает, сгорание записывается проводкой.

Ученик или родитель сам решает, какую долю баллов потратить на оплату месяца (любое число баллов не более остатка и не более долга). Курс обмена задаёт администратор центра (например, 100 баллов = 10 сомони). Списание идёт из лотов, срок которых истекает раньше. Оплата баллами в отчётах показывается отдельной строкой, не смешиваясь с деньгами.

**Правила:** [`BR-030`](#BR-030).

**Критерии приёмки**

1. Дано: у ученика два лота, 50 баллов со сроком до 1 апреля и 80 до 1 июня. Когда он тратит 70. Тогда сначала списан весь первый лот, затем 20 из второго.
2. Когда срок лота истёк. Тогда остаток сгорел, в журнале есть запись о сгорании.
3. Когда ученик тратит больше баллов, чем у него есть, или больше долга по месяцу. Тогда списание отклонено.
4. Когда оплата выполнена баллами. Тогда в отчёте по поступлениям она в отдельной строке «баллы».

### CTR-FIN-040 Кассовые смены и отмена платежей {#CTR-FIN-040}

**Роль:** Кассир, Admin центра · **Согласование:** согласовано · **Реализация:** план

Открытие и закрытие кассовой смены с итоговым отчётом (Z-отчёт): наличные, эквайринг, p2p отдельно. Отмена ранее принятого платежа выполняется только сторно по причине ([`BR-031`](#BR-031), [`SYS-AUD-010`](#SYS-AUD-010)). Крупные отмены попадают в уведомление владельцу ([`SYS-AUD-040`](#SYS-AUD-040)).

### CTR-FIN-050 Начисления ученикам {#CTR-FIN-050}

**Роль:** Admin центра · **Согласование:** допущение ([`Q-028`](#Q-028)) · **Реализация:** план

Начисление создаётся на связку «ученик + группа» за календарный месяц. Сумму за месяц определяет и меняет центр сам; она может отличаться от стандартной цены группы. Скидки центра ([`CTR-FIN-100`](#CTR-FIN-100)) показываются отдельной строкой и уменьшают сумму к оплате (вступление в середине месяца, пауза, пропуски — решает администратор вручную). Каждая ручная корректировка начисления выполняется с причиной и записывается в журнал центра ([`BR-011`](#BR-011), [`BR-032`](#BR-032)).

Долг по месяцу — начисление минус внесённые деньги и погашение баллами. Начиная с 1-го числа следующего месяца непогашенный остаток считается просроченным ([`BR-029`](#BR-029)). При переводе ученика в другую группу остаток долга переносится в новую связку; история старой связки сохраняется.

**Правила:** [`BR-011`](#BR-011), [`BR-028`](#BR-028), [`BR-029`](#BR-029), [`BR-032`](#BR-032).

**Критерии приёмки**

1. Дано: ученик вступил 15 марта, стандартная цена 300. Когда администратор ставит начисление 150 с причиной. Тогда в журнале центра есть запись «было 300 → стало 150» и причина.
2. Когда причина не указана. Тогда корректировка отклонена.
3. Дано: ученик ходит в две группы. Тогда счета и долги по группам ведутся отдельно.
4. Когда ученик переведён в другую группу. Тогда остаток долга виден в новой связке.
5. Дано: за март внесено 100 из 300. Когда наступило 1 апреля. Тогда 200 сомони помечены просроченными.

### CTR-FIN-060 Способы приёма оплаты {#CTR-FIN-060}

**Роль:** Admin центра, Кассир · **Согласование:** допущение ([`Q-025`](#Q-025)) · **Реализация:** план

Центр сам выбирает, какие способы включить:

| Способ | Как фиксируется |
|:--|:--|
| Касса (наличные) | Кассир вносит платёж и указывает сумму; деньги в кассе центра |
| Эквайринг центра | Центр подключает собственный эквайринг (ключи шифруются, [`NFR-SEC-040`](#NFR-SEC-040)); платёж приходит подписанным вебхуком, деньги поступают напрямую центру. Платёж создаётся автоматически |
| Кошелёк сотрудника (p2p) | Родитель переводит деньги на кошелёк или карту сотрудника и показывает перевод администратору. Кассир вносит платёж с номером транзакции, последними 4 цифрами карты или кошелька, суммой и датой; скриншот необязателен |

Для p2p номер транзакции уникален в пределах центра ([`BR-033`](#BR-033)). Платёж из эквайринга приходит со статусом «Принят» и сверяется так же, как остальные.

**Критерии приёмки**

1. Дано: центр включил только кассу. Тогда другие способы кассиру недоступны.
2. Когда внесён p2p-платёж с номером транзакции, уже использованным в центре. Тогда платёж отклонён.
3. Когда вебхук эквайринга пришёл дважды с одним идентификатором события. Тогда платёж создан один раз.
4. Когда подпись вебхука неверна. Тогда платёж не создаётся, событие записано в журнал безопасности.

### CTR-FIN-070 Сверка платежей {#CTR-FIN-070}

**Роль:** Owner, Admin центра · **Согласование:** допущение ([`Q-028`](#Q-028)) · **Реализация:** план

Владелец и администратор филиала видят платежи в статусе «Принят» (администратор — своего филиала), сверяют их с реальными поступлениями (касса, выписка эквайринга, кошелёк сотрудника) и переводят в «Сверен». Несверенные платежи старше заданного числа дней подсвечиваются. Сторно возможно из обоих статусов ([`BR-031`](#BR-031)).

Если платёж внёс тот же человек, который хочет его сверить (при совмещении ролей, [`BR-040`](#BR-040)), сверка допускается только после явного подтверждения «я проверил поступление»: в журнале платёж помечается «самосверка», а отчёт владельцу показывает самосверки отдельной строкой. Отчёт владельцу показывает платежи по способам, сумму несверенных, самосверки и список сторно.

**Критерии приёмки**

1. Когда администратор сверяет чужой платёж. Тогда статус «Сверен», в журнале есть запись, кто и когда сверил.
2. Когда человек сверяет собственный платёж без подтверждения. Тогда действие отклонено.
3. Когда человек сверяет собственный платёж с подтверждением. Тогда статус «Сверен», запись помечена «самосверка», платёж попадает в отдельную строку отчёта.
4. Когда платёж в статусе «Сторнирован». Тогда сверить его нельзя.
5. Когда кассир открывает раздел сверки. Тогда он недоступен.

### CTR-FIN-080 Расходы центра и отчёт о прибыли {#CTR-FIN-080}

**Роль:** Admin центра · **Согласование:** допущение ([`Q-030`](#Q-030)) · **Реализация:** план

Администратор вносит расходы по категориям: аренда, зарплаты, коммунальные услуги, реклама, инвентарь, налоги, прочее (список категорий центр может расширять). Расход может быть повторяющимся (аренда раз в месяц). Расходы на зарплаты попадают из расчёта зарплат ([`CTR-PAY-010`](#CTR-PAY-010)) автоматически. Отчёт о прибыли: поступления (деньги отдельно от баллов) минус все расходы за период. Расход можно отменить только сторно с причиной.

**Критерии приёмки**

1. Дано: за месяц поступило 10 000, расходы: аренда 3 000, зарплата 4 000, прочее 500. Тогда прибыль 2 500.
2. Когда добавлен повторяющийся расход. Тогда он создаётся каждый период до отключения.
3. Когда расход отменяется. Тогда отмена идёт сторно с причиной, исходная запись остаётся.

### CTR-FIN-090 Возврат денег ученику {#CTR-FIN-090}

**Роль:** Admin центра · **Согласование:** допущение ([`Q-028`](#Q-028)) · **Реализация:** план

Возврат выполняется как сторно платежа (полное или частичное) по причине; сумма возврата не превышает уплаченную. Деньги возвращает центр вне платформы, платформа фиксирует факт и записывает в журнал. Возврат баллов не выполняется.

**Критерии приёмки**

1. Когда сумма возврата больше платежа. Тогда возврат отклонён.
2. Когда возврат выполнен. Тогда долг по месяцу пересчитан, квитанция помечена сторнированной.

### CTR-FIN-100 Скидки центра {#CTR-FIN-100}

**Роль:** Owner, Admin центра · **Согласование:** допущение ([`Q-030`](#Q-030)) · **Реализация:** план

Правила скидок задаёт владелец ([`CTR-SET-010`](#CTR-SET-010)): название, вид (процент или фиксированная сумма), срок действия, статус. Пример: «Семья от двух учеников — 10%». Администратор филиала назначает скидку ученику или семье вручную, с причиной; семья определяется общим родителем. Автоматических правил нет ([`BR-037`](#BR-037)).

Скидка уменьшает начисление за месяц отдельной строкой: базовая сумма сохраняется, к оплате — базовая минус скидки. Назначение и снятие скидки пишутся в журнал центра. В отчётах скидки показываются отдельно от денег и баллов. Схема зарплаты «процент от оплат группы» ([`CTR-PAY-010`](#CTR-PAY-010)) настраивается: считать процент от суммы со скидкой или без.

**Критерии приёмки**

1. Дано: начисление за март 300, назначена скидка 10%. Тогда к оплате 270, базовая сумма 300 видна, скидка отдельной строкой.
2. Когда скидка назначена без причины. Тогда назначение отклонено.
3. Когда скидка снята. Тогда начисления будущих месяцев считаются без неё, закрытые месяцы не пересчитываются.
4. Когда срок действия скидки истёк. Тогда новые начисления считаются без неё.

## CTR-PAY. Зарплата сотрудников {#CTR-PAY}

### CTR-PAY-010 Схемы расчёта вознаграждения {#CTR-PAY-010}

**Роль:** Admin центра · **Согласование:** согласовано · **Реализация:** план

В карточке преподавателя администратор выбирает индивидуальную схему расчёта (или комбинирует их для разных групп). Начисление происходит автоматически только после перевода занятия в журнале в статус «Проведён». Результат — расчёт и ведомость; аванс, штраф и премия вносятся вручную отдельными записями с причиной ([`BR-011`](#BR-011)).

| Схема | Механика расчёта | Применение |
|:--|:--|:--|
| 1. Фиксированная ставка за урок или час | Твёрдая сумма за каждое проведённое занятие (например, 60 сомони за академический час) независимо от числа учеников | Базовые курсы и мини-группы: центр берёт риск заполняемости, учителю гарантирован доход |
| 2. Подушевая оплата | Оплата только за фактически присутствовавших (статусы «Присутствовал» и «Опоздал»), например 15 сомони за ученика; за «Пропустил» начисления нет | Мотивирует удерживать интерес детей и следить за доходимостью |
| 3. Процент от оплат группы (Revenue Share) | Установленный процент (например, 35% или 40%) от стоимости уроков посетивших занятие учеников, с учётом индивидуальных скидок или без них (настраивается администратором) | Партнёрская модель для опытных преподавателей и авторских курсов |

### CTR-PAY-020 Начисление при заменах {#CTR-PAY-020}

**Роль:** система · **Согласование:** согласовано · **Реализация:** план

Если урок провёл заменяющий преподаватель, оплата за занятие начисляется по схеме заменяющего, а занятие исключается из ведомости основного учителя ([`CTR-SCH-020`](#CTR-SCH-020)).

### CTR-PAY-030 Ведомость и ручные записи {#CTR-PAY-030}

**Роль:** Admin центра · **Согласование:** допущение ([`Q-030`](#Q-030)) · **Реализация:** план

Ведомость за месяц: начислено по схемам, аванс, штрафы, премии, итог к выплате. Выплата отмечается записью; итог попадает в расходы центра ([`CTR-FIN-080`](#CTR-FIN-080)). Ручные записи (аванс, штраф, премия) требуют причины и попадают в журнал центра.

**Критерии приёмки**

1. Когда внесён штраф без причины. Тогда запись отклонена.
2. Когда ведомость закрыта и выплата отмечена. Тогда итог попал в расходы центра за месяц.

## LRN-TCH. Преподаватель: журнал и мотивация {#LRN-TCH}

### LRN-TCH-010 Гео-чек-ин прихода на работу {#LRN-TCH-010}

**Роль:** Преподаватель · **Согласование:** согласовано · **Реализация:** план

Кнопка «Начать смену» в мобильном или веб-интерфейсе срабатывает только при нахождении устройства в заданном радиусе (например, 100 метров) от GPS-координат филиала. Время прихода фиксируется.

### LRN-TCH-020 Электронный журнал успеваемости {#LRN-TCH-020}

**Роль:** Преподаватель · **Согласование:** согласовано · **Реализация:** план

Отметка статуса каждого ученика на занятии: «Присутствовал», «Опоздал» (с указанием минут), «Пропустил без причины», «Уважительная причина»; шкала оценок настраивается центром (5- или 100-балльная, по умолчанию 5-балльная). Оценки и быстрые теги-комментарии. Перевод занятия в статус «Проведён» запускает начисление зарплаты ([`CTR-PAY-010`](#CTR-PAY-010)); счёт ученика за месяц от числа занятий не зависит ([`BR-028`](#BR-028)).

### LRN-TCH-030 База знаний и автопроверка тестов {#LRN-TCH-030}

**Роль:** Преподаватель · **Согласование:** согласовано · **Реализация:** план

Преподаватель создаёт курсы, материалы и тесты центра; они принадлежат центру, редактирует автор и администраторы, при увольнении преподавателя остаются в центре. Прикрепление PDF, презентаций и видео к уроку или группе. Конструктор домашних тестов с автоматической проверкой ответов и переносом балла в журнал. Материалы купленных и собственных курсов центра описаны в [`PLT-MKT-090`](#PLT-MKT-090).

### LRN-TCH-040 Начисление баллов за успехи {#LRN-TCH-040}

**Роль:** Преподаватель · **Согласование:** согласовано · **Реализация:** план

Преподаватель не видит долги учеников и телефоны родителей; родителям он не пишет, о посещаемости, оценках и баллах родители узнают из автоматических уведомлений и тегов в журнале. Поощрение учеников бонусными баллами за оценки, активность и вовремя сданное ДЗ в пределах недельного или месячного бюджета баллов на группу, установленного администратором. Баллы попадают в баланс ученика лотом со сроком жизни и тратятся на оплату ([`CTR-FIN-030`](#CTR-FIN-030), [`BR-030`](#BR-030)).

## SYS-ACC. Вход и доступ {#SYS-ACC}

### SYS-ACC-010 Вход по логину и паролю {#SYS-ACC-010}

**Роль:** все роли · **Согласование:** допущение ([`Q-022`](#Q-022)) · **Реализация:** прототип · **Экран:** Страница входа

Основной вход — по SMS-коду ([`SYS-ACC-030`](#SYS-ACC-030)); здесь описан запасной вход. Человек входит по логину и паролю, которые выдал администратор центра (владельцу центра — платформа). Логин не зависит от регистра и лишних пробелов. Веб-кабинет есть у владельца и администратора центра: после входа открывается кабинет их центра. Преподаватели, менеджеры и ученики работают в мобильных приложениях (`60-client-platforms`), поэтому после входа им показывается пояснение.

Выданный пароль временный. После первого входа система требует придумать свой пароль: не короче 8 символов, с буквой и цифрой, не совпадающий с временным; несовпадение повторного ввода и слабый пароль показываются под полем. После смены прежний пароль не работает, смена записывается в журнал аудита без паролей.

На неверный логин и неверный пароль система отвечает одинаково, чтобы нельзя было узнать, существует ли логин. После пяти неудачных попыток подряд вход по этому логину блокируется на 15 минут, даже если пароль верный. Заблокированный ученик и уволенный сотрудник войти не могут ([`BR-025`](#BR-025)).

**Правила:** [`BR-012`](#BR-012), [`BR-025`](#BR-025).

**Критерии приёмки**

1. Дано: владелец центра с временным паролем. Когда вводит верные данные. Тогда его просят сменить пароль, после смены открывается кабинет его центра.
2. Когда введён неверный пароль и когда введён несуществующий логин. Тогда сообщение одно и то же.
3. Когда пять раз подряд введён неверный пароль. Тогда шестая попытка с верным паролем отклонена с сообщением о блокировке.
4. Когда преподаватель входит успешно. Тогда веб-кабинет не открывается, показано пояснение про мобильное приложение.
5. Когда пароль слишком простой или совпадает с временным. Тогда смена отклонена, пояснение под полем.
6. Дано: ученик заблокирован. Тогда войти он не может.

### SYS-ACC-020 Выдача и сброс данных для входа {#SYS-ACC-020}

**Роль:** Admin центра, SuperAdmin · **Согласование:** допущение ([`Q-022`](#Q-022)) · **Реализация:** прототип · **Экран:** Кабинет центра → Сотрудники, Пользователи; Все центры → панель центра

Администратор центра выдаёт доступ сотруднику или ученику, у которого его ещё нет (придумывает логин), и сбрасывает пароль, если он потерян (логин остаётся прежним). SuperAdmin так же выдаёт или сбрасывает данные для входа владельца центра: логин — номер телефона владельца. В обоих случаях основание обязательно (не короче 5 символов), прежний пароль перестаёт работать, новый временный показывается один раз, действие записывается в журнал аудита ([`BR-025`](#BR-025)). В списках видно, у кого доступ уже выдан. У заблокированного центра выдача недоступна ([`BR-012`](#BR-012)). Сброс чужого сотрудника из другого центра невозможен.

**Критерии приёмки**

1. Дано: у сотрудника доступа нет. Когда администратор выдаёт доступ без логина или без основания. Тогда выдача отклонена, ошибки под полями.
2. Когда пароль сброшен. Тогда логин прежний, старый пароль не работает, новый временный, в журнале есть запись без пароля.
3. Когда администратор другого центра пытается сбросить пароль этого сотрудника. Тогда сотрудник не найден.
4. Когда SuperAdmin выдаёт данные владельцу центра с основанием. Тогда владелец входит с логином-телефоном и новым паролем.

### SYS-ACC-030 Вход по телефону и SMS-коду {#SYS-ACC-030}

**Роль:** все роли · **Согласование:** допущение ([`Q-023`](#Q-023)) · **Реализация:** план

Основной способ входа — единый аккаунт по номеру телефона и одноразовый код из SMS ([`BR-035`](#BR-035)). Один аккаунт может состоять в нескольких центрах, роль и права задаются для пары «человек + центр»; после входа человек выбирает центр и роль. Код действует ограниченное время, число запросов кода и попыток ввода ограничено, повтор безопасен. Вход по логину и паролю ([`SYS-ACC-010`](#SYS-ACC-010)) остаётся запасным вариантом, например для ребёнка без телефона.

Потеря номера: доступ восстанавливает администратор центра после подтверждения личности, действие записывается в журнал аудита ([`BR-036`](#BR-036)). Сессии выдаются короткоживущими токенами с обновлением; выход из других сеансов доступен пользователю.

**Критерии приёмки**

1. Дано: аккаунт состоит в двух центрах. Когда человек входит по SMS-коду. Тогда ему предлагают выбрать центр и роль.
2. Когда код введён неверно пять раз подряд. Тогда запрос блокируется на 15 минут.
3. Когда код просрочен или использован повторно. Тогда вход отклонён.
4. Когда номер сменился и администратор восстанавливает доступ. Тогда в журнале аудита есть запись, старый номер больше не входит.

# Ключевые пользовательские сценарии

Для каждого сценария указаны требования, которые он проверяет.

## Сценарий 1. Подключение центра и настройка прав (SuperAdmin)

*Требования: [`PLT-CTR-020`](#PLT-CTR-020), [`PLT-CTR-040`](#PLT-CTR-040), [`PLT-CTR-050`](#PLT-CTR-050)*

1. **Onboarding.** SuperAdmin нажимает «Зарегистрировать центр», проходит три шага мастера и активирует бесплатный тариф «Старт».
2. **Тонкая настройка.** В реестре открывает «Настройка модулей» центра, включает модули зарплат и инвентаря, задаёт лимиты сотрудников и ГБ.
3. **Режим поддержки.** При обращении клиента сотрудник поддержки указывает причину и нажимает «Войти», смотрит настройки центра только для чтения (без финансов) и завершает сессию или ждёт окончания таймера; администратор центра видит запись о входе.

## Сценарий 2. Поиск центра родителем на карте и пробный урок

*Требования: [`PLT-MOD-030`](#PLT-MOD-030), [`LRN-CAT-010`](#LRN-CAT-010), [`CTR-CRM-010`](#CTR-CRM-010)*

1. **Модерация и публикация.** SuperAdmin проверяет GPS-координаты и описание на русском и таджикском филиала в «Модерации каталога» и публикует точку.
2. **Поиск и заявка.** Родитель открывает каталог на карте, фильтрует центры по предмету и району, строит маршрут и отправляет заявку на пробный урок.
3. **Запись и зачисление.** Администратор записывает ребёнка «Гостем на 1 урок». После оценки (1–5 звёзд) переводит в основной состав и формирует PDF-договор ([`SYS-DOC-010`](#SYS-DOC-010)).

## Сценарий 3. Рабочий день преподавателя, гео-чек-ин и баллы

*Требования: [`LRN-TCH-010`](#LRN-TCH-010), [`LRN-TCH-020`](#LRN-TCH-020), [`LRN-TCH-030`](#LRN-TCH-030), [`LRN-TCH-040`](#LRN-TCH-040), [`CTR-PAY-010`](#CTR-PAY-010), `SYS-I18-020`*

1. **Приход на работу.** Преподаватель нажимает «Начать смену»; система сверяет GPS с радиусом филиала и фиксирует время.
2. **Ведение журнала.** Отмечает присутствующих и ставит ученику «Опоздание 10 мин»; родителю на его языке уходит уведомление.
3. **Оценки, баллы и ФОТ.** Выставляет оценки, начисляет +50 баллов лучшим ученикам, прикрепляет тест и переводит урок в «Проведён»: система начисляет зарплату по схеме преподавателя; оценки и посещаемость попадают в автоправила баллов.

## Сценарий 4. Оплата месяца: баллы и кассир

*Требования: [`CTR-FIN-030`](#CTR-FIN-030), [`CTR-FIN-020`](#CTR-FIN-020), [`CTR-FIN-050`](#CTR-FIN-050), [`SYS-AUD-020`](#SYS-AUD-020)*

1. **Начисление.** Администратор центра задал начисление за март по связке «ученик + группа»: 300 сомони. Долг ученика виден родителю.
2. **Баллы.** Родитель видит у ребёнка лоты баллов со сроками (по курсу центра 10 дирамов за балл) и сам тратит 100 баллов, то есть 10 сомони, на март. Списание идёт из лота с ранним сроком.
3. **Деньги.** Родитель приносит 200 сомони наличными кассиру; тот вносит платёж за март со статусом «Принят». Долг за март 90 сомони.
4. **Квитанция и аудит.** Родителю уходит PDF-квитанция («не фискальный документ»), операции записаны в журнал центра и кассовую смену. Оплата баллами в отчёте отдельной строкой.

## Сценарий 5. Сверка платежей, p2p и закрытие смены

*Требования: [`CTR-FIN-040`](#CTR-FIN-040), [`CTR-FIN-060`](#CTR-FIN-060), [`CTR-FIN-070`](#CTR-FIN-070), [`CTR-FIN-090`](#CTR-FIN-090), [`SYS-AUD-020`](#SYS-AUD-020), [`SYS-AUD-040`](#SYS-AUD-040)*

1. **p2p-платёж.** Родитель перевёл деньги на кошелёк сотрудника и показал перевод. Кассир вносит платёж с номером транзакции и последними 4 цифрами; повторный номер система отклоняет.
2. **Z-отчёт.** Кассир закрывает смену; система сводит приходы по способам: наличные, эквайринг, p2p.
3. **Сверка.** Администратор сверяет принятые платежи с реальными поступлениями и переводит их в «Сверен»; свой платёж кассир сверить не может.
4. **Сторно.** Ошибочный платёж администратор отменяет сторно с причиной; владельцу приходит уведомление о крупной отмене, долг по месяцу восстанавливается.
5. **Отчёт владельцу.** Владелец видит платежи по способам, несверенные платежи, расходы и прибыль за период.

## Сценарий 6. Смена тарифа центра

*Требования: [`PLT-TRF-020`](#PLT-TRF-020), [`PLT-BIL-040`](#PLT-BIL-040), [`PLT-BAL-040`](#PLT-BAL-040)*

1. **Выбор центра.** В реестре SuperAdmin открывает «Действия» → «Сменить тариф…» (то же доступно из «Центров у лимита» и «Настройки модулей»).
2. **Тариф и причина.** Диалог показывает цены, разницу, нагрузку после перехода и достаточность баланса; недоступные тарифы заблокированы с указанием превышения. SuperAdmin выбирает тариф и вводит причину.
3. **Способ оплаты.** «Выставить счёт» (оплатит владелец онлайн либо SuperAdmin подтвердит по документу) или «Списать с баланса на платформе».
4. **Результат.** Тариф меняется после оплаты (при списании — сразу); платный тариф действует 30 дней; в журнале видны выставление, оплата, списание и смена «Было → Стало».

## Сценарий 7. Пополнение баланса и управление овердрафтом

*Требования: [`PLT-BAL-030`](#PLT-BAL-030), [`PLT-BAL-050`](#PLT-BAL-050), [`PLT-BAL-060`](#PLT-BAL-060)*

1. **Поступление денег.** Центр перечислил оплату; SuperAdmin открывает «Все центры» → «Действия» → «Баланс и овердрафт…».
2. **Пополнение.** Указывает способ, документ, дату, сумму и подтверждает получение; предпросмотр показывает баланс до и после.
3. **Лимит овердрафта.** При необходимости меняет лимит с причиной; ниже использованного установить нельзя.
4. **Результат.** Запись в журнале баланса и аудита; центр с положительным балансом исчезает из фильтра «В овердрафте».

## Сценарий 8. Центр отправляет филиал на публикацию в каталог

*Требования: [`PLT-MOD-040`](#PLT-MOD-040), [`PLT-MOD-010`](#PLT-MOD-010), [`PLT-MOD-030`](#PLT-MOD-030), [`PLT-MOD-050`](#PLT-MOD-050)*

1. **Заявка центра.** В «Филиалах и каталоге» администратор заполняет карточку (адрес, телефон, точка на карте, описания на русском и таджикском) и отправляет на модерацию.
2. **Очередь модерации.** Заявка появляется в «Модерации каталога»; пока идёт проверка, центр её не меняет.
3. **Решение.** Модератор сверяет координаты и описания и публикует, возвращает или отклоняет с причиной.
4. **Обратная связь.** Центр видит статус («Опубликован на карте», «Возвращён» с комментарием, «Отклонён»); исправленную заявку можно отправить повторно. Все шаги записываются в журнал.

## Сценарий 9. Центр заказывает методику и получает её после онлайн-оплаты

*Требования: [`PLT-MKT-060`](#PLT-MKT-060), [`PLT-MKT-070`](#PLT-MKT-070), [`PLT-MKT-080`](#PLT-MKT-080), [`PLT-MKT-090`](#PLT-MKT-090), [`INT-PAY-010`](#INT-PAY-010)*

1. **Заявка.** Администратор центра открывает «Материалы и тесты» → «Каталог», выбирает курс и нажимает «Подать заявку». Заявка «Новая».
2. **Счёт.** SuperAdmin видит заявку во вкладке «Заявки центров» и выставляет счёт; заявка «Счёт выставлен», в кабинете центра появляется оплата.
3. **Онлайн-оплата и передача.** Владелец оплачивает счёт онлайн; платёжный шлюз сообщает платформе, счёт закрывается, курс передаётся автоматически, заявка «Выполнена».
4. **Результат.** Курс в «Моих методиках»: центр просматривает программу и материалы. Выдача записана в журнал вместе со счётом.

## Сценарий 10. Заявка с ручной оплатой, отказом или бонусом

*Требования: [`PLT-MKT-070`](#PLT-MKT-070), [`PLT-MKT-080`](#PLT-MKT-080), [`PLT-BIL-040`](#PLT-BIL-040), [`PLT-BAL-040`](#PLT-BAL-040)*

1. **Ручная оплата.** Центр заплатил в банке. SuperAdmin выставляет счёт, затем подтверждает оплату по документу; этим же действием курс передаётся центру, заявка «Выполнена».
2. **Отмена счёта.** Если центр передумал, SuperAdmin отменяет счёт с причиной: заявка снова «Новая», доступа нет.
3. **Списание с баланса.** При достаточных средствах SuperAdmin выбирает «Списать с баланса на платформе»: курс открывается сразу, операция в журнале баланса.
4. **Бонус или отказ.** Для акции SuperAdmin передаёт курс бесплатно с причиной; невыполнимую заявку отклоняет с причиной, видимой центру.

## Сценарий 11. SuperAdmin наполняет и публикует курс

*Требования: [`PLT-MKT-020`](#PLT-MKT-020), [`PLT-MKT-030`](#PLT-MKT-030), [`PLT-MKT-040`](#PLT-MKT-040), [`PLT-MKT-050`](#PLT-MKT-050), [`PLT-MKT-110`](#PLT-MKT-110)*

1. **Создание.** «Создать курс»: название, направление, цена; открывается страница курса.
2. **Программа.** На вкладке «Программа и материалы» добавляет модули, уроки и материалы (план, видео, PDF, презентация, тест); счётчики обновляются автоматически.
3. **Публикация.** Когда заданы цена и есть хотя бы один урок, нажимает «Опубликовать»: курс появляется в каталоге центров. Позже может изменить цену или снять курс с публикации с причиной.
4. **Контроль.** На вкладках «Покупатели» и «Заявки» видит, кто купил курс и какие заявки ждут решения; при необходимости отзывает доступ с причиной.

## Сценарий 12. Центр создаёт собственный курс

*Требования: [`PLT-MKT-100`](#PLT-MKT-100), [`PLT-MKT-030`](#PLT-MKT-030)*

1. **Создание.** В «Материалах и тестах» → «Мои курсы» администратор нажимает «Создать курс»: название, направление, описание.
2. **Наполнение.** Добавляет модули и уроки, прикрепляет планы, видео, документы, презентации и тесты; курс редактируется в любой момент.
3. **Область видимости.** Курс виден только этому центру: он не продаётся, не попадает в магазин и недоступен другим центрам и SuperAdmin.

## Сценарий 13. Окончание подписки центра

*Требования: [`PLT-BIL-070`](#PLT-BIL-070), [`PLT-DSH-030`](#PLT-DSH-030), [`BR-034`](#BR-034)*

1. **Окончание периода.** Оплаченный период закончился, счёт на продление не оплачен: 7 дней льготного срока, владелец получает напоминания.
2. **Только чтение.** После льготного срока центр работает в режиме «только чтение»: данные видны, изменять их нельзя, оплатить счёт можно.
3. **Блокировка.** Через 30 дней вход блокируется, данные не удаляются.
4. **Возврат.** После оплаты счёта доступ возвращается полностью.

## Сценарий 14. Вход по SMS в нескольких центрах

*Требования: [`SYS-ACC-030`](#SYS-ACC-030), [`BR-035`](#BR-035), [`BR-036`](#BR-036)*

1. **Код.** Человек вводит номер телефона и получает SMS-код.
2. **Выбор центра.** Он преподаватель в центре А и родитель в центре Б; после кода выбирает центр и роль.
3. **Смена номера.** Если номер потерян, администратор центра подтверждает личность и меняет номер; запись попадает в журнал аудита.

# Клиентские платформы

## NFR-CLI-010 Распределение интерфейсов между Web и мобильным приложением {#NFR-CLI-010}

Для оптимизации бюджета разработки и удобства работы («за компьютером в офисе» против «на ходу со смартфона») клиентские интерфейсы разделяются между Web-приложением и мобильным приложением (iOS / Android).

| Роль и модуль | Формат | Обоснование |
|:--|:--|:--|
| SuperAdmin (владелец платформы) | Только Web | Тарифы, Feature Flags, магазин методик, B2B-биллинг, модерация на карте и режим поддержки требуют большого экрана и работы с таблицами |
| Admin центра (владелец или администратор) | Web + лёгкий мобильный дашборд | Расписание, CRM, зарплаты, аудит и PDF-договоры удобны на ПК; владельцу со смартфона нужны сводка за день и тревожные уведомления |
| Кассир | Web (рабочий ПК или планшет) | Реестр платежей, Z-отчёты и печать квитанций выполняются на стационарном месте |
| Преподаватель | Mobile (основной) + Web для подготовки | На уроке нужны гео-чек-ин, посещаемость и баллы в два касания; загрузка материалов и сборка тестов удобнее в Web |
| Родитель | Первый этап: Telegram-бот и Mini App; затем Mobile (iOS / Android) | На первом этапе уведомления, долг, баллы и расписание в Telegram; нативное приложение добавляет гео-чек-ин, push и карту с маршрутом |
| Ученик | Telegram Mini App, затем Mobile + Web (адаптивный); ребёнок до 12 лет — через устройство родителя | Расписание и баллы нужны в телефоне, большие тесты и PDF удобнее на ноутбуке или планшете |

Команда платформы (менеджер по клиентам, финансы, модератор, поддержка) работает только в Web.

## NFR-CLI-020 Стратегия разработки и запуска {#NFR-CLI-020}

1. **Этап 1. Единое Web-приложение (SPA на React или Vue).** Разрабатывается первым как единая точка входа: панель SuperAdmin, кабинет администратора, касса, конструктор курсов и тестов. Интерфейс адаптивен под мобильный экран, чтобы на старте преподаватели и ученики могли работать через мобильный браузер.
2. **Этап 2. Единое кроссплатформенное мобильное приложение (Flutter или React Native).** Вместо трёх приложений создаётся одно для Родителя, Ученика и Преподавателя; после авторизации интерфейс подстраивается под роль (с мгновенным переключением, если человек и преподаватель, и родитель). Первый кабинет родителя и ученика — Telegram-бот и Mini App ([`INT-TGM-010`](#INT-TGM-010)), нативное приложение позже. Нативное приложение обеспечивает надёжный GPS-трекинг для чек-ина, фоновые Push и плавную карту.

# Нефункциональные требования

Раздел фиксирует то, что уже следует из согласованных требований, и перечисляет показатели, которые ещё нужно утвердить. Утверждённые значения заносятся в таблицу; до этого статус — «к определению».

## NFR-SEC. Безопасность и данные {#NFR-SEC}

### NFR-SEC-010 Изоляция данных центров {#NFR-SEC-010}

Данные каждого центра (прайс-листы, платежи, касса, расходы, зарплаты) хранятся в общей схеме базы данных, строки помечены `tenant_id`, а изоляция дополнительно обеспечивается защитой на уровне строк (RLS) в базе; любой запрос выполняется от имени конкретного центра; SuperAdmin видит только технические метрики ([`BR-022`](#BR-022)). Согласовано.

### NFR-SEC-020 Неизменяемость журнала аудита {#NFR-SEC-020}

Записи журнала нельзя изменить или удалить; финансовые записи удаляются только сторно ([`BR-010`](#BR-010), [`SYS-AUD-010`](#SYS-AUD-010)). Согласовано.

### NFR-SEC-030 Режим поддержки {#NFR-SEC-030}

Вход в кабинет центра всегда с причиной, только на чтение, без финансов, с таймером, отмечен баннером и записывается в журнал платформы и центра ([`PLT-CTR-050`](#PLT-CTR-050)). Согласовано.

### NFR-SEC-040 Защита платёжных данных центра {#NFR-SEC-040}

Ключи эквайринга центра хранятся в зашифрованном виде и не попадают в журналы и ответы API. Вебхуки принимаются только с проверенной подписью; повтор события безопасен (дедупликация по идентификатору события). В журналах только маска (последние 4 цифры) и номер транзакции. Согласовано.

### NFR-SEC-050 Срок хранения журналов {#NFR-SEC-050}

Платёжный журнал хранится не менее 5 лет, остальной журнал аудита не менее 1 года. Окончательные сроки определит юридическое заключение ([`Q-014`](#Q-014)). Допущение.

## NFR-REL. Надёжность и размещение {#NFR-REL}

### NFR-REL-010 Резервное копирование и доступность {#NFR-REL-010}

Ежедневная резервная копия базы и файлов, цель по потере данных (RPO) не более 24 часов, цель по восстановлению (RTO) не более 4 часов, доступность 99,5% в месяц. Периодически проверяется восстановление из копии. Допущение.

### NFR-REL-020 Размещение и переносимость {#NFR-REL-020}

Система размещается в облаке в пределах страны ([`Q-024`](#Q-024)). Приложение упаковано в контейнеры и настраивается переменными окружения, без привязки к конкретному облаку. Допущение.

### NFR-I18-010 Языки интерфейса и уведомлений

Языков два: русский и таджикский, по умолчанию русский. Все тексты хранятся в словарях с ключами; уведомления отправляются на языке получателя (`SYS-I18-010`). Согласовано.

### INT-SMS-010 SMS-шлюз {#INT-SMS-010}

**Согласование:** согласовано · **Реализация:** мок

### INT-GEO-010 Геокодер {#INT-GEO-010}

**Согласование:** допущение ([`Q-006`](#Q-006)) · **Реализация:** мок

### INT-NTF-010 Каналы уведомлений {#INT-NTF-010}

**Согласование:** допущение ([`Q-012`](#Q-012)) · **Реализация:** план

Push, Telegram-бот и SMS для родителей, учеников и владельцев центров (`SYS-I18-020`, [`SYS-AUD-040`](#SYS-AUD-040), [`PLT-SMS-040`](#PLT-SMS-040)). Каналы, языки и тексты напоминаний о счетах и решениях модерации не определены.

### INT-ACQ-010 Эквайринг центра (вебхуки) {#INT-ACQ-010}

**Согласование:** допущение ([`Q-025`](#Q-025)) · **Реализация:** план

Центр подключает собственного эквайера; платформа принимает подписанный вебхук об оплате ученика и создаёт платёж «Принят» ([`CTR-FIN-060`](#CTR-FIN-060)). Ключи центра хранятся зашифрованными ([`NFR-SEC-040`](#NFR-SEC-040)), дедупликация по идентификатору события, неверная подпись не создаёт платёж. Деньги идут напрямую центру ([`BR-026`](#BR-026)).

### INT-TGM-010 Telegram-бот и Mini App {#INT-TGM-010}

**Согласование:** допущение ([`Q-031`](#Q-031)) · **Реализация:** план

Один бот платформы на всех центров. На первом этапе он служит кабинетом родителя и ученика (Mini App) и каналом уведомлений на русском и таджикском (`SYS-I18-020`).

# Каталог бизнес-правил

Правила, общие для нескольких модулей, записаны здесь один раз. Модули ссылаются на них по номеру `BR-…`. Изменение правила меняется в одном месте.

## Деньги, тариф и оплата

### BR-001 Тариф меняется только после оплаты {#BR-001}

Смена тарифа центра на платный выполняется только после оплаты счёта на новый тариф: онлайн, списанием с баланса на платформе или ручным подтверждением SuperAdmin. Исключения: переход на бесплатный тариф («Старт») выполняется сразу; отсрочка оплаты по решению SuperAdmin ([`PLT-TRF-030`](#PLT-TRF-030)). Применяется в [`PLT-TRF-020`](#PLT-TRF-020), [`PLT-TRF-030`](#PLT-TRF-030), [`PLT-BIL-030`](#PLT-BIL-030).

### BR-002 Ручное подтверждение требует основания {#BR-002}

Подтверждение оплаты и пополнение баланса вручную допустимы, только когда деньги уже поступили вне системы. Обязательны: способ, номер документа (выписка, ордер, чек перевода), дата поступления (не в будущем и не раньше выставления счёта), сумма (для счёта — равна сумме счёта, частичные оплаты не поддерживаются) и явное подтверждение. Действие необратимо. Применяется в [`PLT-BIL-040`](#PLT-BIL-040), [`PLT-BAL-030`](#PLT-BAL-030), [`PLT-SMS-020`](#PLT-SMS-020).

### BR-003 «Просрочен» — признак, а не статус {#BR-003}

Счёт остаётся «Ожидает оплаты»; «просрочен» — признак открытого счёта с истёкшим сроком оплаты. Последствия просрочки не определены ([`Q-005`](#Q-005)). Применяется в [`PLT-BIL-020`](#PLT-BIL-020).

### BR-004 Отмена счёта {#BR-004}

Отменить можно только неоплаченный счёт, с указанием причины. Оплаченный счёт отменить нельзя. Применяется в [`PLT-BIL-020`](#PLT-BIL-020), [`PLT-BIL-050`](#PLT-BIL-050).

### BR-005 Списание с баланса в пределах доступного {#BR-005}

Списание с баланса на платформе допустимо в пределах «баланс + лимит овердрафта». Уход баланса в минус фиксируется как использование овердрафта. Применяется в [`PLT-BAL-010`](#PLT-BAL-010), [`PLT-BAL-020`](#PLT-BAL-020), [`PLT-BAL-040`](#PLT-BAL-040), [`PLT-SMS-020`](#PLT-SMS-020), [`PLT-MKT-070`](#PLT-MKT-070).

### BR-006 Лимит овердрафта не ниже использованного {#BR-006}

Лимит овердрафта нельзя установить ниже уже использованной суммы. Применяется в [`PLT-BAL-020`](#PLT-BAL-020), [`PLT-BAL-050`](#PLT-BAL-050).

### BR-007 Один открытый счёт на смену тарифа {#BR-007}

У центра может быть только один неоплаченный счёт на смену тарифа. Применяется в [`PLT-TRF-020`](#PLT-TRF-020).

### BR-008 Тариф недоступен при превышении лимитов {#BR-008}

Тариф, в который центр не вмещается по лимитам (сотрудники, хранилище, филиалы), недоступен для выбора; система перечисляет превышения. Применяется в [`PLT-TRF-020`](#PLT-TRF-020).

### BR-009 Платный период — 30 дней {#BR-009}

Платный тариф действует 30 дней с момента оплаты; подписка продлевается на 30 дней только после оплаты счёта на продление. Применяется в [`PLT-TRF-020`](#PLT-TRF-020), [`PLT-BIL-070`](#PLT-BIL-070), [`PLT-DSH-030`](#PLT-DSH-030).

### BR-020 Цена пакета SMS действует на новые продажи {#BR-020}

Изменение цены пакета SMS влияет только на новые продажи; прежние сохраняют цену. Применяется в [`PLT-SMS-010`](#PLT-SMS-010).

### BR-021 Порог «центр у лимита» {#BR-021}

Центр считается подошедшим к лимиту, когда использование любого из трёх лимитов достигло порога (по умолчанию 80%; переключатель 70, 80, 90, 100%). Применяется в [`PLT-TRF-040`](#PLT-TRF-040).

## Аудит и защита действий

### BR-010 Журнал аудита неизменяем {#BR-010}

Денежные операции, смена тарифов, изменение прав и критичные решения платформы записываются в журнал: время до секунды, ФИО и роль, IP и устройство, действие, объект, «Было → Стало», причина. Записи нельзя изменить или удалить; финансовые записи отменяются только сторно. Применяется в [`PLT-AUD-010`](#PLT-AUD-010), [`SYS-AUD-010`](#SYS-AUD-010), [`SYS-AUD-030`](#SYS-AUD-030).

### BR-011 Причина обязательна {#BR-011}

Необратимые и денежные действия, а также решения с последствиями для центра выполняются только с причиной или основанием: смена тарифа, отмена счёта, изменение лимита овердрафта, изменение цены пакета и курса, снятие курса с публикации, отзыв доступа, бесплатная передача, отклонение и возврат заявок. Применяется в [`PLT-TRF-020`](#PLT-TRF-020), [`PLT-BAL-050`](#PLT-BAL-050), [`PLT-MKT-050`](#PLT-MKT-050), [`PLT-MOD-030`](#PLT-MOD-030).

### BR-012 Заблокированный центр {#BR-012}

Для заблокированного центра недоступны смена тарифа, списание с баланса, покупки, заявки на курсы и начисления SMS. Применяется в [`PLT-CTR-030`](#PLT-CTR-030), [`PLT-TRF-020`](#PLT-TRF-020), [`PLT-MKT-060`](#PLT-MKT-060).

### BR-022 Изоляция данных центра {#BR-022}

Прайс-листы, платежи, касса, расходы и зарплаты центра хранятся в его изолированном контуре (общая схема базы с `tenant_id` и защитой на уровне строк, [`NFR-SEC-010`](#NFR-SEC-010)); SuperAdmin ими не управляет и их не видит, в том числе в режиме поддержки ([`PLT-CTR-050`](#PLT-CTR-050)). Баланс и овердрафт центра на платформе — взаиморасчёты с платформой, а не касса центра. Применяется в [`PLT-BAL-010`](#PLT-BAL-010), [`CTR-FIN-010`](#CTR-FIN-010), [`NFR-SEC-010`](#NFR-SEC-010).

### BR-019 Овердрафт центра и долг ученика {#BR-019}

«Овердрафт» центра (долг перед платформой) не связан с долгом ученика перед центром ([`CTR-FIN-050`](#CTR-FIN-050)). В интерфейсе баланс центра называется «Баланс на платформе». Применяется в [`PLT-CTR-010`](#PLT-CTR-010), [`PLT-BAL-010`](#PLT-BAL-010).

## Курсы и каталог

### BR-013 Условия публикации курса {#BR-013}

Курс публикуется только при заданной цене и хотя бы одном уроке. Применяется в [`PLT-MKT-040`](#PLT-MKT-040).

### BR-014 Доступ к курсу создаётся только оплатой или бонусом {#BR-014}

Доступ центра к курсу создаётся одним действием: оплата счёта на курс (онлайн — автоматически, вручную — действием SuperAdmin), списание с баланса или бесплатная передача по причине. Курсом нельзя владеть дважды; на один курс у центра не может быть второго открытого счёта или заявки. Применяется в [`PLT-MKT-060`](#PLT-MKT-060), [`PLT-MKT-080`](#PLT-MKT-080).

### BR-015 Покупка даёт текущую версию курса {#BR-015}

Число уроков и тестов фиксируется в момент передачи; новые версии продаются отдельно ([`Q-009`](#Q-009)). Применяется в [`PLT-MKT-080`](#PLT-MKT-080), [`PLT-MKT-090`](#PLT-MKT-090).

### BR-016 Собственный курс центра изолирован {#BR-016}

Курс, созданный центром, виден и редактируется только этим центром, не продаётся и не попадает в магазин, заявки и аудит платформы. Купленный курс центр может только просматривать. Применяется в [`PLT-MKT-010`](#PLT-MKT-010), [`PLT-MKT-100`](#PLT-MKT-100).

### BR-017 Условия публикации филиала в каталоге {#BR-017}

Публикация филиала возможна при подтверждённых координатах и заполненных описаниях RU и TJ; расхождение точки с геокодером более 150 м помечается. Решения «Вернуть» и «Отклонить» требуют причины. Применяется в [`PLT-MOD-020`](#PLT-MOD-020), [`PLT-MOD-030`](#PLT-MOD-030), `SYS-I18-030`.

### BR-018 Лимит филиалов {#BR-018}

Число заявок на публикацию (на модерации и опубликованных) ограничено лимитом филиалов тарифа центра. Применяется в [`PLT-MOD-040`](#PLT-MOD-040), [`CTR-ORG-010`](#CTR-ORG-010).

### BR-023 Лимит сотрудников {#BR-023}

Число активных сотрудников центра не превышает лимит сотрудников его тарифа. Добавление сверх лимита отклоняется; увольнение освобождает место. Применяется в [`CTR-STF-010`](#CTR-STF-010), [`PLT-TRF-010`](#PLT-TRF-010).

### BR-024 Занятия преподавателя не пересекаются {#BR-024}

У одного преподавателя не может быть двух занятий активных групп в один день недели с пересекающимся временем. Сохранение группы с таким временем отклоняется с указанием группы, с которой есть пересечение. Применяется в [`CTR-SCH-010`](#CTR-SCH-010), [`CTR-GRP-010`](#CTR-GRP-010).

### BR-025 Данные для входа {#BR-025}

Основной вход — по номеру телефона и коду из SMS ([`SYS-ACC-030`](#SYS-ACC-030)). Запасной вариант, например для ребёнка без телефона: каждому человеку, получившему такой доступ (администратор центра, сотрудник, ученик), платформа выдаёт логин и временный пароль. Логин уникален на всей платформе и состоит из 4–32 символов: латинские буквы, цифры, точка, дефис, подчёркивание; регистр не различается. Логин администратора центра формируется из номера телефона владельца (если он занят, по номеру центра), логин сотрудника и ученика придумывает администратор центра. Пароль создаётся автоматически, показывается один раз, в открытом виде не хранится и не попадает в журнал аудита; при первом входе его нужно сменить. При увольнении сотрудника доступ закрывается, а логин освобождается. Заблокированный ученик войти не может. Выдача доступа и сброс пароля требуют основания и записываются в журнал аудита без пароля; после пяти неудачных попыток подряд вход по логину блокируется на 15 минут. Применяется в [`PLT-CTR-020`](#PLT-CTR-020), [`CTR-STF-010`](#CTR-STF-010), [`CTR-USR-010`](#CTR-USR-010), [`SYS-ACC-010`](#SYS-ACC-010), [`SYS-ACC-020`](#SYS-ACC-020).

## Финансы центра

### BR-026 Платформа не принимает деньги учеников {#BR-026}

Платформа не принимает, не хранит и не переводит деньги учеников центру. Она фиксирует платежи, которые центр получил сам (касса, собственный эквайринг, кошелёк сотрудника). Подключённый эквайринг центра присылает вебхук напрямую центру; ключи хранятся в зашифрованном виде. Применяется в [`CTR-FIN-020`](#CTR-FIN-020), [`CTR-FIN-060`](#CTR-FIN-060).

### BR-027 Деньги в дирамах, одна валюта {#BR-027}

Все суммы хранятся целыми числами в дирамах (1 сомони = 100 дирам). Валюта одна — сомони. Округление выполняется только там, где его требует правило, и в одном месте. Применяется в [`CTR-FIN-020`](#CTR-FIN-020), [`CTR-FIN-050`](#CTR-FIN-050), [`PLT-TRF-010`](#PLT-TRF-010).

### BR-028 Начисление на «ученик + группа» {#BR-028}

Счёт на оплату создаётся на связку «ученик + группа» за календарный месяц. Ученик может состоять в любом числе групп; по каждой ведётся отдельный счёт. При переводе ученика в другую группу остаток долга переносится в новую связку. Применяется в [`CTR-FIN-020`](#CTR-FIN-020), [`CTR-FIN-050`](#CTR-FIN-050), [`CTR-GRP-010`](#CTR-GRP-010).

### BR-029 Частичная оплата, переплата, просрочка {#BR-029}

Платёж покрывает конкретный месяц. Частичная оплата и переплата допустимы и фиксируются. Переплата остаётся отдельным лишним остатком ученика и не распределяется на другие месяцы автоматически. Непогашенный остаток становится просроченным с 1-го числа следующего месяца. Применяется в [`CTR-FIN-020`](#CTR-FIN-020), [`CTR-FIN-050`](#CTR-FIN-050).

### BR-030 Баллы — отдельный баланс с лотами {#BR-030}

Баллы ученика хранятся лотами (дата выдачи, срок действия, остаток). Источник — только [`LRN-TCH-040`](#LRN-TCH-040) и [`CTR-CIN-010`](#CTR-CIN-010); купить баллы и начислить их администратором вручную нельзя. Баллы — поощрение, отдельного каталога наград нет. Списание идёт из лотов с более ранним сроком, просроченный остаток сгорает проводкой. Срок жизни и курс обмена задаёт центр. Оплата баллами в отчётах отдельно от денег. Применяется в [`CTR-FIN-030`](#CTR-FIN-030).

### BR-031 Платёж отменяется только сторно {#BR-031}

Проведённый платёж, квитанция и расход не удаляются и не правятся. Отмена и возврат — только сторно (полное или частичное) с обязательной причиной и записью в журнал центра. Сумма сторно не больше уплаченной. Применяется в [`CTR-FIN-040`](#CTR-FIN-040), [`CTR-FIN-070`](#CTR-FIN-070), [`CTR-FIN-080`](#CTR-FIN-080), [`CTR-FIN-090`](#CTR-FIN-090).

### BR-032 Ручная корректировка начисления {#BR-032}

Каждое изменение суммы начисления, сделанное вручную (вступление в середине месяца, пауза, пропуски), выполняется с причиной и записью в журнал центра (было → стало). Применяется в [`CTR-FIN-050`](#CTR-FIN-050).

### BR-033 Уникальность p2p-транзакции {#BR-033}

Номер транзакции p2p-платежа уникален в пределах центра. Повтор отклоняется. Применяется в [`CTR-FIN-060`](#CTR-FIN-060).

### BR-034 Окончание подписки центра {#BR-034}

После окончания оплаченного периода действует льготный срок 7 дней, затем режим «только чтение», через 30 дней — блокировка входа. Данные центра не удаляются. Оплата счёта возвращает полный доступ. Бесплатный тариф «Старт» не истекает. Применяется в [`PLT-BIL-070`](#PLT-BIL-070), [`PLT-DSH-030`](#PLT-DSH-030).

## Доступ и роли

### BR-035 Роль привязана к паре «человек + центр» {#BR-035}

Один аккаунт (по номеру телефона) может состоять в нескольких центрах; роль и права задаются отдельно для каждой пары «человек + центр». Владелец центра управляет подпиской и тарифом, назначает администраторов и кассиров; администратор не меняет тариф и подписку и не удаляет владельца. Применяется в [`CTR-STF-010`](#CTR-STF-010), [`SYS-ACC-030`](#SYS-ACC-030).

### BR-036 Родители и дети {#BR-036}

У ребёнка может быть несколько родителей или опекунов. Ребёнок старше 14 лет (возраст в настройках платформы) может иметь собственный вход. Ребёнок без телефона работает через теневой профиль и вход по логину и паролю. Восстановление доступа при смене номера выполняет администратор центра с подтверждением личности, действие пишется в журнал. Применяется в [`LRN-PRN-010`](#LRN-PRN-010), [`SYS-ACC-030`](#SYS-ACC-030).

### BR-037 Скидки центра {#BR-037}

Скидку назначает администратор вручную ученику или семье по правилу скидки центра (процент или фиксированная сумма, срок действия) с причиной; автоматических правил нет. Скидка уменьшает начисление отдельной строкой: базовая сумма сохраняется, к оплате — базовая минус скидки. В отчётах скидки показываются отдельно от денег и баллов. Применяется в [`CTR-FIN-100`](#CTR-FIN-100), [`CTR-FIN-050`](#CTR-FIN-050).

### BR-038 Права по филиалам {#BR-038}

Владелец видит и управляет всеми филиалами центра. Администратор и кассир привязаны строго к одному филиалу и видят данные только его. Записи журнала аудита без филиала (настройки центра, входы платформы) видит только владелец. Применяется в [`CTR-STF-010`](#CTR-STF-010), [`CTR-FIN-020`](#CTR-FIN-020), [`CTR-SET-010`](#CTR-SET-010), [`CTR-COI-010`](#CTR-COI-010).

### BR-039 Один владелец {#BR-039}

У центра ровно один владелец. Смену или передачу владения выполняет владелец платформы после подтверждения личности, действие пишется в журнал платформы и центра. Применяется в [`PLT-CTR-020`](#PLT-CTR-020), [`CTR-STF-010`](#CTR-STF-010).

### BR-040 Несколько ролей у человека {#BR-040}

Человек может иметь несколько ролей в одном центре, права складываются, после входа выбирается рабочая роль. Платёж, внесённый человеком, он может сверить сам только после явного подтверждения; такая самосверка помечается в журнале и отдельной строкой попадает в отчёт владельцу. Применяется в [`SYS-ACC-030`](#SYS-ACC-030), [`CTR-FIN-070`](#CTR-FIN-070).
