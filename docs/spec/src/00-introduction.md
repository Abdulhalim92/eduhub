# Введение

## Концепция продукта

«Линия» — B2B2C-платформа формата Multi-Tenant SaaS: единое облачное ядро для управления сетью независимых учебных центров с изоляцией их коммерческих данных, локальным учётом начислений, платежей, расходов и зарплат, системой мотивации учеников (баллы, которыми ученик оплачивает часть месяца), B2B-магазином методических материалов и единым каталогом центров на карте города для родителей.

Система разделена на два логических контура: изолированный контур каждого учебного центра (идентификатор `tenant_id`) и глобальный пользовательский контур (Global ID для учеников и родителей, единый каталог центров).

## Как устроен документ

Документ сгруппирован по **областям** (кому принадлежит процесс) и **модулям** (предметные области внутри). Процесс описывается один раз — в области того, кто им владеет. Остальные роли получают короткий подраздел «Сторона центра» или ссылку на номер требования.

| Часть | Область | Основные роли |
|:--|:--|:--|
| A | Управление платформой | SuperAdmin |
| B | Центр: расписание, ученики, финансы, зарплаты | Владелец, Admin центра, Кассир |
| C | Обучение: журнал, кабинеты, каталог на карте | Преподаватель, Ученик, Родитель |
| D | Сквозные службы: аудит, мультиязычность, документы | все роли |

Далее идут сценарии, клиентские платформы, нефункциональные требования, интеграции, каталог бизнес-правил, статусы и переходы, открытые вопросы, история изменений и приложение с трассировкой.

## Идентификаторы требований

Каждое требование имеет устойчивый идентификатор **`ОБЛАСТЬ-МОДУЛЬ-НОМЕР`**, например `PLT-BAL-030`. Номера не переиспользуются и не меняются при переносе раздела: на них ссылаются код, тесты и задачи. Нумерация идёт с шагом 10, чтобы можно было вставить новое требование между существующими.

| Область | Код | Модуль |
|:--|:--|:--|
| Платформа | `PLT-DSH` | Дашборд и рабочие очереди |
| | `PLT-CTR` | Реестр центров и подключение |
| | `PLT-TRF` | Тарифы и лимиты |
| | `PLT-BAL` | Баланс на платформе и овердрафт |
| | `PLT-BIL` | Счета и оплата |
| | `PLT-SMS` | Биллинг SMS-пакетов |
| | `PLT-MKT` | Магазин методик |
| | `PLT-MOD` | Модерация каталога |
| | `PLT-COM` | Рассылки и справочники |
| | `PLT-AUD` | Журнал аудита платформы |
| Центр | `CTR-ORG` `CTR-SCH` `CTR-STU` `CTR-AST` `CTR-CRM` `CTR-ANL` `CTR-FIN` `CTR-PAY` | Структура, расписание, ученики, инвентарь, CRM, аналитика, финансы (начисления, платежи, расходы), зарплаты |
| Обучение | `LRN-TCH` `LRN-PRN` `LRN-CAT` | Преподаватель, кабинеты родителя и ученика, каталог на карте |
| Сквозные | `SYS-AUD` `SYS-I18` `SYS-DOC` | Аудит и безопасность, мультиязычность, печатные формы |
| Прочее | `NFR-…` `INT-…` `BR-…` `Q-…` | Нефункциональные требования, интеграции, бизнес-правила, открытые вопросы |

Новая область или модуль добавляется как новый файл исходников без перенумерации остального.

## Шаблон требования

Заголовок: идентификатор и название. Под ним строка полей и текст:

- **Роль** — кто выполняет или кому принадлежит функция.
- **Согласование** — «согласовано» или «допущение» (принято в прототипе, ждёт решения владельца, см. раздел «Открытые вопросы»).
- **Реализация** — «прототип» (работает в кликабельном прототипе), «частично» или «план».
- **Экран** — где функция видна пользователю. Из полей «Роль», «Реализация» и «Экран» строится приложение «Трассировка».
- **Описание** — что и зачем.
- **Правила** — ссылки на бизнес-правила `BR-…`; сами правила записаны один раз в каталоге.
- **Критерии приёмки** — проверяемые формулировки «Дано / Когда / Тогда». Для планируемых функций критерии добавляются при проработке модуля.

Оформление экранов (цвета, таблицы, пагинация, фильтры) описано не здесь, а в отдельном дизайн-гайде проекта.

## Глоссарий

| Термин | Значение |
|:--|:--|
| Центр (tenant) | Независимая организация-клиент платформы со своими данными, штатом и кассой |
| Global ID | Единый аккаунт родителя или ученика по номеру телефона, объединяющий все центры |
| Shadow ID | Теневой профиль ребёнка без телефона; позже привязывается к номеру ребёнка с сохранением истории |
| Баланс на платформе | Предоплаченные средства центра для оплаты счетов платформы; не касса и не выручка центра |
| Овердрафт центра | Лимит, на который баланс на платформе может уйти в минус; использованная часть — долг перед платформой |
| Долг ученика | Непогашенный остаток начисления за месяц по связке «ученик + группа»; не связан с овердрафтом центра (`BR-019`) |
| Feature Flags | Включение и выключение модулей и лимитов для конкретного центра |
| Режим поддержки (Impersonation) | Вход сотрудника платформы в кабинет центра только для чтения, без финансов, с причиной и таймером; фиксируется в журналах платформы и центра |
| Счёт | Документ платформы центру: продление, смена тарифа, курс, SMS-пакет |
| Заявка на публикацию | Карточка филиала, отправленная центром на модерацию каталога |
| Заявка на курс | Запрос центра на получение курса из магазина методик |
| Передача курса | Создание доступа центра к курсу после оплаты, бонусом или списанием с баланса |
| Собственный курс центра | Курс, который центр создал сам; виден только этому центру |
| Центр у лимита | Центр, у которого использование сотрудников, хранилища или филиалов достигло порога (`BR-021`) |
| Churn Risk (отток) | Риск ухода центра; признак — отсутствие входов более 10 дней |
| NPS | Оценка качества уроков родителем или учеником (1–5 звёзд) |
| Z-отчёт | Итоговый отчёт кассира при закрытии кассовой смены: наличные, эквайринг, p2p |
| Сторно | Отмена финансовой записи отдельной операцией с причиной (физическое удаление запрещено) |
| Лот баллов | Порция баллов ученика с датой выдачи, сроком действия и остатком (`BR-030`) |
| Связка «ученик + группа» | Единица начисления: на неё создаётся счёт за месяц (`BR-028`) |
| Сверка | Подтверждение администратором, что принятый кассиром платёж действительно поступил (`CTR-FIN-070`) |
| p2p-платёж | Перевод родителя на кошелёк или карту сотрудника центра, который фиксируется в платформе (`CTR-FIN-060`) |
