# 80. Тестирование и приёмка

## Принципы

1. **TDD** (`.claude/rules/go.md`): нет кода без падающего теста. Порядок: тест красный по правильной причине, минимальный код, рефакторинг. Код, написанный раньше теста, переписывается.
2. Критерии приёмки требований («Дано / Когда / Тогда» в `docs/spec/src/`) становятся тестами: один критерий — один или несколько тестов с идентификатором требования в имени, например `TestCTR_FIN_020_PartialPayment`.
3. Тесты не проверяют моки вместо поведения, без test-only методов в production-коде.
4. Эталон поведения — требования и критерии приёмки спецификации; клиентский код и прототип в тестах не участвуют.

## Уровни

| Уровень | Что проверяет | Инструменты |
|:--|:--|:--|
| Модульные | Domain и чистые функции: разнесение платежа, порядок списания лотов, проверка лимитов, автомат статусов | `testing`, таблицы случаев |
| Сервисные с БД | Транзакции, блокировки, RLS, идемпотентность, триггеры «только добавление» | PostgreSQL в контейнере, миграции применяются в тесте |
| HTTP | Контракт OpenAPI, коды ошибок, права по ролям | `httptest`, генерируемые клиенты |
| Конкурентные | Параллельные списания, платежи, сверка | `-race`, `errgroup`, много горутин |
| Контрактные интеграции | Вебхуки с подписью, повторная доставка, SMS-заглушка | Фикстуры провайдеров |
| Сквозные | Сценарии из `docs/spec/src/50-scenarios.md` | Тест через HTTP на стенде |
| Нагрузочные | Цели `70-nfr.md` | Генератор данных `cmd/seed` |

## Обязательные наборы

1. **Деньги** — список в `40-money.md`, раздел «Тесты, обязательные для денежного кода».
2. **Изоляция** — тест перебирает таблицы центра и проверяет, что запросы от центра A не видят и не меняют строки центра B; новая таблица без политики RLS роняет тест.
3. **Права** — таблица «действие × роль» из `30-auth-rbac.md`: для каждой ячейки запрет и разрешение. В режиме поддержки все методы записи и финансов отклоняются.
4. **Аудит** — каждая денежная мутация оставляет запись; `UPDATE` и `DELETE` журнала отклоняются; цепочка хэшей валидна и ломается при подмене.
5. **Подписка** — переходы по датам, поведение API в `read_only` и `blocked`.
6. **Вход** — лимиты кода, блокировка, ротация refresh, одинаковый ответ при неверных данных.
7. **Миграции** — применение вверх и вниз на копии, проверка на запрещённые операции.

## Проверка перед «готово» (из `backend/`)

```
go build ./...
go vet ./...
go test ./... -race -count=1
golangci-lint run
govulncheck ./...
```

Нужен свежий вывод всех пяти команд; «должно работать» не принимается (`.claude/rules/workflow.md`).

## Критерии приёмки этапа

Этап принят, если одновременно:

1. Все требования этапа (`85-traceability.md`) покрыты тестами, тесты зелёные.
2. Контракт методов совпадает с `openapi.yaml`, а он — с требованиями; отличия оформлены в спецификации.
3. Для денег выполнены все обязательные тесты, нет `float`, нет записи без аудита.
4. Миграции имеют DOWN и проверены на копии.
5. Пройден обзор `go-reviewer` и аудит `sec-auditor` для модулей с деньгами и правами.
6. Все методы этапа проверены тестами через HTTP на чистой базе.
7. Обновлены спецификация (`python3 tools/build-spec.py` без ошибок) и таблица трассировки.

## Определение готовности задачи

Задача готова, когда выполнено: код и тесты по TDD, проверки из раздела выше, запись в журнал аудита там, где её требует спецификация, документация метода в OpenAPI, согласованные решения занесены в спецификацию, а не оставлены в коде. Если что-то не проверено (например, нет нагрузочного теста) — это явно сказано в отчёте.
