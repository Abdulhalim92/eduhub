# 95. План разработки бэкенда

Подробный план реализации. Источники: `docs/spec/src/` (требования), остальные файлы `docs/tz/`, правила `.claude/rules/`. Фронтенд, прототип и макеты в плане не используются: клиенты могут меняться, поэтому бэкенд проверяется через API и тесты. Контракт описывается требованиями и OpenAPI.

Сроки, команда и бюджет не заданы, размеры шагов относительные: S — до дня работы одного разработчика, M — несколько дней, L — около недели (оценка грубая, не обещание). План составлен агентом `go-planner` и обработан; он остаётся предложением до согласования владельцем.

## 1. Принципы

1. **Порядок работы шага** (`.claude/rules/workflow.md`): план шага, согласование, `go-coder` (по явному «делай»), `go-reviewer`, `go-tester`; для денег и прав дополнительно `sec-auditor`.
2. **TDD** (`go.md`): сначала красный тест по правильной причине. Имя теста содержит идентификатор требования: `TestBR_005_…`, `TestPLT_BAL_040_…`.
3. **Деньги** (`money.md`, `40-money.md`): `int64` в дирамах, проводки только добавляются, одна транзакция на остаток и проводку, `Idempotency-Key`, аудит в той же транзакции.
4. **Изоляция** (`NFR-SEC-010`): общая схема, `tenant_id`, RLS; роль приложения не владеет таблицами и не обходит RLS.
5. **Внешние провайдеры не выбраны** (`Q-006`, `Q-024`, `Q-025`): везде интерфейс плюс заглушка.
6. **Расхождение требования и кода** оформляется правкой спецификации (`Q-NNN`), а не молча.
7. **Шаг считается готовым**, когда из `backend/` свежим выводом прошли `go build ./...`, `go vet ./...`, `go test ./... -race -count=1`, `golangci-lint run`, `govulncheck ./...`; для миграций — тест «up → down → up»; для API — контрактный тест OpenAPI.

Навык `adr`, каталог `docs/adr/`. Без ADR 1–5 шаги 1–6 не начинать.

## 3. Допущения плана (оформить в спецификации до шагов этапа 1)

| № | Допущение | Почему |
|:--|:--|:--|
| A1 | Использование лимита сотрудников и состав центра на этапе 1 считаются по членствам (`memberships`), хранилище равно 0 до появления файлов | `PLT-CTR-060`, `PLT-TRF-010` зависят от этапа 2 (люди), но тарифы и центры нужны раньше |
| A2 | Первый владелец платформы создаётся служебной подкомандой `bootstrap` ролью migrator с записью в аудит | Нужен вход до появления любых пользователей |
| A3 | Стоимость SMS при входе относится к расходам платформы, а не к пакету центра | `SYS-ACC-030`, уточнить при выборе провайдера (`Q-006`) |
| A4 | Для центра с одним сотрудником правило «нельзя сверять свой платёж» смягчено явным подтверждением | `CTR-FIN-070`, `Q-028` |

## 12. Риски и меры

| Риск | Мера |
|:--|:--|
| Указатели и `nil` в PATCH-DTO и nullable-колонках | `*T` только в DTO, `pgtype` только в репозитории; `nilaway` в CI; тест каждого `nil`-поля |
| Гонки и утечки горутин | `SKIP LOCKED`, `FOR UPDATE`, частичные уникальные индексы, `errgroup`, `goleak`, `-race` |
| Взаимоблокировки в оплате счёта | Фиксированный порядок блокировок (ADR 0006), тест встречных транзакций |
| Дублирование бизнес-правил в DTO и сервисе | DTO только синтаксис; правила `BR` только в service и domain |
| Хэш аудита не воспроизводится | Считать в БД над нормализованным `jsonb::text` (ADR 0007), тест «записать → проверить» |
| Утечка между центрами | `set_config(..., true)` внутри транзакции, `FORCE RLS`, каталожный тест покрытия |
| Вход до выбора центра против RLS | Узкая `SECURITY DEFINER`-функция с фиксированным `search_path` |
| Идемпотентность и откат | Ключ в той же транзакции, тест отката |
| Провайдеры не выбраны | Интерфейсы и заглушки; контракт вебхуков не финален |
| Нет первого владельца платформы | Подкоманда bootstrap (допущение A2) |
| Овердрафт центра — кредитный риск | Лимит, индикатор долга, ручное решение о блокировке; правила `Q-002`, `Q-005` |
