# 95. План разработки бэкенда

Пошаговый план реализации бэкенда «Линии» на Go в каталоге `backend/`. Источники:
- требования `docs/spec/src/` (версия 2.5);
- остальные файлы `docs/tz/`;
- правила `.claude/rules/` (`go`, `db`, `migrations`, `money`, `security`, `architecture`, `workflow`).

Контракт задают требования спецификации и OpenAPI; бэкенд проверяется через API и тесты.

Статус документа: предложение, действует до согласования владельцем продукта. Сроки, состав команды и бюджет не заданы (`90-plan.md`). Размеры шагов относительные и описаны в разделе 5.

## 1. Цель и рамки

**Цель.** Нужно построить модульный монолит (`10-architecture.md`), который реализует требования спецификации 2.5 тремя контурами:
- платформа;
- центр;
- ученик и родитель.

Деньги, права и изоляция центров должны быть проверяемыми. Каждое требование имеет тест, а каждое значимое решение оформлено в ADR.

**Ограничения, которые не обсуждаются:**

1. Деньги хранятся как `int64` в дирамах, `float` запрещён (`BR-027`, `money.md`). Проводки только добавляются; ошибки исправляются сторно (`BR-010`, `BR-031`). Изменение остатка и запись проводки выполняются в одной транзакции, а каждая денежная мутация идемпотентна и пишет запись в аудит.
2. Изоляция центров: общая схема, `tenant_id` и RLS. Роль приложения не владеет таблицами и не обходит RLS (`NFR-SEC-010`, `BR-022`).
3. Платформа не принимает деньги учеников, а только фиксирует их (`BR-026`).
4. Миграции выполняются без простоя и обязательно имеют DOWN (`migrations.md`).
5. Секретов в репозитории нет; персональные данные и секреты не попадают в логи (`security.md`).
6. Внешние провайдеры не выбраны (`Q-006`, `Q-024`, `Q-025`). Везде используется интерфейс и заглушка.
7. Решения версии 2.5 обязательны:
   - у центра один владелец (`BR-039`);
   - администратор и кассир привязаны к одному филиалу (`BR-038`);
   - у человека может быть несколько ролей, права складываются (`BR-040`);
   - самосверка платежа допускается только с подтверждением и отметкой (`BR-040`, `CTR-FIN-070`);
   - скидки назначаются только вручную (`BR-037`);
   - баллы служат только поощрением и способом оплаты месяца (`BR-030`);
   - триала и промокодов нет, новый центр начинает с «Старт»;
   - роли менеджера центра нет;
   - настройки центра описаны в `CTR-SET-010`;
   - пробный урок оформляется заявкой без аккаунтов (`CTR-CRM-010`);
   - режим поддержки работает только на чтение (`PLT-CTR-050`).

## 2. Принципы разработки

### 2.1 Порядок работы над шагом

`go-planner` (план шага) → согласование и явное «делай» → `go-coder` → `go-reviewer` → `go-tester` (`workflow.md`). Для миграций дополнительно нужен `db-reviewer`. Деньги, права, вход, вебхуки и шифрование дополнительно проверяет `sec-auditor`. ADR готовит `arch-sysdesign` через навык `adr`.

Один шаг плана — одна задача для `go-coder`. Шаг размера L `go-planner` при проверке готовности делит на подшаги: каждый подшаг — отдельный вызов `go-coder` и отдельный PR.

### 2.2 TDD

Production-кода без падающего теста нет (`go.md`). Порядок такой:
1. Красный тест, который падает по правильной причине.
2. Минимальный код до зелёного теста.
3. Рефакторинг.

Каждый критерий приёмки «Дано / Когда / Тогда» из спецификации превращается хотя бы в один тест. Имя теста содержит идентификатор: `TestCTR_FIN_020_PartialPayment`, `TestBR_037_DiscountRequiresReason`. В колонке «Красный тест первым» перечислены тесты, с которых начинается шаг.

### 2.3 Вертикальные тонкие срезы и walking skeleton

- Этап 0 заканчивается сквозным срезом (шаг 0.15). Один простой сценарий проходит через все слои: HTTP по OpenAPI → сервис → транзакция с RLS → аудит → outbox → воркер → метрики и логи → развёртывание на dev.
- Дальше каждый шаг — вертикальный срез одной возможности: миграция, репозиторий, сервис, HTTP, OpenAPI, тесты, аудит и метрики. Горизонтальных шагов вида «все таблицы», «все репозитории» нет.
- Срез считается готовым только после развёртывания на dev и прохождения smoke-теста.

### 2.4 Малые PR и trunk-based

- Основная ветка `master` всегда зелёная и пригодна к развёртыванию.
- Ветки живут не дольше двух рабочих дней. PR содержит не больше примерно 400 изменённых строк без учёта сгенерированного кода. Слияние — squash, сообщения в формате conventional commits на английском.
- Незавершённая возможность попадает в `master` под выключенным релизным флагом (раздел 2.5), а не живёт в долгой ветке.
- Долгоживущих релизных веток нет. Исправление продуктива делается в `master` и выпускается новым образом.

### 2.5 Флаги

Есть два вида флагов, и смешивать их нельзя (ADR 0015):

| Вид | Назначение | Хранение | Срок жизни |
|:--|:--|:--|:--|
| Релизный флаг | Скрыть незавершённый срез, kill-switch | Конфигурация, типизированный реестр с владельцем и датой удаления | Удаляется после приёмки этапа |
| Модуль центра | Продуктовая настройка тарифа и центра: зарплаты, инвентарь, CRM-воронка, гео-чек-ин (`PLT-CTR-040`) | Таблица `tenant_flags` | Постоянно |

Тесты среза проходят в обоих состояниях флага. Пока у релизного флага не наступила дата удаления, CI предупреждает о нём; после этой даты CI падает.

### 2.6 OpenAPI-first

Первый PR шага с HTTP-методом содержит изменение `api/openapi.yaml` и сгенерированные типы. Контрактный тест в нём должен падать. Обязательные расширения операции:
- `x-requirements` — идентификаторы требований и `BR`;
- `x-permission` — действие из реестра прав;
- `x-idempotent` — для денег, тарифа, баланса, баллов, доступа и SMS.

Линтер схемы отклоняет операцию без этих полей. `oasdiff` в CI запрещает ломающие изменения внутри `/api/v1` (`50-api.md`).

### 2.7 ADR

Значимые решения — выбор библиотеки, схема данных денег, модель прав, политика ретраев, инфраструктура — оформляются в `docs/adr/` до кода (раздел 6). Код, который противоречит принятому ADR, не принимается. Изменение решения оформляется новым ADR, который заменяет прежний.

### 2.8 Трассировка

Каждое требование и `BR` попадает в шаг плана (раздел 20) и в тест с идентификатором в имени. Команда `make trace` сравнивает идентификаторы спецификации с именами тестов и `x-requirements` в OpenAPI. На приёмке этапа покрытие идентификаторов этого этапа должно быть 100%. `85-traceability.md` обновляется вместе со спецификацией.

### 2.9 Расхождения

Если требование и код расходятся, или противоречат друг другу два источника, это оформляется правкой спецификации или новым `Q-NNN`, а не тихо в коде. Известные расхождения перечислены в разделе 8.

## 3. Сквозные соглашения кода

### 3.1 Размещение валидации

| Слой | Что проверяет | Чего не делает |
|:--|:--|:--|
| Transport (DTO, middleware) | Синтаксис по OpenAPI: обязательность, типы, enum, формат, длины, диапазоны (`pageSize` ≤ 100). Нормализация: обрезка пробелов, телефон в E.164 (по умолчанию +992), логин в нижнем регистре. Наличие `Idempotency-Key` для операций `x-idempotent` | Бизнес-правил `BR` нет |
| Service (usecase) | Права (действие плюс область: платформа, центр, филиал), принадлежность объекта, состояние центра и подписки (`BR-012`, `BR-034`), допустимость перехода по `85-states.md`, лимиты, идемпотентность, транзакция и порядок блокировок | Разбора HTTP нет |
| Domain | Чистые инварианты и алгоритмы: `Dirams`, `Reason` (не короче 5 символов: `SYS-ACC-020`, `PLT-BAL-050`, `CTR-STF-010`; обязательность причины — `BR-011`), `Login` (`BR-025`), `Phone`, `Period` (месяц), автоматы статусов, разнесение платежа, порядок списания лотов, расчёт скидки | Ничего не знает о БД и HTTP |
| Repository | Отображение `pgtype` в домен и обратно, перевод нарушений ограничений БД в типизированные ошибки (уникальность → `CONFLICT` с полем) | Бизнес-валидации нет |

Каждое правило `BR` реализуется в одном месте: в domain или service. Ограничения БД — уникальные и частичные индексы, `CHECK amount_dirams > 0`, `EXCLUDE` — служат страховкой от гонок и тестируются отдельно. Длина причины — инвариант `domain.Reason`. OpenAPI её только документирует, а контрактный тест сверяет, что значения совпадают.

### 3.2 Optional-поля и `nil`

- `*T` используется только в DTO transport для необязательных полей.
- Для PATCH, где «очистить значение» отличается от «не менять» (например, срок действия скидки), используется трёхзначный тип `Optional[T]{Set, Null, Value}`.
- В domain необязательное значение выражается явным типом (например, `Optional[T]` или `*T` по ADR 0026); «магические» значения (`0`, `""`, `false`) для отсутствия запрещены. Repository переводит `pgtype.*` в домен. Решение фиксируется ADR 0026.
- Ответы: списки никогда не `null` (`[]`), `omitempty` только для действительно необязательных полей, контракт закреплён в OpenAPI.
- Значение `*ptr` не попадает в логи и метрики без проверки `ptr != nil`.
- `nilaway` в CI: на этапе 0 информативно, с этапа 1 блокирует слияние. Для каждого optional-поля есть тест на три случая: поле отсутствует, равно `null`, задано.

### 3.3 Конкурентность

| Место | Паттерн |
|:--|:--|
| HTTP-обработчики | Без горутин, одна синхронная транзакция |
| Воркер outbox | Пул фиксированного размера: `errgroup.WithContext` и `SetLimit(N)` из конфигурации; при остановке контекст отменяется, невзятые события возвращаются |
| Плановые задачи (начисления месяца, сгорание баллов, подписки, повторяющиеся расходы) | Лидер через `pg_try_advisory_lock`. Обход центров пачками с ограниченной параллельностью `SetLimit(N)`. Каждый центр — своя транзакция, идемпотентность через уникальные ключи. Ошибка одного центра не останавливает остальные и уходит в повтор |
| Чтение «по многим источникам» (дашборды, кабинет родителя с детьми в разных центрах, ADR 0025) | `errgroup.WithContext` с лимитом и `context.WithTimeout`, каждая ветка в своей транзакции центра |
| Конкурентные мутации | `SELECT … FOR UPDATE`, `pg_advisory_xact_lock`, частичные уникальные индексы, `FOR UPDATE SKIP LOCKED`, фиксированный порядок блокировок (ADR 0006) |
| Внешние вызовы | `context.WithTimeout`, circuit breaker; повтор с джиттером только для идемпотентных вызовов |

Тесты: `-race` всегда, `goleak` в пакетах с горутинами, отдельные конкурентные тесты для денег.

### 3.4 Права и изоляция

- Решение о доступе принимается в service по реестру «действие → роли и область». Действует запрет по умолчанию (ADR 0014).
- RLS — второй барьер.
- Платформа читает данные многих центров только через представления и функции с разрешённым набором полей, без платежей, кассы, расходов, зарплат и телефонов (`BR-022`).
- Ответ формируется проекцией DTO по роли. Например, преподаватель не получает телефоны родителей и долги (`01-roles.md`), и это проверяется тестом.

### 3.5 Ошибки и время

- Формат ошибки и коды — по `50-api.md`. Чужой объект возвращает `NOT_FOUND` без раскрытия.
- Время хранится в `TIMESTAMPTZ` в UTC.
- Бизнес-даты — месяц начисления, «1-е число следующего месяца», сутки сгорания баллов — считаются в часовом поясе `Asia/Dushanbe` через интерфейс `clock` (ADR 0018, допущение A4).

## 4. Definition of Ready и Definition of Done

### 4.1 Definition of Ready (шаг можно начинать)

1. Указаны идентификаторы требований и `BR`. Их статус в спецификации — «согласовано» или «допущение» с `Q-NNN`.
2. Есть критерии приёмки «Дано / Когда / Тогда» или они перечислены в шаге.
3. Блокирующие `Q` закрыты, либо допущение принято и записано (раздел 7). Расхождения раздела 8, касающиеся шага, сняты.
4. Нужные ADR приняты (раздел 6).
5. Есть черновик OpenAPI для новых методов, набросок изменения модели данных и план миграции (expand и contract).
6. Права определены: действие, роли, область (платформа, центр, филиал), поведение в режиме поддержки и в состоянии подписки `read_only`.
7. Перечислены события аудита и outbox. Определено, нужна ли идемпотентность.
8. Есть список красных тестов. Размер не больше L, иначе шаг разделён. Решено, нужен ли релизный флаг.

### 4.2 Definition of Done шага

1. Тест был красным до кода (видно по истории PR или описанию), тесты зелёные.
2. Из `backend/` получен свежий вывод пяти команд: `go build ./...`, `go vet ./...`, `go test ./... -race -count=1`, `golangci-lint run`, `govulncheck ./...`.
3. Миграции: тест up → down → up, линтер миграций зелёный, тест покрытия RLS зелёный.
4. OpenAPI обновлён, контрактный тест зелёный, `oasdiff` не нашёл ломающих изменений.
5. Тест матрицы прав дополнен: каждая новая ячейка проверена и на разрешение, и на запрет.
6. Для каждой мутации, которую требует спецификация, есть запись в аудит, и тест это проверяет.
7. В логах нет персональных данных. Для нового потока есть метрики, если он виден в эксплуатации.
8. Пройдены `go-reviewer` и `go-tester`. Для денег, прав, входа и вебхуков — `sec-auditor`.
9. Обновлены трассировка, спецификация (при расхождении) и runbook (при новом эксплуатационном компоненте).
10. Срез развёрнут на dev, smoke-тест прошёл. Состояние релизного флага записано.
11. Всё, что не проверено, явно перечислено в отчёте.

### 4.3 Гейт денежного кода

Применяется к шагам с пометкой **[деньги]** в дополнение к разделу 4.2:
- Нужны тесты из `40-money.md`, раздел «Тесты, обязательные для денежного кода», которые относятся к шагу.
- В ответе на мутацию нет `float`, суммы передаются целыми в полях `…Dirams`.
- Для методов HTTP `Idempotency-Key` обязателен. Повтор с тем же телом возвращает прежний ответ, с другим телом — `IDEMPOTENCY_MISMATCH`. Для операций воркера (сгорание баллов, автоправила, события вебхуков) идемпотентность обеспечивает уникальный ключ события или `source_ref`, и тест проверяет повторную обработку.
- Аудит пишется в той же транзакции. Тест проверяет, что ошибка аудита откатывает действие.
- Конкурентный тест: N параллельных операций под `-race` не нарушают инвариант.
- Граничные значения: 0, 1 дирам, ровно лимит, переполнение `int64`.
- Таблицы движения денег защищены триггером «только добавление». Тест проверяет, что `UPDATE` и `DELETE` отклоняются.
- Пройден `sec-auditor`. Для миграций пройден `db-reviewer`.

### 4.4 Критерии выхода из этапа

Действуют критерии `80-testing-acceptance.md`, раздел «Критерии приёмки этапа», и дополнительно:
- `make trace` показывает 100% по идентификаторам этапа;
- сквозные сценарии этапа (раздел 20.3) проходят через HTTP на чистой базе стенда;
- релизные флаги этапа включены на staging, и для каждого принято решение: включить в продуктиве или удалить;
- runbook этапа написан.

## 5. Формат шага и размеры

Шаги пронумерованы «этап.номер», зависимости указаны по номерам. Размеры:

| Размер | Объём | Разбиение |
|:--|:--|:--|
| S | До одного дня работы одного разработчика | Один PR |
| M | 2–4 дня | 1–3 PR |
| L | Около недели | `go-planner` делит на подшаги до начала работы |

Шаг больше L не допускается. Оценки грубые и не являются обязательством.

## 6. ADR

Каталог `docs/adr/`, навык `adr`. Владелец подтверждает рекомендацию или выбирает альтернативу.

|:--|:--|:--|:--|:--|

| 0002 | HTTP-роутер | Стандартный `net/http.ServeMux` (шаблоны с методами) и собственная цепочка middleware | `chi` (рекомендация `10-architecture.md`) | 0.4 |
| 0003 | Доступ к данным | `sqlc` поверх `pgx` v5. Динамические фильтры — ручной `pgx` с allow-list полей сортировки и фильтров. `sqlx` и ORM не используются | Только ручной `pgx` | 0.7 |
| 0004 | Миграции | `goose`, имена `YYYYMMDDHHMMSS`, SQL up и down, `NO TRANSACTION` для `CONCURRENTLY`, линтер `squawk` | `golang-migrate` | 0.6 |

### 12.1 Тесты денежного контура

1. Все пункты `40-money.md`, раздел «Тесты, обязательные для денежного кода», и `money.md`.
2. Свойства на случайных последовательностях операций (property-based):
   - долг связки = Σ строк начисления − Σ разнесений − Σ оплат баллами;
   - остаток лота ≥ 0;
   - сумма сторно ≤ уплаченного;
   - кэш равен журналу.
3. Внедрение сбоев: ошибка на каждом шаге `RecordPayment`, `ReversePayment`, `SpendPoints`, начисления зарплаты. После любого сбоя в базе нет половинчатых записей.
4. Встречные транзакции по одним и тем же сущностям не дают взаимоблокировок; порядок блокировок соответствует ADR 0006.
5. Календарь: конец месяца, февраль високосного года, полночь по `Asia/Dushanbe` против полуночи UTC.
6. Повтор вебхуков: тот же `event_id`, перестановка порядка, параллельная доставка.
7. Изоляция: каждый метод финансов центра A не видит и не меняет данные центра B. Режим поддержки и платформа получают 403 или пустое представление (`BR-022`).

### 12.2 Аудит

- Тест покрытия: для каждой операции реестра прав с пометкой «денежная» или «правовая» HTTP-тест проверяет запись в аудите. В записи должны быть «было → стало», причина, актор, роль, IP и устройство (`SYS-AUD-030`).
- Список обязательных событий сверяется с `60-audit-integrations.md` и `SYS-AUD-020` после снятия Р6.
- После нагрузочного прогона проверка цепочки хэшей проходит без разрывов.

### 12.3 Проверка безопасности

`sec-auditor` проверяет:
- `RecordPayment`, сверку, сторно, баллы, вебхуки эквайринга, шифрование ключей;
- права по филиалам и самосверку;
- журналы на отсутствие персональных данных и ключей;
- подбор `Idempotency-Key` и чужих идентификаторов (IDOR).

Найденные проблемы уровней critical и high устраняются до приёмки, medium — по решению владельца с записью в рисках.

### 12.4 Нагрузка

Профиль из `70-nfr.md` (подтверждается `Q-027`):
- данные: 500 центров, 50 000 учеников, 5 000 платежей в день;
- пиковые сценарии:
  - 50 параллельных платежей по одной связке;
  - всплеск вебхуков 100 в секунду с повторами;
  - задача начислений месяца на 50 000 связок;
  - сгорание баллов.

Критерии:
- p95 записи не больше 500 мс;
- задача начислений укладывается в окно 30 минут и не блокирует запросы;
- нет взаимоблокировок;
- кэши равны журналам;
- цепочка аудита цела.

Результат фиксируется в отчёте приёмки.

## 17. Операционная часть

### 17.1 Окружения

| Окружение | Назначение | Данные | Выкладка |
|:--|:--|:--|:--|
| `local` | Разработка, `docker-compose` | Генератор `cmd/seed` | Вручную |
| `test` (CI) | Тесты с `testcontainers` | Фикстуры | На каждый PR |
| `dev` | Интеграция срезов, smoke-тесты | Синтетические | Автоматически из `master` |
| `staging` | Приёмка этапов, сквозные сценарии, учения по восстановлению, нагрузка | Синтетические, объём `70-nfr.md` | По тегу релиза |
| `prod` | Пилот и эксплуатация | Реальные (после `Q-014`) | По тегу с ручным подтверждением |

До решения `Q-024` `dev` и `staging` работают на временной площадке только с синтетическими данными. Продуктив разворачивается только после P.1. Доступ к продуктиву именной, с минимальными правами и журналом действий.

### 17.2 CI/CD

- **PR:**
  - форматирование и `go mod tidy`, `go vet`, `golangci-lint` (включая `gosec`), `nilaway`;
  - `go test ./... -race -count=1` с `testcontainers`;
  - линтер миграций и цикл up → down → up, тест покрытия RLS;
  - линтер OpenAPI, проверка «схема ↔ код», `oasdiff`;
  - `govulncheck`, `gitleaks`, проверка лицензий;
  - сборка образа и его сканирование, отчёт `make trace`.
- **`master`:** то же, плюс публикация образа с тегом коммита и SBOM, выкладка на dev, smoke-тест.
- **Тег релиза:** выкладка на staging (задача миграций до приложения), сквозные сценарии этапа, затем ручное подтверждение и выкладка в продуктив.
- **Ночной прогон:** полный набор сквозных сценариев, нагрузочный дымовой тест, `govulncheck` по свежей базе уязвимостей.
- **Еженедельно:** проверка восстановления на staging (раздел 17.6).
- Каноничная цель — `make ci`. Конфигурация CI-провайдера только вызывает её.

### 17.3 Секреты

- Источник — секрет-хранилище, приложение получает секреты переменными окружения (ADR 0016). В репозитории, образах и логах секретов нет, `gitleaks` блокирует PR.
- Перечень секретов:
  - пароли ролей БД;
  - ключи подписи JWT (с `kid`);
  - мастер-ключ шифрования ключей эквайринга (с версией);
  - секреты вебхуков шлюзов и эквайринга;
  - токен Telegram-бота и секрет вебхука;
  - ключи SMS-провайдера и геокодера;
  - доступ к объектному хранилищу.
- Ротация описана в runbook для каждого секрета. JWT и мастер-ключ ротируются без простоя (старый ключ действует на чтение до истечения).

### 17.4 Наблюдаемость

- **Логи:** JSON `slog` с полями `request_id`, `trace_id`, `tenant_id`, `actor_id`, маршрут, статус, длительность. Персональные данные, токены, пароли, ключи и номера карт отсутствуют, телефоны в маске. Срок хранения операционных логов — 30 дней (журнал аудита хранится отдельно, `NFR-SEC-050`).
- **Метрики (Prometheus):**
  - HTTP (RPS, латентность, ошибки по маршрутам), пул БД, медленные запросы;
  - outbox (глубина, возраст старейшего события, `dead`);
  - SMS (отправлено, ошибки, расход бюджета);
  - вебхуки (принято, отклонено по подписи, `unmatched`);
  - подписки по состояниям, задачи планировщика (длительность, ошибки).
- **Трассировка:** OpenTelemetry для HTTP, запросов `pgx` и внешних вызовов, сквозной `trace_id` в логах и событиях outbox.
- **Алерты:**
  - скорость расхода бюджета ошибок SLO;
  - рост 5xx;
  - разрыв цепочки аудита;
  - расхождение кэша и журнала (баланс платформы, долги, лоты);
  - рост `dead`;
  - всплеск неверных подписей вебхуков;
  - превышение бюджета SMS;
  - неудачная резервная копия;
  - отставание миграций.

### 17.6 Резервное копирование и восстановление

- Ежедневная полная копия и непрерывный архив WAL (ADR 0022). Копии шифруются и хранятся отдельно от основной базы. Копия объектного хранилища ежедневная.
- Проверка восстановления:
  - еженедельно автоматически на staging: восстановление, `/readyz`, проверка цепочки аудита, сверка кэшей;
  - ежеквартально учение с замером RTO и протоколом (P.2, 6.6).
- Неудачная копия или проверка даёт алерт и инцидент.

### 17.7 Безопасность

- **Модель угроз:** v1 в шаге 0.18, обновления в 3.1 и перед P.4. Ключевые угрозы и меры:
  - утечка между центрами: RLS, тест покрытия, `AssertIsolated`;
  - подбор OTP и SMS-накрутка: лимиты, глобальный бюджет, только номера +992 по умолчанию;
  - подмена вебхуков и повтор: подпись до записи, дедупликация;
  - злоупотребление режимом поддержки: только чтение, таймер, журнал центра;
  - инсайдер в центре: самосверка с отметкой, скидки и сторно с причиной и сигналами `SYS-AUD-040`;
  - перебор чужих идентификаторов: `NOT_FOUND` без раскрытия;
  - утечка ключей эквайринга: envelope encryption;
  - подделка `initData` Telegram;
  - сбор данных из публичного каталога: лимиты, минимум полей.
- **Зависимости:** `govulncheck` на каждый PR и каждую ночь, сканирование образа, проверка лицензий, обновление зависимостей не реже раза в месяц.
- **Криптография:** `argon2id` для паролей, SHA-256 для цепочки, Ed25519 для JWT. MD5 и SHA-1 запрещены (`security.md`).
- **Транспорт:** только TLS, HSTS, CORS по allow-list.
- **Проверки:** `sec-auditor` на шагах с деньгами, правами, входом и вебхуками; полный аудит перед пилотом (P.4).

### 17.8 Нагрузочные проверки

- Инструмент — сценарный генератор нагрузки (например, k6), данные из `cmd/seed`.
- Профили:
  - вход по SMS (с заглушкой шлюза);
  - списания с баланса платформы (1.25);
  - платежи, вебхуки, начисления месяца (12.4);
  - рассылка уведомлений (4.9);
  - публичный каталог (5.12);
  - полный профиль (6.5).
- Дымовой нагрузочный тест ночью на staging, полный прогон на приёмке этапов 1, 3, 4, 5 и в 6.5. Результат сравнивается с SLO; регрессия больше 20% p95 блокирует релиз.

### 17.9 Релизы и откат

- Версия — тег SemVer, образ неизменяем и привязан к коммиту. Заметки о выпуске собираются из conventional commits.
- Миграции по схеме expand/contract:
  1. Добавить (nullable, новые таблицы, индексы `CONCURRENTLY`).
  2. Выложить код, совместимый со старой и новой схемой.
  3. Заполнить данные пачками.
  4. Сузить схему (`SET NOT NULL`, удаление) отдельным релизом после окна (`migrations.md`).
- Порядок выкладки: задача миграций → приложение (rolling update с `readyz`) → smoke-тест.
- Откат: прежний образ, совместимый с расширенной схемой. DOWN-миграции применяются в продуктиве только если проверены на копии. Данные денег не откатываются: ошибка исправляется сторно.
- Kill-switch через релизный флаг для новой функции без перевыкладки.

## 18. Риски

| Риск | Мера |
|:--|:--|
| Разыменование `nil` и неверная обработка указателей в PATCH-DTO и nullable-колонках | `*T` только в DTO, `Optional[T]` для PATCH, `pgtype` только в репозитории, `nilaway` в CI, тест «отсутствует, `null`, задано» для каждого optional-поля (раздел 3.2) |
| Утечки горутин и гонки | Горутины только в воркере и fan-out с `errgroup.WithContext` и `SetLimit`; `goleak`, `-race`; конкурентность мутаций решается в БД (`FOR UPDATE`, `SKIP LOCKED`, частичные уникальные индексы) |
| Неправильное размещение валидации: дубли и рассинхрон контрактов | Синтаксис в OpenAPI и transport, правила `BR` только в service и domain, ограничения БД как страховка; контрактный тест сверяет константы (раздел 3.1) |
| Утечка данных между центрами | RLS с `FORCE`, `set_config(..., true)` внутри транзакции, тест покрытия по каталогу, `AssertIsolated`, проекции платформы без финансов (`BR-022`) |
| Двойное списание и половинчатые проводки | Одна транзакция, `Idempotency-Key`, `FOR UPDATE`, аудит в той же транзакции, внедрение сбоев (12.1) |
| Взаимоблокировки | Фиксированный порядок блокировок (ADR 0006), тест встречных транзакций |
| Узкое место цепочки аудита под одной блокировкой | Цепочка на (`scope`, центр), замер в нагрузке; при необходимости — новый ADR |
| Ошибки на границе месяца и суток | Бизнес-календарь `Asia/Dushanbe` (ADR 0018), тесты календаря |

| Подмена или повтор вебхуков | Подпись до записи, дедупликация по (`provider`, `event_id`), журнал безопасности |
| Потеря мастер-ключа делает ключи эквайринга нечитаемыми | Версии ключа, резервная копия в секрет-хранилище, runbook ротации и восстановления |
| Нет управляемого PostgreSQL в стране (`Q-024`) | Контейнеры без привязки к облаку; заранее оценить собственную эксплуатацию (копии, обновления, репликация) |
| Провайдеры не выбраны (`Q-006`, `Q-025`) | Интерфейсы и заглушки, контракт вебхуков не финален, реальный провайдер — отдельный шаг |
| Расхождения в спецификации приводят к неверной реализации | Раздел 8 снимается до шага, DoR пункт 3 |
| Дрейф спецификации и кода | `make trace`, `x-requirements`, правка спецификации через `Q-NNN` |
| Ломающие изменения API | `oasdiff` в CI, устаревание через `Deprecation` (`50-api.md`) |
| Блокирующие миграции на больших таблицах | Линтер миграций, expand/contract, прогон на объёме staging |
| Затор в outbox | Метрики глубины и возраста, алерт, ограниченный пул, runbook разбора `dead` |

- Клиентские приложения и вёрстка: план покрывает только бэкенд.

## 22. Что решает владелец и ближайшие шаги

**Что решает владелец:**
1. Подтвердить или изменить ADR из раздела 6. Для этапа 0 нужны 0001–0013, 0015–0018, 0021, 0026.
