# 10. Архитектура

Формат по `.claude/rules/architecture.md`: компоненты, потоки данных, хранение, надёжность, безопасность, trade-offs.

## Компоненты

Модульный монолит на Go в `backend/` (свой `go.mod`). Один репозиторий, один бинарник сервера и один бинарник воркера (общий код, разные точки входа). Модули не обращаются к таблицам друг друга: только через интерфейсы сервисов или события.

## Слои и зависимости

В каждом модуле: `transport` (HTTP, DTO) → `service` (сценарии, транзакции) → `domain` (сущности, инварианты, чистые функции без знания БД и HTTP) ← `repository` (pgx). Зависимости направлены внутрь: domain ничего не импортирует из transport и repository. Размещение валидации — `.claude/rules/go.md`.

Предлагаемая структура:

```
backend/
  cmd/server/            точка входа HTTP
  cmd/worker/            outbox, уведомления, фоновые задачи, сгорание баллов, подписки
  cmd/seed/              генератор демонстрационных центров
  internal/<module>/{transport,service,domain,repository}
  internal/platform/     db (pgx pool, транзакции), httpx, config, clock, idgen, i18n, crypto
  migrations/            SQL, up и down
  api/openapi.yaml       контракт (источник для кода и проверки)
```

## Технологии (рекомендации, фиксируются ADR)

| Область | Выбор | Почему |
|:--|:--|:--|
| Язык | Go (актуальная стабильная версия), `go.mod` в `backend/` | Требование проекта |
| HTTP | `net/http` + `chi` | Минимум магии, совместим со стандартной библиотекой |
| БД | PostgreSQL 16+, драйвер `pgx` v5 | RLS, транзакции, `FOR UPDATE`, `jsonb` |
| Миграции | `goose` или `golang-migrate`, SQL up/down | Правила `migrations.md` |
| Запросы | `pgx` с ручными SQL или `sqlc` | Параметризация обязательна (`db.md`) |
| Контракт | OpenAPI 3, генерация типов | Единый формат и проверка в CI |
| Логи | `slog`, JSON, `request_id` | Правила `go.md` |
| Метрики и трассы | Prometheus и OpenTelemetry | Наблюдаемость (`70-nfr.md`) |
| Очередь | Таблица outbox в PostgreSQL и воркер | Нет отдельного брокера на старте, меньше эксплуатации |
| Кэш и лимиты | Таблицы PostgreSQL на старте, Redis добавить при необходимости | Проще в эксплуатации при размещении в стране |
| Файлы | S3-совместимое хранилище | Скриншоты p2p, материалы, PDF |
| PDF | Генерация на сервере (шаблоны ru/tg) | Квитанции без фискальной функции |
| Пароли | `argon2id` | `go.md`, `security.md` |

## Потоки данных (ключевые)

1. **Внесение платежа** (`CTR-FIN-020`): HTTP → проверка прав (кассир, центр) → транзакция: проверка идемпотентности, блокировка начисления, запись платежа, разнесение по начислениям, запись переплаты, запись в аудит, событие в outbox → ответ → воркер формирует квитанцию PDF и уведомление родителю.
2. **Вебхук эквайринга** (`INT-ACQ-010`): HTTP без токена → проверка подписи до любой записи → дедупликация по идентификатору события → транзакция как в п. 1 со статусом «Принят» и источником `acquiring`.
3. **Оплата счёта платформы** (`PLT-BIL-030`): онлайн-шлюз присылает вебхук → закрытие счёта, применение действия (смена тарифа, продление, передача курса) в одной транзакции, проводка баланса, аудит.
4. **Вход по SMS** (`SYS-ACC-030`): запрос кода (лимиты по номеру и IP) → outbox → воркер шлёт SMS → проверка кода → сессия.
5. **Сгорание баллов и состояния подписки**: воркер по расписанию проводит просроченные лоты и переводит подписки между состояниями; каждый шаг идемпотентен.

## Надёжность

- **Транзакции:** изменение остатка и запись проводки в одной транзакции; явный `ROLLBACK` при ошибке (`money.md`).
- **Outbox:** события пишутся в ту же транзакцию, что и бизнес-данные; воркер доставляет at-least-once, получатели идемпотентны.
- **Повторы и DLQ:** экспоненциальная задержка, после N попыток запись уходит в `dead` для разбора, администратор платформы видит счётчик.
- **Circuit breaker и таймауты:** на каждый внешний вызов `context.WithTimeout`; при падении SMS-провайдера уведомление переходит на Telegram и Push (`PLT-SMS-040`).
- **Блокировки:** `SELECT … FOR UPDATE` или `pg_advisory_xact_lock` по счёту или связке; порядок блокировок фиксирован, чтобы не получать взаимоблокировки.
- **Фоновые задачи:** блокируются по `pg_try_advisory_lock`, чтобы работать в одном экземпляре.

## Безопасность

Подробно — `30-auth-rbac.md`, `70-nfr.md`. Кратко: проверка прав в каждом обработчике (RBAC плюс принадлежность центру), RLS как второй барьер, подписи вебхуков, шифрование ключей эквайринга, нет PII и секретов в логах, rate limiting публичных эндпоинтов, `govulncheck` в CI.

## Trade-offs

| Вопрос | Варианты | Рекомендация |
|:--|:--|:--|
| Структура | A: модульный монолит. B: микросервисы. C: монолит без модулей | A. Команда небольшая, транзакции между финансами и баллами должны быть атомарными, границы модулей оставляют путь к разделению |
| Очередь | A: outbox в PostgreSQL. B: Kafka или NATS. C: Redis streams | A на старте. Меньше компонентов при размещении в стране; B при росте нагрузки |
| Доступ к данным | A: `pgx` и ручной SQL. B: `sqlc`. C: ORM | A или B. Нужен точный контроль блокировок и RLS; ORM скрывает их |
| Изоляция | A: общая схема и RLS. B: схема на центр. C: база на центр | A (решение владельца). Проще миграции и отчёты платформы; цена — дисциплина `tenant_id` и тесты RLS |
| Книга операций | A: двойная запись. B: журнал движений по счетам | B для центров и баланса платформы: достаточно одной суммы со знаком и обязательного основания. A только если появятся несколько валют или внешняя бухгалтерия |

Решения, принятые в ходе реализации, фиксируются через навык `adr`.
